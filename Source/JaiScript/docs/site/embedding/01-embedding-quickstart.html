    Embedding Quickstart​

    JaiScript's whole integration pitch fits in two lines. It compiles into your project as a static lib plus headers, and an engine is just an object:

    C++
    auto e = jai::engine::make();
e->execute("print(\"hello\");");   // a bare engine ships a basic print

    There is no global interpreter state anywhere: every script_value carries its engine, so two engines are fully isolated (separate globals, separate classes, separate budgets) and two engines on two threads need no locks. engine::make() always returns a std::shared_ptr<engine>. The private constructor makes it impossible to create one any other way (include/jaiscript/core/engine.hpp, engine::make).

    Build it into your project​

    The library is one CMake target, JaiScript::jaiscript. Linking it brings the include path, the C++20 requirement, /bigobj on MSVC and ws2_32 on Windows; as a subproject only the library builds (tools, tests and examples stay off), and its MSVC runtime follows yours:

    CMake
    add_subdirectory(JaiScript)                       # or: find_package(JaiScript 0.1 CONFIG REQUIRED)
target_link_libraries(my_game PRIVATE JaiScript::jaiscript)

    The installed route, every option and the MSVC runtime rules are in docs/BUILD.md; examples/embed_quickstart/ is a complete host (a bound class, a signal, saves, hot reload, rails, the debugger) that builds either way. The headers a host usually includes:

    C++
    #include <jaiscript/core/engine.hpp>              // engine, script_value, the error types
#include <jaiscript/core/dynamic_binder.hpp>      // dynamic_binder, convert_script_function
#include <jaiscript/stdlib/stdlib.hpp>            // jai::stdlib::register_all
#include <jaiscript/serialization/convenience.hpp> // jai::to_json / from_json / to_binary / from_binary
#include <jaiscript/debug/connector.hpp>          // jai::debug::listen (VS Code attach)

    <jaiscript/jaiscript.hpp> pulls the core, the binder and the archives in one include (not the standard library).

    Execute and read results: as<T>​

    execute() returns a jai::script_value; convert it with as<T>() or the direct accessors as_int(), as_float(), as_string(), as_bool().

    C++
    // compiled and run against the library
auto eng = jai::engine::make();               // always a shared_ptr<engine>
jai::stdlib::register_all(eng);               // formatted print, to_string, to_json, math, ...

jai::script_value r = eng->execute("2 + 2");
r.as<int>();                                        // 4
eng->execute("6 * 7").as_int();                     // 42
eng->execute("\"jai\" + \"script\"").as<std::string>();  // "jaiscript"
eng->execute("1.5 * 2").as<double>();               // 3.0
eng->execute("3 > 2").as<bool>();                   // true

    Output:

    as<int>: 4
as_int(): 42
as<std::string>: jaiscript
as<double>: 3
as<bool>: 1

    (3 and 1 are how std::cout prints 3.0 and true without showpoint / boolalpha.)

    Note the stdlib is opt-in. A bare engine ships two conveniences: a basic print (concatenates its arguments to the host-controlled output stream; no {} formatting) and format_value (so template-string specs like ${hp:.1f} work on every engine). Nothing else: no to_string, no containers library, no JSON. jai::stdlib::register_all(eng) brings the standard library and upgrades print in place to the formatted {} version (same name, one registration: the upgrade replaces, it never stacks). Neither print grants any authority: output goes only to the stream the host installed via set_output_stream: a log file, a capture buffer, or a discarding sink. The opt-in surface is part of the sandbox story (see Safety Rails).

    Registering C++ functions​

    C++
    // Typed: signature drives conversion and overload resolution
eng->add_function("square", [](jai::script_int n) { return n * n; });
eng->execute("square(12)").as_int();      // 144

// Variadic: you receive the raw argument vector
eng->add_variadic_function("sum_all", [&eng](const std::vector<jai::script_value>& args) {
    jai::script_int total = 0;
    for (auto& a : args) total += a.as_int();
    return jai::script_value(total, eng.get());
});
eng->execute("sum_all(1, 2, 3, 4)").as_int();   // 10

    Registering the same name twice with different signatures creates an overload set resolved by argument types at the call site. Use add_variadic_function for print-shaped functions and optional parameters.

    Every script_value you construct yourself needs the engine pointer: jai::script_value(3.14159, eng.get()), or use the convenience factories eng->make_value(v) / eng->make_null() / eng->make_array() / eng->make_map().

    Globals: copies vs live bindings​

    C++
    eng->add_global("PI", jai::script_value(3.14159, eng.get()));   // copied in

int hp = 100;
eng->add_global_ref("hp", hp);      // LIVE binding (cpp_bound) — no copy
eng->execute("hp = hp - 25;");      // hp is now 75 in C++
hp = 1;                              // and C++ writes are visible to the script
eng->execute("hp").as_int();        // 1

    Output:

    hp after script damage: 75
script sees: 1

    add_global_ref on a primitive (int8..64, unsigned variants, float, double, bool, char, std::string) creates a cpp_bound value: a typed pointer box that reads the live C++ variable and writes through to it. For non-primitive types it falls back to a non-owning aliasing shared_ptr. The caller must guarantee the object outlives the engine (documented in the header, engine.hpp add_global_ref).

    What write-through covers​

    The write-through matrix holds on both backends (the interpreter and the VM, chapter 3); the test suite holds them to it:

    • Name-level assignment and compound assignment write through: hp = hp + 50;, hp += 7;, ++hp, hp-- all mutate the C++ variable, at every width: int8 through uint64, float/double, and std::string +=.
    • Reads are always live: change the C++ variable between executes and the script sees the new value.
    • Mixed conversions keep the binding: boundInt += 2.5 converts (truncates) and still writes through.
    • A bound char is a width-1 bound int. It reads as its code point.

    Where the binding deliberately drops (detach rules)​

    • clone() of a bound primitive detaches. It snapshots the value. A plain copy of the script_value stays bound.
    • Every store detaches. Storing a bound value into an array element, map slot, or object member, whether by literal construction ([hp], {"k": hp}), assignment, push, or an implicit-this member store, snapshots the value at store time. Write-through belongs to the registered name (and references/captures/by-ref params bound to it), never to stored copies.
    • Plain = through a script reference (auto& r = hp; r = r + 4;) stores a detached result into the slot and drops the binding; compound assigns through refs (r += 5) DO write through.

    The exact-width as<T&> aliasing rules​

    A non-const as<T&> on a bound value gives you a live reference into the C++ variable (zero-copy, reads and writes are real), but only when the binding's width and signedness exactly match the script-side type:

    as<T&> requestaliases live when the bound C++ type is
    as<jai::script_int&>exactly int64_t (or script_int)
    as<jai::script_float&>exactly double
    as<std::string&>std::string
    as<jai::script_bool&>bool

    Anything else (an int32_t behind as<script_int&>, a float behind as<script_float&>) throws a catchable jai::runtime_error, never std::bad_variant_access, and never silently reads the wrong bytes.

    C++
    // compiled and run against the library
jai::script_int gold = 10;
eng->add_global_ref("gold", gold);
auto v = eng->execute("gold");            // a bound alias, not a snapshot
v.as<jai::script_int&>() += 5;            // gold is now 15 in C++

int32_t narrow = 5;
eng->add_global_ref("narrow", narrow);
eng->execute("narrow").as<jai::script_int&>();   // throws jai::runtime_error
// "cannot bind a non-const script reference to a C++-bound variable of a different width"
eng->execute("narrow += 7;");             // by NAME any width works (decoded reads/writes)

    Output:

    gold after as<script_int&> += 5: 15
int32 as<script_int&>: cannot bind a non-const script reference to a C++-bound variable of a different width
narrow after script += 7: 12

    The same rules apply to non-const T& parameters of add_function bindings: a bound argument of exactly-matching width aliases the live variable (the callee's writes land in C++). A plain script argument works as in C++: the callee gets a copy of the value the argument names, and when it returns (or throws) its final value is stored back into that argument with the store a script = makes, so the variable's declared type converts or rejects it with the usual text.

    C++
    eng->add_function("heal", [](int64_t& hp, int64_t amount) { hp = std::min<int64_t>(hp + amount, 100); });
eng->add_function("tag", [](std::string& name) { name += " (healed)"; });
    jaiscript
    int hp = 40;
heal(hp, 25);             // hp is 65
var party = [10, 20];
heal(party[1], 90);       // party[1] is 100
tag(player.name);         // a field, a map value, a C++ property (through its setter), v.x of a vector
heal(hp + 1, 5);          // a temporary: the callee works on a copy, nothing is stored back

    Every value kind writes back the same way: integers, floats, bool, std::string, std::vector, std::map, jai::script_value, std::shared_ptr<T>, enums and the host types a math adapter binds. A registered class taken as T& is the live object itself and needs no store. Any lvalue a script T& parameter binds is written back (a variable, a field, an element, a map value, a static, a reference, a C++ property) and so is a math component (v.x); a literal or a temporary is passed as a copy and nothing is stored. A const T& parameter is a read and costs nothing extra, and a binding with no non-const T& parameter runs exactly as before: the choice is made when the function is bound.

    Running a script file​

    C++
    eng->add_include_path("scripts");           // where import/include look after the file's own folder
eng->execute_file("scripts/game.jai");      // parse (or load the .jaibite sibling), check, run

    execute_file attributes every node to the file's canonical path, whatever spelling you pass: check listings, stack traces and debugger breakpoints all name it. It keeps a parsed copy beside the source (game.jai gets game.jaibite); add *.jaibite to your .gitignore, or turn the cache off with eng->jaibite_cache(false). Functions, classes and globals the file declares stay in the engine for later calls.

    Calling script from C++​

    A script function is a value. Look it up by name and call it with a vector of arguments; the result is a checked_result, not an exception:

    jaiscript
    int damage_for(int level) { return level * 3; }
    C++
    // examples/embed_quickstart makes these calls
jai::script_value fn = eng->get_variable("damage_for");
jai::checked_result<jai::script_value> r = fn.as_function()({eng->make_value(int64_t{4})});
if (!r) { throw std::runtime_error(eng->format_error(r)); }   // "Division by zero in integer operation", ...
int64_t dmg = r.value().as_int();                                  // 12
    • Errors. A run-time error comes back in the result: eng->format_error(r) is its text and eng->format_stack_trace() the script stack. A script throw that nothing catches crosses the call as a jai::script_exception carrying the thrown text, so a host that calls script from its frame loop wants both a result check and a catch.
    • The budget. A call made while no script runs is a host entry: it gets a fresh execution-budget deadline, like execute() (Safety Rails).
    • external_call_guard. Needed only when the call can happen while a script is running: from inside a host function the script called, or from a signal the script emitted. Construct jai::engine::external_call_guard guard(eng.get()); around the call so reference parameters do not bind against the script call in flight. A call from your own loop needs nothing; the guard is harmless there.
    • A typed wrapper. auto damage = jai::convert_script_function<int64_t(int64_t)>(fn); gives a std::function for callbacks. It never throws: a failure goes to set_script_error_handler and the call returns R{}.

    Reading script state back​

    get_variable(name) reads a global; as<T>() converts it. How a container comes out follows its declared type: array<int>, array<string> and the other typed arrays are raw buffers that copy out as a std::vector, and only array<var> has a script_value vector to view:

    jaiscript
    int score = 7;
array<string> log = ["spawned", "hit"];
map<string, int> kills = {"orc": 3, "troll": 1};
array<var> loot = [12, "rope", 2.5];
    C++
    // examples/embed_quickstart makes these calls
int64_t score = eng->get_variable("score").as_int();
auto log   = eng->get_variable("log").as<std::vector<std::string>>();              // a typed array copies out
auto kills = eng->get_variable("kills").as<std::map<std::string, int64_t>>();

jai::script_value loot = eng->get_variable("loot");   // hold the value: as_array() views into it
const std::vector<jai::script_value>& items = loot.as_array();       // array<var> only

jai::script_value log_value = eng->get_variable("log");
log_value.unchecked_array_node()->for_each(eng.get(), [](const jai::script_value& line) {
    std::cout << line.as_string() << "\n";                         // any array kind, no copy of the buffer
});

    as_array() on a typed array raises an error that names the type and the extraction that works (array<string> is a typed buffer: ... extract as<std::vector<std::string>>). unchecked_array_node() requires is_array(). A bound C++ object comes back with as<std::shared_ptr<Monster>>(), sharing the live object; a host function that takes bound_array<int64_t>& mutates a typed array in place (dynamic_binder). Writing back is add_global(name, value), or an execute that assigns.

    Error surfaces​

    Checking is strict by default, so the first surface you meet is a load error: the script is rejected before a single statement runs.

    C++
    // compiled and run against the library
eng->execute("undefined_thing + 1");   // throws jai::static_check_error — nothing ran

    what() is the whole accumulated listing, compiler style: every error in the file, not just the first:

    static check failed:
<script>:1:1: error: use of undeclared identifier 'undefined_thing'
    undefined_thing + 1;
    ^

    Names your host injects at run time aren't in the script's text, so the checker cannot see them. extern declares one without defining it, and the same script becomes a runtime error instead, catchable and raised only if control flow actually reaches the name:

    C++
    eng->execute("extern function spawn_wave; spawn_wave(3);");
// throws jai::runtime_error: "'spawn_wave' is declared extern but never defined"

    (what() appends the error's category, <text>: <category>, when the text does not already begin with it: Cannot apply '+=' to string and int: Type mismatch. A script catch sees the text alone.)

    The other two surfaces are unchanged by checking, and the engine survives all of them:

    C++
    eng->execute("throw \"from script\";"); // uncaught script throw -> jai::runtime_error("from script")
eng->execute("var x = ;");              // throws jai::parse_error:
                                        //   "Parse error: <script>:1:10: Expected expression"
eng->execute("40 + 2").as_int();        // 42

    Every one of them derives from std::exception, so one catch (const std::exception&) is a valid backstop: jai::static_check_error for load-time type and name errors, jai::parse_error for syntax, and jai::runtime_error for anything raised while running (an uncaught script throw arrives as jai::script_exception, which derives from it). jai::parse_error and jai::runtime_error share the base jai::exception, which carries a location(); jai::static_check_error derives from std::runtime_error directly. Its listing is the location. eng->format_stack_trace() / eng->last_stack_trace() give the script stack of the most recent failure. For a throw two calls deep:

    jaiscript
    function inner() { throw "boom"; }
function outer() { inner(); }
outer();
      at inner (<script>:1)
  at outer (<script>:2)
  at <script> (<script>:3)

    For errors that surface where C++ cannot throw (converted callbacks, signal receivers), install a sink with eng->set_script_error_handler(...). The default sink is std::cerr (engine.hpp, set_script_error_handler).

    One subtlety worth knowing: some recoverable parse errors make the parser synchronize and return null instead of throwing, so the robust contract to code against is "execute() returns and the engine stays usable", not "every bad input throws".

    The time source​

    Every time:: call a script makes (Time in the language guide) reads one engine-owned clock, and the host can replace it. Three providers make up the source: monotonic (a steady reading, the clock behind time::now(), time::engine_elapsed(), time::execute_elapsed() and every stopwatch), wall (nanoseconds since the Unix epoch in UTC, behind time::unix_time() and every date) and sleep (what time::sleep and time::sleep_ms do). An empty provider selects the system one: steady_clock, system_clock, this_thread::sleep_for.

    A virtual clock is the whole integration for tests, replays, netcode and deterministic simulation. The script sees exactly the time the host says it is:

    C++
    // compiled and run against the library
std::chrono::nanoseconds sim_now{0};
const auto epoch = std::chrono::nanoseconds(1700000000000000000LL);   // 2023-11-14T22:13:20Z
eng->time_source(
    [&] { return sim_now; },                                          // monotonic
    [&] { return epoch + sim_now; },                                  // wall
    [&](std::chrono::nanoseconds d) { sim_now += d; });              // sleep advances the simulation
sim_now += std::chrono::milliseconds(1500);
eng->execute("print(time::now(), ' ', time::utc_now().to_string());");
    output
    1.5 2023-11-14T22:13:21.500Z

    The engine reads its providers on a strict budget. Each time:: call reads the provider it needs once, and only when it is called; constructing a stopwatch or a date reads nothing. Outside those calls the engine reads the monotonic provider in exactly one place: at a host entry (an execute()/execute_file()/jaibite run, or a script function or coroutine the host invokes while no script is running), and only after a loaded program names time::execute_elapsed, whose answer is measured from that reading. Nested executes, includes and imports belong to the entry that runs them. A stateful provider (a replay feeding recorded readings) therefore sees the same sequence of reads on every run of the same program.

    The execution budget and the import check window run on the real steady clock whatever the source, so a virtual clock can neither stall nor trip them. The engine keeps its own sample of that clock, read at each host entry (the reading the budget deadline starts from, and time::execute_elapsed too while the source is the system clock) and at the budget check's periodic samples. While the monotonic provider is the system one, a time:: read and a sleep's wake refresh the sample as well; a host provider never does.

    time::engine_elapsed() counts from the system clock's reading when the engine was constructed; on a host monotonic provider it is that provider's reading, so the host decides where zero is. eng->time_source({}, {}, {}) restores the system clocks. The host reads the same clock scripts do through eng->monotonic_now(), wall_now(), engine_elapsed(), execute_elapsed() and sleep_for(duration). A parallel body cannot call time:: at all (the clock would make it differ from its serial run), so providers are only ever called on the engine's thread.

    Practical notes​

    • Reuse engines. Engine creation plus first-execute lazy init costs on the order of a hundred warm script executions, so an engine-per-evaluation architecture pays mostly overhead. Costs are quantified in Performance.
    • execute() re-parses only novel strings. A 64-entry LRU source cache makes repeated execute(same_string) skip the parse (and on the VM, the compile). For hot scripts use a jaibite (see the jaibite chapter).
    • eng->set_output_stream(stream) redirects print(); pass nullptr to restore std::cout.
    • Include paths for script include/import: eng->add_include_path(dir).
    • Checking is strict by default. Porting a loosely typed codebase? eng->static_checking(jai::check_mode::warn) collects diagnostics instead of gating, for the whole engine; [[warn_mode]] does the same for one file, block, or statement; extern declares the names you inject at run time. Full story in Static Checking.
