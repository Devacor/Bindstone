Embedding Quickstart​

JaiScript's whole integration pitch fits in two lines — it compiles into your project as a static lib plus headers, and an engine is just an object:

C++
auto e = jai::engine::make();
e->execute("print(\"hello\");");

There is no global interpreter state anywhere: every script_value carries its engine, so two engines are fully isolated (separate globals, separate classes, separate budgets) and two engines on two threads need no locks. engine::make() always returns a std::shared_ptr<engine> — the private constructor makes it impossible to create one any other way (include/jaiscript/core/engine.hpp, engine::make).

Execute and read results: as<T>​

execute() returns a jai::script_value; convert it with as<T>() or the direct accessors as_int(), as_float(), as_string(), as_bool().

C++
// hosts/quickstart.cpp — compiled and run against the real lib
auto eng = jai::engine::make();               // always a shared_ptr<engine>
jai::stdlib::register_all(eng);               // print, to_string, to_json, math, ...

jai::script_value r = eng->execute("2 + 2");
r.as<int>();                                        // 4
eng->execute("6 * 7").as_int();                     // 42
eng->execute("\"jai\" + \"script\"").as<std::string>();  // "jaiscript"
eng->execute("1.5 * 2").as<double>();               // 3.0
eng->execute("3 > 2").as<bool>();                   // true

Verified output:

as<int>: 4
as_int(): 42
as<std::string>: jaiscript
as<double>: 3
as<bool>: 1

Note the stdlib is opt-in: a bare engine has no print, no to_string, nothing — call jai::stdlib::register_all(eng) to get the standard library. That opt-in is part of the sandbox story (see Safety Rails).

Registering C++ functions​

C++
// Typed: signature drives conversion and overload resolution
eng->add_function("square", [](jai::script_int n) { return n * n; });
eng->execute("square(12)").as_int();      // 144

// Variadic: you receive the raw argument vector
eng->add_variadic_function("sum_all", [&eng](const std::vector<jai::script_value>& args) {
    jai::script_int total = 0;
    for (auto& a : args) total += a.as_int();
    return jai::script_value(total, eng.get());
});
eng->execute("sum_all(1, 2, 3, 4)").as_int();   // 10

Registering the same name twice with different signatures creates an overload set resolved by argument types at the call site (engine::add_function auto-converts to an overloaded registration; pinned by overload_registration_tests.cpp). Use add_variadic_function for print-shaped functions and optional parameters.

Every script_value you construct yourself needs the engine pointer: jai::script_value(3.14159, eng.get()), or use the convenience factories eng->make_value(v) / eng->make_null() / eng->make_array() / eng->make_map().

Globals: copies vs live bindings​

C++
eng->add_global("PI", jai::script_value(3.14159, eng.get()));   // copied in

int hp = 100;
eng->add_global_ref("hp", hp);      // LIVE binding (cpp_bound) — no copy
eng->execute("hp = hp - 25;");      // hp is now 75 in C++
hp = 1;                              // and C++ writes are visible to the script
eng->execute("hp").as_int();        // 1

Verified output (hosts/quickstart.cpp):

hp after script damage: 75
script sees: 1

add_global_ref on a primitive (int8..64, unsigned variants, float, double, bool, char, std::string) creates a cpp_bound value: a typed pointer box that reads the live C++ variable and writes through to it. For non-primitive types it falls back to a non-owning aliasing shared_ptr — the caller must guarantee the object outlives the engine (documented in the header, engine.hpp add_global_ref).

What write-through covers​

Pinned exhaustively in source/tests/semantics/test_cpp_bound.cpp (both backends):

  • Name-level assignment and compound assignment write through: hp = hp + 50;, hp += 7;, ++hp, hp-- all mutate the C++ variable, at every width (t2_compound_writethrough_matrix covers int8/uint8/int16/int32/uint32/int64/uint64, float/double, and std::string +=).
  • Reads are always live: change the C++ variable between executes and the script sees the new value (cpp_changes_visible_in_script).
  • Mixed conversions keep the binding: boundInt += 2.5 converts (truncates) and still writes through (t2_compound_writethrough_matrix, "section 12.3").
  • A bound char is a width-1 bound int — it reads as its code point (pin_bound_char_read_write).

Where the binding deliberately drops (detach rules)​

  • clone() of a bound primitive detaches — it snapshots the value (pin_copy_alias_clone_detach). A plain copy of the script_value stays bound.
  • Every store detaches (all-detach ruling, 2026-07): storing a bound value into an array element, map slot, or object member — by literal construction ([hp], {"k": hp}), assignment, push, or an implicit-this member store — snapshots the value at store time. Write-through belongs to the registered name (and references/captures/by-ref params bound to it), never to stored copies (pin_element_compound_detach_and_replace, pin_ref_compound_on_stored_bound_never_reaches_cpp).
  • Assigning a bound value into an object member snapshots at store time (pin_member_compound_detach_and_replace, pin_implicit_this_member_store_detaches).
  • Plain = through a script reference (auto& r = hp; r = r + 4;) stores a detached result into the slot and drops the binding; compound assigns through refs (r += 5) DO write through (t2_writethrough_through_refs).

The exact-width as<T&> aliasing rules​

A non-const as<T&> on a bound value gives you a live reference into the C++ variable — zero-copy, reads and writes are real — but only when the binding's width and signedness exactly match the script-side type:

as<T&> requestaliases live when the bound C++ type is
as<jai::script_int&>exactly int64_t (or script_int)
as<jai::script_float&>exactly double
as<std::string&>std::string
as<jai::script_bool&>bool

Anything else — an int32_t behind as<script_int&>, a float behind as<script_float&> — throws a **catchable jai::runtime_error**, never std::bad_variant_access, and never silently reads the wrong bytes (the D12/S9 ruling, pinned by test_cpp_bound.cpp::t2_byref_cpp_extraction).

C++
// hosts/bound_ref.cpp — verified
jai::script_int gold = 10;
eng->add_global_ref("gold", gold);
auto v = eng->execute("gold");            // a bound alias, not a snapshot
v.as<jai::script_int&>() += 5;            // gold is now 15 in C++

int32_t narrow = 5;
eng->add_global_ref("narrow", narrow);
eng->execute("narrow").as<jai::script_int&>();   // throws jai::runtime_error
// "cannot bind a non-const script reference to a C++-bound variable of a different width"
eng->execute("narrow += 7;");             // by NAME any width works (decoded reads/writes)

Verified output:

gold after as<script_int&> += 5: 15
title: abc!
clone stays 15, live is 999
int32 as<script_int&>: cannot bind a non-const script reference to a C++-bound variable of a different width
narrow after script += 7: 12
gold after bump(gold): 1004
plain var after bump: 3

The same rules apply to **non-const T& parameters** of add_function bindings: a bound argument of exactly-matching width aliases the live variable (the callee's writes land in C++), while a plain script variable passed to the same T& parameter keeps copy isolation — the callee gets a private copy and the caller never sees its writes (the aliasing delta is confined to cpp-bound arguments; pinned by t2_byref_cpp_extraction, "plain script_int& writes never reach the caller").

Error surfaces​

C++
// hosts/errors.cpp — verified
eng->execute("undefined_thing + 1");   // throws jai::runtime_error:
                                        //   "Undefined variable 'undefined_thing': Undefined variable"
eng->execute("throw \"from script\";"); // uncaught script throw -> jai::runtime_error("from script")
eng->execute("var x = ;");              // throws parse error:
                                        //   "Parse error: <script>:1:10: Expected expression"
eng->execute("40 + 2").as_int();        // engine survives all of the above: 42

All exceptions derive from std::exception; eng->format_stack_trace() / eng->last_stack_trace() give the script stack of the most recent failure — verified for a throw two calls deep:

  at inner (<script>:1)
  at outer (<script>:2)
  at <script> (<script>:3)

errors that surface where C++ cannot throw (converted callbacks, signal receivers), install a sink with eng->set_script_error_handler(...) — the default sink is std::cerr (engine.hpp, set_script_error_handler).

Note for tests: some recoverable parse errors make the parser synchronize and return null instead of throwing (documented in Source/JaiScript/CLAUDE.md; the deeply-nested input tests assert "execute returns and the engine stays usable" rather than check_throws).

Practical notes​

  • Reuse engines. Engine creation plus first-execute lazy init is ~90 µs; a warm repeated script is ~0.4–1 µs (docs/execution_mode_metrics.md). An engine-per-evaluation architecture pays 10–40x the script cost in overhead.
  • execute() re-parses only novel strings — a 64-entry LRU source cache makes repeated execute(same_string) skip the parse (and on the VM, the compile). For hot scripts use a jaibite (see the jaibite chapter).
  • eng->set_output_stream(stream) redirects print(); pass nullptr to restore std::cout.
  • Include paths for script include/import: eng->add_include_path(dir).
