dynamic_binder: Binding C++ Classes​

jai::dynamic_binder<T> (include/jaiscript/core/dynamic_binder.hpp) is the fluent builder that registers a C++ class with an engine. One chain covers constructors, methods, properties, operators, statics, and inheritance:

C++
// hosts/binder.cpp — compiled and run against the real lib
jai::dynamic_binder<Vec2>(*eng, "Vec2")
    .constructor<>()
    .constructor<double, double>()            // overloaded ctors
    .method("length", &Vec2::length)
    .method("scale", &Vec2::scale)            // Vec2& scale(double) -> chainable
    .method("translate", &Vec2::translate)
    .method("+", &Vec2::operator+)            // operator overloading by name
    .method("==", &Vec2::operator==)
    .property("x", &Vec2::x)
    .property("y", &Vec2::y)
    .build();
jaiscript
var v = Vec2(3.0, 4.0);
v.length();                                   // 5
var a = Vec2(1.0, 2.0) + Vec2(3.0, 4.0);      // operator+ dispatches to C++
var c = Vec2(1.0, 1.0);
c.scale(3.0).translate(1.0, 0.0).x;           // 4 — chained through T& returns
v.x = 30.0;                                   // property writes hit the C++ member

Verified output (hosts/binder.cpp): 5, 10, 1 (==), 4 (chain), 30.2655 (post-write length()).

build() finalizes registration; the destructor calls it for you if you forget (the binder is also movable, non-copyable). Pinning tests: integration/class_builder_tests.cpp and integration/dynamic_binder_tests.hpp (suites "Class Builder" / dynamic binder).

Constructors​

  • .constructor<>() — default; if T has a T(engine*) constructor it is preferred automatically (has_engine_constructor concept).
  • .constructor<Args...>() — typed; registered as an overload set with full C++ parameter signatures, so Vec2(1, 2) vs Vec2() resolve by arity and type.
  • Construction from script is just a call: Vec2(3.0, 4.0). The object is created with std::make_shared<T> and stored inside a class_instance wrapper.
  • Registered classes also participate in conversion construction: a script function declared function f(Vec2 v) called with arguments a 1-arg ctor accepts will convert (see language/constructor_conversion_tests.cpp).

Methods​

Three shapes, all .method(name, ...):

C++
.method("length", &Vec2::length)                    // member fn ptr (const or not)
.method("setText", [](Button& self, const std::string& t) { self.setText(t); })
                                                     // lambda; first param T& or const T& = self
.method("version", []() { return 3; })              // lambda without self
.static_method("origin", []() { return Vec2(); })   // Class::origin() / Vec2::origin()

Same-arity overloads of one method name resolve by C++ parameter signature — each registration carries its param_type_info vector so set(float, float) vs set(int, int) pick correctly instead of last-registration-wins (comment + machinery in dynamic_binder.hpp::method; overload scoring shared with free functions via engine::select_cpp_overload).

Passing a member data pointer to .method() is a compile error with a message telling you to use .property() (static_assert in the lambda overload).

Properties​

C++
.property("x", &Vec2::x)                       // member pointer: read/write
.property("hp", &Player::getHp, &Player::setHp)  // getter/setter pair (lambdas or member fns)
.static_property("count", &Player::count)      // class-level
  • Script access is natural: v.x, v.x = 30.0. Setters are only generated for copy-assignable member types.
  • A std::vector<E> member is wrapped in a zero-copy bound_cpp_vector<E> with array-like methods (size/push/pop/at/[]), auto-registered on first use.
  • Members whose type is a registered class bind by reference (cpp_bound) so mutation and signal connection act on the live member, not a copy; unregistered copyable types copy (comment in property_impl).
  • Registration-order validation: a property whose type is an unregistered class throws at registration time with a fix-it message. Opt out for circular dependencies with jai::skip_type_check: .property("child", &Parent::child, jai::skip_type_check).

Operator overloading​

Operators are methods named by their token: + - * / % == != < <= > >= <=>, plus []. Register a real C++ operator or a lambda:

C++
.method("+", &Point::operator+)
.method("==", [](const Point& a, const Point& b) { return a.x == b.x && a.y == b.y; })

Registering != is optional when == exists — script != falls back to negated == (pinned by dynamic_binder_tests.hpp::equality_operator, comparison_operators, arithmetic_operators). Free-function operators between primitives can also be registered on the engine (add_function("+", ...)); the engine detects numeric-operator overrides and disables its fast paths accordingly (engine.hpp::isNumericOperator).

Script classes overload operators the same way from the other side — bool operator<(Money o) { ... } / function operator+(Money o) { ... } — so a type can start in script and graduate to C++ without call sites changing. Runnable demo (verified on both backends): engine/snippets/script_operator_overloading.jai; note the class-typed-return parse quirk recorded in engine/INTENT_QUESTIONS.md #2 (use the function operator+ form when an operator returns the class itself).

Chaining T& returns​

A method returning T& into its receiver (the scale().translate() idiom) is safe across temporaries: the returned cpp_bound receiver is kept alive by the object_holder::keep_alive anchor, so Vec2(1,1).scale(3).translate(1,0).x never dangles. Pinned by dynamic_binder_tests.hpp::method_chaining and value_semantics_tests.hpp::method_chaining_no_copy; the June-review dangling-temporary fix is the reason the anchor exists (do not remove it — noted in Source/JaiScript/CLAUDE.md).

Inheritance and upcasting​

C++
jai::dynamic_binder<Animal>(*eng, "Animal")
    .constructor<>()
    .method("speak", &Animal::speak)
    .property("name", &Animal::name)
    .build();

jai::dynamic_binder<Dog>(*eng, "Dog")
    .constructor<>()
    .base_class<Animal>()          // appends; chain for multiple inheritance
    .method("fetch", &Dog::fetch)
    .build();
  • base_class<Base>() is static_assert-guarded (is_base_of) and rejects diamond inheritance at registration with a thrown error.
  • Derived instances inherit base methods and properties: d.speak(), d.name work, and virtual dispatch is preserved (verified: Dog().speak() returns the Dog override).
  • **Automatic upcast on shared_ptr<Base> parameters**: a C++ function or method taking std::shared_ptr<Animal> accepts a script-side Dog (verified in hosts/binder.cpp: speak_of(pet) → "REX says woof"). base_class also records the serialization assignability edge so polymorphic loads type-check.
  • Script classes can extend C++ classes: class Wrapper : ReloadCppBase { ... } with super(...) calling the bound constructor (pinned by hot_reload_correctness_tests.cpp::cpp_object_survives_field_changing_reload).

shared_ptr semantics​

Objects are reference types at the C++ boundary. eng->make_object(shared_ptr) wraps your pointer — no copy, shared identity:

C++
auto pet = std::make_shared<Dog>();
eng->add_global("pet", eng->make_object(pet));
eng->execute("pet.name = \"REX\";");
// pet->name == "REX", pet.use_count() == 2   (verified)

eng->make_object<T>(args...) constructs in place. add_global_ref on a class type wraps a non-owning aliasing pointer — you must guarantee lifetime. Passing shared_ptr<T> through as<std::shared_ptr<T>>() round-trips the same control block (semantics/weak_ptr_tests.cpp covers the weak side).

auto_bind and helpers​

.auto_bind(mode) auto-detects and registers (bind_mode::all | properties | hierarchy):

  • base classes from a T::_jai_base_types tuple typedef,
  • JAI_PROPERTY-declared properties when T is a property_owner (observable ones get wrapper types with on_change),
  • common methods by concept: to_string(), size(), empty(), ==/!= from operator==,
  • a static T::jai_auto_bind(dynamic_binder<T>&) hook so classes can register private members themselves.

Other verbs worth knowing:

  • .version(n) + .post_load_hook([](T& self, int version){...}) — serialization versioning/migration (see the Serialization chapter).
  • .deserialization_factory(...) — construct non-default-constructible types on load (archive-only, context-only, or context+archive signatures, auto-detected).
  • .transparent_wrapper(unwrap) — operations not found on the wrapper retry on the unwrapped value (player.score + 5 where score is observable_property<int>).
  • Template types: a name like "Point<int>" auto-registers the base template name with the parser (integration/template_binder_tests.cpp).

Threading note (what exists vs planned)​

What exists today: engine-level isolation. No statics anywhere means two engines on two threads are safe with no locks — but one engine (and the objects registered into it) must be used from one thread at a time. A .thread_shareable() binder flag for sharing const assets across engine isolates appears in docs/parallel_design.md and is explicitly marked "new — does not exist" — it is a design proposal, not API. Do not look for it in the header.
