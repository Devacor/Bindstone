dynamic_binder: Binding C++ Classes​

One declaration, three superpowers. Declare a field once with JAI_PROPERTY and it is simultaneously reflected (C++ code can enumerate and edit it by name), script-visible (obj.field just works), and serialized (JSON and binary, from the same declaration — including polymorphic pointers and signal connections). This chapter walks one game class through all three, then documents the fluent binder chain that makes it go. Every C++ signature below is taken from include/jaiscript/core/dynamic_binder.hpp and friends; every snippet was compiled against the real library and run on both backends, with byte-identical output.

Three systems that drift​

Every engine eventually grows the same three subsystems, usually years apart, usually by different people:

  • Reflection — an editor or debug inspector needs to enumerate an object's fields by name.
  • Script binding — designers need tower.level to work from a script.
  • Serialization — save files need to write those same fields out and read them back.

Three systems, three registration sites, one class — and every new field is a three-stop tour. Miss a stop and you get the classic bugs: the field that saves but doesn't show in the editor, the script-visible field that silently never persists, the renamed member that still loads under its old name in one system and not the other. The systems don't fail loudly; they drift.

JaiScript's answer is to make the declaration itself the registration. A field declared through JAI_PROPERTY lives in a per-instance property_manager and a per-type schema; reflection walks the manager, the binder reads the schema, and the archives serialize the manager. There is nothing to keep in sync because there is only one thing.

The declaration​

A spawner building for a tower-defense game: three plain properties, one observable property, one signal, and two ordinary methods. This is the entire integration surface — everything in the rest of this chapter falls out of these ~30 lines:

C++
#include <jaiscript/core/registrar.hpp>
#include <jaiscript/properties/macros.hpp>
#include <jaiscript/properties/property_serialization.hpp>
#include <jaiscript/signals/signal_property.hpp>

class Spawner : public jai::property_owner<Spawner> {
public:
    JAI_PROPERTY((std::string), id, "north-gate");
    JAI_PROPERTY((int64_t), level, 1);
    JAI_PROPERTY((double), interval, 2.5);
    JAI_OBSERVABLE_PROPERTY((int64_t), threat, 0);     // emits on_change(old, new)
    JAI_SIGNAL_PROPERTY(void(int64_t), onWave);        // script-connectable, serializable

    void spawn_wave() { total_waves_ += 1; onWaveSignal(total_waves_); }
    int64_t total_waves() const { return total_waves_; }

private:
    int64_t total_waves_ = 0;   // not a property: private, unreflected, unsaved
};

static jai::registrar<Spawner, void> _regSpawner("Spawner",
    [](jai::dynamic_binder<Spawner>& b) {
        b.method("spawn_wave", &Spawner::spawn_wave);
        b.method("total_waves", &Spawner::total_waves);
    });

Reading it back:

  • property_owner<Spawner> gives the class a property_mgr and registers its serialization identity ($type name, polymorphic load factory) at program start — no separate serialization registration exists to forget.
  • JAI_PROPERTY((type), name, default) declares a jai::property<T> member. The type goes in parentheses so templates with commas survive the macro. The member behaves like a T in C++ (level += 1, comparisons, streaming all forward), and it self-registers into the manager and the type schema.
  • JAI_SIGNAL_PROPERTY(signature, name) expands to the engine's established pair — a private signal_emitter you fire (onWaveSignal(n)) and a public jai::signal view scripts and other systems connect to — plus a hidden property that rides save/load. Declaring it is also the entire script registration: auto_bind surfaces the signal as a connectable member (how, below).
  • jai::registrar is a self-registering static: any binary that links this file knows how to bind Spawner into any engine. The configure lambda only names what the macros can't know — the methods. Everything JAI_PROPERTY and JAI_SIGNAL_PROPERTY declared is bound automatically (registrar calls auto_bind() for you).

Host setup is three lines; bind_registrar replays every registrar in the binary into the engine you hand it:

C++
auto eng = jai::engine::make();
jai::stdlib::register_all(*eng);   // formatted print, containers, math, json
jai::bind_registrar(*eng);         // every jai::registrar in the binary, one call

This is the production shape, not a docs idealization: Bindstone registers Building, Creature, Game and company exactly this way (with a MV::Services context argument — jai::registrar<Building, MV::Services> — so bindings can reach engine services), and MutedVision's Clickable component declares six JAI_SIGNAL_PROPERTY members (onPress, onAccept, onDrag, …) whose script-connected handlers survive scene save/load.

Scripted​

Superpower one. No glue was written for id, level, interval, or onWave, yet property access, method calls, and signal connection all read like the class was written in script:

jaiscript
auto s = Spawner();
s.level = 3;
s.onWave.connect("hud", [=](int wave) -> void {
    print("wave {} incoming", wave);
});
s.spawn_wave();
s.spawn_wave();
print("{} at level {}: {} waves so far", s.id, s.level, s.total_waves());
output
wave 1 incoming
wave 2 incoming
north-gate at level 3: 2 waves so far

The constructor came free too: build() auto-registers a default constructor for any default-constructible, non-abstract type (and prefers a T(engine*) constructor when one exists). Signal connections take a name ("hud") — named connections are owned by the signal, so they live as long as the object and can be replaced or removed by name (disconnect("hud")).

Live objects, both directions​

Objects are reference types at the boundary. make_object(shared_ptr) wraps your pointer — no copy, shared identity — so script writes land in the C++ member and C++ emits reach script receivers:

C++
auto gate = std::make_shared<Spawner>();
eng->add_global("gate", eng->make_object(gate));
eng->execute("gate.id = \"east-gate\"; gate.level = 7;");
// gate->id.get() == "east-gate", gate->level.get() == 7   (verified)

eng->execute(R"JAI(
    gate.onWave.connect("hud", [=](int wave) -> void {
        print("gate wave {}", wave);
    });
)JAI");
gate->spawn_wave();   // C++ emit -> the script receiver runs
output
gate wave 1

The observable property completes the loop in the other direction — script observes, C++ mutates, and the change notification crosses the boundary. Assignments from either side fire it; unchanged writes don't:

jaiscript
gate.threat.on_change([=](int old_value, int new_value) -> void {
    print("threat {} -> {}", old_value, new_value);
});
C++
gate->threat = 5;                                    // C++ write
eng->execute("gate.threat = gate.threat + 2;");      // script write; reads unwrap in expressions
output
threat 0 -> 5
threat 5 -> 7

Lifetime notes: eng->make_object<T>(args...) constructs in place; add_global_ref on a class instance wraps a non-owning alias (you guarantee the object outlives the engine). One engine serves one thread at a time — two engines on two threads need no locks, because nothing is global.

Reflected​

Superpower two. The same declaration is a runtime reflection surface — this is what editor inspectors and debug panels are built on. Walk every property by name, read typed values, and write through the property so observable change signals still fire:

C++
gate->visit_reflected_properties([](const std::string& name, jai::property_base* p) {
    std::cout << "prop: " << name << "\n";
});
if (auto* lvl = gate->property_value<int64_t>("level")) {
    std::cout << "level via reflection: " << *lvl << "\n";
}
gate->set_property_value<int64_t>("threat", int64_t{9});   // on_change fires
output
prop: id
prop: interval
prop: level
prop: onWave
prop: threat
level via reflection: 7
threat 7 -> 9

The walk is virtual: hold a base pointer to a derived object and you still see the full most-derived chain. Per-property metadata rides along — value_type_id() for the C++ type, allow_save() for serialization eligibility — and the static side is queryable without an instance via Spawner::schema() / Spawner::all_property_names().

Serialized​

Superpower three. No save/load methods were written. One call walks the same property manager the other two superpowers use — and notice what's inside the payload: the signal's named script receiver serialized with the object:

C++
eng->execute(R"JAI(
    gate.onWave.connect("logger", "print(\"wave logged\");");   // named script-text receiver
)JAI");
auto json = jai::to_json(*eng, gate);
output
{
  "_type_": "",
  "value0":
  {
    "$id": 1,
    "$val":
    {
      "id": "east-gate",
      "interval": 2.5,
      "level": 7,
      "onWave":
      {
        "parameter_names":
        [
        ],
        "observers":
        [
        ],
        "owned_observers":
        {
          "logger":
          {
            "parameter_names":
            [
            ],
            "script": "print(\"wave logged\");"
          }
        }
      },
      "threat": 9
    }
  }
}

Loading reconstructs the object and re-arms the receiver. Pass the engine as the load context so persisted script receivers attach to it and execute on the next emit:

C++
auto loaded = jai::from_json<std::shared_ptr<Spawner>>(*eng, json, *eng);
// loaded->id.get() == "east-gate", level 7, threat 9   (verified)
loaded->spawn_wave();   // the receiver came back from the save file
output
wave logged

Binary is the same declaration through a different archive — no second format to maintain, and this object's payload is 374 bytes instead of 492 characters of JSON:

C++
auto bytes  = jai::to_binary(*eng, gate);                                   // std::vector<uint8_t>
auto again  = jai::from_binary<std::shared_ptr<Spawner>>(*eng, bytes, *eng);
again->spawn_wave();   // "wave logged" — receivers persist in binary too   (verified)

Ship saves in binary, debug them in JSON, diff them in code review — one declaration serves all of it. The receiver rule is deliberate: named script-text receivers persist; function-object receivers (script lambdas and C++ callbacks) are runtime-only and are skipped, never errored on. Serialization depth — versioning, migration hooks, $ref aliasing, custom archives — lives in Serialization.

Hot reload with state intact​

Script classes can extend bound C++ classes — and because the C++ half of such an object is the same live object across reloads, iterating on the script half never resets engine state. Redefine the class with a new field mid-session:

jaiscript
class SmartSpawner : Spawner {
    int aggression = 1;
    SmartSpawner() : super() {}
}
auto smart = SmartSpawner();
smart.level = 5;
smart.aggression = 2;
smart.spawn_wave();

Later, same session — a fresh execute() redefines the class with a new field, while smart is alive:

jaiscript
class SmartSpawner : Spawner {
    int aggression = 1;
    int burst = 4;                  // new field takes its initializer
    SmartSpawner() : super() {}
}

print("reloaded: level={} aggression={} burst={} waves={}",
    smart.level, smart.aggression, smart.burst, smart.total_waves());
output
reloaded: level=5 aggression=2 burst=4 waves=1

Existing script fields kept their values (aggression=2), the new field took its initializer (burst=4), and the C++ base — its properties and its private total_waves_ counter — was neither destroyed nor rebuilt (waves=1). The migration rules, the migrate hook, and the it-always-succeeds contract are in Hot Reload.

The fluent chain, verb by verb​

Under the registrar sits jai::dynamic_binder<T> (include/jaiscript/core/dynamic_binder.hpp) — the fluent builder you can also drive directly for types that aren't property_owners. The classic value-type example:

C++
jai::dynamic_binder<Vec2>(*eng, "Vec2")
    .constructor<>()
    .constructor<double, double>()             // overloaded ctors resolve by arity + type
    .method("length", &Vec2::length)
    .method("scale", &Vec2::scale)             // Vec2& scale(double) -> chainable
    .method("translate", &Vec2::translate)
    .method("+", &Vec2::operator+)             // operators are methods named by token
    .method("==", &Vec2::operator==)
    .static_method("axes", []() { return 2; })
    .static_method("dot", [](const Vec2& a, const Vec2& b) { return a.x * b.x + a.y * b.y; })
    .property("x", &Vec2::x)
    .property("y", &Vec2::y)
    .build();
jaiscript
var v = Vec2(3.0, 4.0);
print("length {}", v.length());
var a = Vec2(1.0, 2.0) + Vec2(3.0, 4.0);
print("sum ({}, {})", a.x, a.y);
print("chain {}", Vec2(1.0, 1.0).scale(3.0).translate(1.0, 0.0).x);
v.x = 30.0;                                    // property writes hit the C++ member
print("after write {}", v.length());
print("eq {}", Vec2(1.0, 2.0) == Vec2(1.0, 2.0));
print("neq {}", Vec2(1.0, 2.0) != Vec2(9.0, 2.0));   // != falls back to negated ==
print("axes {}", Vec2::axes());
print("dot {}", Vec2::dot(Vec2(1.0, 2.0), Vec2(3.0, 4.0)));
output
length 5.000000
sum (4.000000, 6.000000)
chain 4.000000
after write 30.265492
eq true
neq true
axes 2
dot 11.000000

Two behaviors in that transcript deserve a sentence each. The chain Vec2(1,1).scale(3).translate(1,0).x runs entirely on C++ temporaries: a method returning T& into its receiver stays valid because the bound receiver is kept alive across the chain — the idiom is safe by construction, not by luck. And != worked without being registered: when only == exists, script != is its negation.

The verbs:

  • .constructor<Args...>() — typed constructor overload; script calls Vec2(3.0, 4.0) and overloads resolve by arity and C++ parameter types. .constructor<>() prefers a T(engine*) constructor when the type has one. If you register none, build() adds a default constructor for default-constructible types.
  • .method(name, &T::fn) — member function pointer, const or not.
  • .method(name, lambda) — a lambda whose first parameter is T& or const T& becomes a method (that parameter is self); without it, a method that ignores the instance. Same-arity overloads of one name resolve by C++ parameter signature — registering set(double, double) after set(int64_t, int64_t) adds an overload rather than clobbering it. Passing a member data pointer here is a compile error that tells you to use .property().
  • .method("+", ...) — operator overloading by token: + - * / % == != < <= > >= <=> and []. Script classes can overload operators from the other side, so a type can start in script and graduate to C++ without call sites changing.
  • .static_method(name, fn) — free function or stateless lambda, called as Vec2::axes(). Bound-class arguments work (Vec2::dot(a, b) above); returning a bound class from the lambda form doesn't compile — see the last section.
  • .property(name, &T::member) — read/write field access. Setters are only generated for copy-assignable member types. A std::vector<E> member binds as a zero-copy live view with array-like methods (size/push/pop/at/[]). Members whose type is a registered class bind by reference, so mutation acts on the live member. A plain jai::signal<Sig> or signal_emitter<Sig> member binds as a script connect surface with this same one line — see the signals section.
  • .property(name, getter, setter) — computed properties from lambdas or member function pairs; pass nullptr as the setter for read-only.
  • .property(name, &T::member, jai::skip_type_check) — a property whose type isn't registered yet throws at registration time with a fix-it message; this tag acknowledges a deliberate circular dependency and skips the check.
  • .static_property(name, &var) / .static_property(name, getter, setter) — class-level values.
  • .base_class<Base>() — inheritance edge: methods and properties of the base become callable on the derived, virtual dispatch preserved, and the polymorphic-load type check learns that a Base slot may hold this type. static_assert-guarded; diamond inheritance throws.
  • .version(n) + .post_load_hook(fn) — serialization version stamp and a post-load migration hook, [](T& self) or [](T& self, int version).
  • .deserialization_factory(fn) — construct non-default-constructible types on load; archive-only, context-only, and context+archive signatures are auto-detected.
  • .transparent_wrapper(unwrap) — operations not found on the wrapper retry on the unwrapped value. This is how gate.threat + 2 worked: the observable wrapper unwraps to its int for arithmetic while keeping .on_change on the wrapper.
  • .auto_bind(mode) — everything the declarations already know: property_owner schemas (JAI_PROPERTY values, JAI_OBSERVABLE_PROPERTY wrappers, JAI_SIGNAL_PROPERTY connect surfaces), base classes from the inheritance declaration, and common methods by concept (to_string(), size(), empty(), ==/!= from operator==). A static T::jai_auto_bind(dynamic_binder<T>&) hook lets a class bind its own private members. Modes: all, properties, hierarchy.
  • .bound_engine() — the engine this binder targets; configure lambdas use it for bind_signal_type and globals.
  • .build() — finalizes registration. The destructor calls it if you forget; the binder is movable, non-copyable.

Signals: one view, every signature​

Signal members reach script with no per-signature ceremony. A JAI_SIGNAL_PROPERTY on a property_owner is exposed by auto_bind; a plain jai::signal<Sig> or signal_emitter<Sig> member is exposed by one .property("name", &T::member) line. Either way, script sees the same three-verb surface:

jaiscript
s.onWave.connect("hud", [=](int wave) -> void { ... });   // named function receiver
s.onWave.connect("logger", "print(\"wave logged\");");     // named script-text receiver
s.onWave.connected("hud");                                 // true
s.onWave.disconnect("hud");

The machinery behind it is one class, not one per signature. Reading a signal member hands script an engine-wide Signal view over a type-erased operations table (signal_script_ops, include/jaiscript/signals/signal_view.hpp): three function pointers — connect, disconnect, connected — whose thunks instantiate at the binding site, where the emitter's concrete type is known. On the auto_bind path, JAI_SIGNAL_PROPERTY stamps its schema entry is_signal (properties/property_schema.hpp), and the binder turns that entry into a read-only property whose getter asks the live signal property for its erased table (property_base::signal_ops). That lookup is find_reflected_property — virtual, whole inheritance chain — so a signal declared on a base class connects through a derived registration in either registration order. That is MutedVision's everyday shape: Clickable declares onAccept, Button registers with base_class + auto_bind, and script connects on the button. Script-text receivers work through the same table — connecting text routes the binding engine into the emitter before the connect, so C++-side emits fire them regardless of how the object came to exist (constructed in script, made in C++, or loaded from a save).

A typed registration can sit on top of this: jai::bind_signal_type<Sig> registers a named class for one signature and takes precedence over the generic view at member reads. When to reach for it — named signal types, pre-registration, precedence — is covered in Signals & Observable Properties.

What the view doesn't do (and what to use instead):

  • It doesn't own the signal. A view is a member read of a live bound object — the same lifetime class as any C++-bound member reference. A view held past its owner dangles; keep the owner alive for as long as script holds the signal.
  • It doesn't set parameter_names. Script-text receivers connected through the view see whatever parameter names the emitter's owner set in C++ (none, by default). When a handler needs the emit arguments, connect a function receiver — its parameters bind positionally, no naming required.

That is the binder's half of the signal story. The user's half — the owner/view idiom for firing signals from C++, receiver lifetime and emit_while, the two receiver forms, and observable properties — is Signals & Observable Properties.

Inheritance and polymorphism​

Declare the C++ inheritance once — property_owner<Derived, Base> — and the same edge serves script dispatch, C++ upcasts, and polymorphic saves:

C++
class Pickup : public jai::property_owner<Pickup> {
public:
    JAI_PROPERTY((std::string), name, "pickup");
};

class HealthPickup : public jai::property_owner<HealthPickup, Pickup> {
public:
    JAI_PROPERTY((int64_t), healing, 25);
};

// Register the BASE first — a derived binder wires inheritance by looking its base up.
jai::dynamic_binder<Pickup>(*eng, "Pickup")
    .auto_bind()
    .method("kind", [](Pickup& p) { return std::string("pickup:") + p.name.get(); })
    .build();
jai::dynamic_binder<HealthPickup>(*eng, "HealthPickup")
    .auto_bind()                                   // picks up the Pickup base edge + healing
    .property("name",                              // re-expose the base property explicitly
        [](HealthPickup& s) { return s.name.get(); },
        [](HealthPickup& s, const std::string& v) { s.name = v; })
    .build();

Polymorphic serialization needs no extra registration at all — property_owner already recorded the $type identity and the derived→base edge. Save through the base pointer, load through the base pointer, get the derived object back:

C++
std::shared_ptr<Pickup> loot = std::make_shared<HealthPickup>();
loot->name = std::string("elixir");
std::static_pointer_cast<HealthPickup>(loot)->healing = 40;

auto lootJson = jai::to_json(*eng, loot);          // saved through the BASE pointer
auto back = jai::from_json<std::shared_ptr<Pickup>>(*eng, lootJson);
auto* hp = dynamic_cast<HealthPickup*>(back.get());   // != nullptr, healing == 40  (verified)
output
{
  "_type_": "",
  "value0":
  {
    "$id": 1,
    "$type": "HealthPickup",
    "$val":
    {
      "name": "elixir",
      "healing": 40
    }
  }
}

The $type discriminator picked the concrete factory on load — no switch statement, no factory map, no slicing. On the script side, the same edge gives upcasts and inherited dispatch: a C++ function taking shared_ptr<Pickup> accepts a script-made HealthPickup, and base methods are callable on derived instances:

C++
eng->add_function("describe", [](std::shared_ptr<Pickup> p) { return p->name.get(); });
jaiscript
var h = HealthPickup();
h.name = "elixir";
h.healing = 40;
print("upcast: {} heals {}", describe(h), h.healing);
print("inherited method: {}", h.kind());
output
upcast: elixir heals 40
inherited method: pickup:elixir

Two rules keep this deterministic. Register bases before derived types — the derived binder wires the script-side edge by looking up the base's registration, and a missing base means the edge quietly doesn't form. And re-expose inherited JAI_PROPERTY fields on the derived binder (the getter/setter pair above): each inheritance level owns its own property manager, and the automatic schema binding does not reliably reach across levels — see the next section. Methods inherit fine; it's specifically base-level properties that want the explicit line.

Script classes extending C++ classes (class SmartSpawner : Spawner, with super(...) calling the bound constructor) were demonstrated in the hot-reload section — that direction works with zero extra registration.

What this doesn't do (and what to use instead)​

  • Auto-binding covers primitive, string, and signal properties. JAI_PROPERTY fields of int-family, float/double, bool, and std::string become script-visible automatically, and JAI_SIGNAL_PROPERTY members surface as connectable signal views. Container- and class-typed properties still reflect and serialize from the one declaration, but script access needs an explicit .property()/.method() in the configure lambda — a member-pointer .property() on a std::vector gets you the zero-copy live view.
  • Inherited property auto-binding is unreliable — bind it explicitly. The schema-driven binder can generate a derived-level accessor for a base-level property that misses the base's property manager (each level owns its own), and whether you get the working base accessor or the dead derived one depends on registration history. The reliable spelling on both backends is the pattern from the previous section — a one-line getter/setter .property() on the derived binder. Signal properties are the exception: their lookup is virtual and whole-chain (find_reflected_property), so a base-declared JAI_SIGNAL_PROPERTY connects through a derived registration in either registration order.
  • Function-object signal receivers don't serialize. Lambdas connected from script and C++ callbacks fire live but are skipped on save, by design. For handlers that should be part of an object's persistent state, connect named script-text receivers (connect("logger", "print(\"...\");")) and pass the engine as load context (from_json(eng, json, eng)) so they re-arm.
  • static_method lambdas can't return a bound class. Returning Vec2 from a static_method lambda is a compile error in the return-conversion path. Return primitives or strings from static lambdas; for factories, register a constructor overload or an engine-level function instead.
  • property_owner types round-trip as shared_ptr, not by value. Their property managers hold pointers into the object, so the types are deliberately move-pinned — from_json<Spawner> by value won't compile. Use from_json<std::shared_ptr<Spawner>>, as every example here does.
  • Reading an observable property yields a wrapper, not the raw value. In expressions it unwraps transparently (gate.threat + 2 works), but printing it directly shows [object]. Put it in an expression or assign it to a typed local when you want the value itself.
  • No cross-thread object sharing. An engine (and the objects registered into it) belongs to one thread at a time. The zero-global-state design means the alternative is cheap: one engine per thread, values copy cleanly, and nothing needs a lock. There is no binder flag that makes a single bound object thread-shared.
  • Auto-named registrars can't name template instantiations. jai::registrar<Point<int>, Ctx> without an explicit name is a compile error pointing you at the named constructor — pass "Pointi" (or any script-legal name) yourself. Template-syntax names like "Point<int>" register the base template name with the parser automatically.
