Backends: Tree-Walking Interpreter vs Bytecode VM​

One parser, one AST, two interchangeable execution backends (include/jaiscript/core/execution_backend.hpp):

  • backend_type::interpreter — the tree-walking interpreter. The default.
  • backend_type::vm — the bytecode VM (include/jaiscript/vm/): compiles the AST to chunks, environment-backed frames, fused superinstructions, counted-loop opcodes, fiber-based coroutines.
C++
// hosts/backends.cpp — verified
auto vm = jai::engine::make();
vm->set_backend(jai::backend_type::vm);     // BEFORE the first execute
vm->execute(script).as_int();               // 5050 — same answer as the interpreter

set_backend must happen before the first execute​

Once any script has run, defined functions and classes have captured the executing backend, so switching is refused with a thrown jai::runtime_error:

set_backend after execute() is unsupported: defined functions and classes capture the executing backend

(verified in hosts/backends.cpp; enforcement in engine.cpp::set_backend, has_executed_ latch). There is also set_backend(std::unique_ptr<execution_backend>) for injecting a custom backend, and backend_type::auto_select is a legacy alias for interpreter (implicit switching was removed).

Backend construction is lazy — creating an engine or setting the type costs nothing until a script actually runs (engine.hpp::backend() accessor comment).

The parity contract​

The two backends are held to byte-for-byte behavioral parity, including error text. This is not aspirational; it is machinery:

  • The full Foundry suite runs against both (jaiscript_tests.exe and jaiscript_tests.exe --backend=vm); both must stay green on every commit. Verified on the documentation worktree (VM-perf @ 03eec00d, Debug config): 80 suites, 1,586 tests per backend — all green on the interpreter; on the VM three performance-tolerance tests flaked under concurrent build load and all three pass rerun in isolation (they assert wall-clock speedups/budgets, not semantics). The Release BENCHMARKS config adds performance suites on top of that count.
  • A differential fuzzer (source/tests/fuzz/, jaiscript_fuzz) generates random programs and reports any output/error divergence between the backends. A 10,000-seed campaign ran with zero crashes; every divergence class it found is fixed and pinned in language/review_regression_tests.cpp (the fuzz_* tests), with the triage ledger in source/tests/fuzz/known_divergences.md.
  • Many individual suites run their assertions in a both-backends matrix on top of the global flag (e.g. test_cpp_bound.cpp::t2_*, vm_backend_tests.cpp).

One known, deliberately-suppressed divergence remains open in the ledger (known_divergences.md, KD-CORO-RESUME-PAST-END): resuming a coroutine past its final yield when it has no return — the interpreter repeats the last yielded value, the VM yields null. It is triaged (the interpreter is judged wrong: a finished coroutine has no value) and sits in "in-flight coroutine final-return fix territory". Don't build on either behavior.

Script callables execute through execution_backend::execute_callable, and thunks capture engine* + payload — never a backend pointer — so values, signals and callbacks work identically under both backends.

Numbers: what the choice actually costs​

All figures from docs/execution_mode_metrics.md (measured 2026-07-04 on the VM-perf branch, Release BENCHMARKS, medians of interleaved samples; scripts: a 1-line predicate, a 6-line function script, a ~30-line class+loop script):

regimeinterpretervm
engine create + first trivial execute~90 µs~87 µs (identical)
cold one-shot, fresh engine (tiny script)36.9 µs34.8 µs (VM already ahead)
warm engine, novel string every time (tiny)7.1 µs8.4 µs (interp +18–20% ahead)
warm engine, repeated string (tiny)1.03 µs0.60 µs (VM 1.7–1.8x faster)
warm jaibite execute (tiny)0.85 µs0.38 µs
warm jaibite execute (6-line fn script)3.10 µs1.69 µs
~30-line class/loop script, warm251.6 µs241.4 µs (1.04x)
  • VM compilation costs about one third of parsing (tiny: parse 3.8 µs, compile ~1.5 µs; 30-line: parse 67.5 µs, compile ~21 µs) and is cached (in the source-cache entry or the jaibite), so it amortizes by the 3rd–4th execution in every re-execution regime.
  • The interpreter's only durable win is genuinely unique, never-repeated small strings on a warm engine — worth 1.3–5 µs per execution, gone entirely at ~30 lines.
  • Class-heavy scripts see only ~4% VM advantage warm: per-execute class redefinition/hot-reload machinery costs the same on both.

Recommendation​

From the same document (its standing recommendation, plus docs/why_jaiscript.md):

  • Use the VM as the default backend. It is at parity or ahead on cold one-shots, 1.7–1.8x ahead on warm small scripts, and cumulatively ahead by the 1st–4th execution everywhere scripts repeat — which is what game scripts do.
  • Keep the interpreter as the debug/oracle backend. Its value is non-cost: reference-semantics simplicity, debuggability (it is the planned future debugger backend), and being the second implementation that keeps the VM honest. It is also the marginal winner if your workload is truly unique-string one-offs.
  • Don't build a tiered/auto-promotion mode. The measured compile premium (1.5–21 µs, ~⅓ of a parse both modes already pay) doesn't justify promotion bookkeeping and a third semantic path; the 64-entry source LRU + jaibite already capture "hot script" with zero policy machinery.

Practical pattern: make the backend a config/CLI flag (the examples do exactly this — examples/roguelike/main.cpp --backend, examples/demoreel TAB-toggles per run) so any behavioral suspicion can be A/B'd against the other backend instantly.
