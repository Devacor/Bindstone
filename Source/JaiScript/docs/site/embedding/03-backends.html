    Backends: Interpreter vs VM​

    Every engine runs your script through one parser and one AST, then hands it to one of two interchangeable execution backends (include/jaiscript/core/execution_backend.hpp), a choice made once per engine, and A/B-able the moment behavior or speed raises an eyebrow:

    • backend_type::vm: the bytecode VM (include/jaiscript/vm/): compiles the AST to chunks, environment-backed frames, fused superinstructions, counted-loop opcodes, fiber-based coroutines. The default.
    • backend_type::interpreter: the tree-walking interpreter, the reference implementation the VM is checked against.
    C++
    std::string script = "int s = 0; for (int i = 1; i <= 100; ++i) { s += i; } s";
auto oracle = jai::engine::make();
oracle->set_backend(jai::backend_type::interpreter);   // BEFORE the first execute
oracle->execute(script).as_int();                       // 5050 — same answer as the VM

    set_backend must happen before the first execute​

    Once any script has run, defined functions and classes have captured the executing backend, so switching is refused with a thrown jai::runtime_error:

    set_backend after execute() is unsupported: defined functions and classes capture the executing backend

    backend_type::auto_select names the default and selects the VM. The engine never switches backends implicitly.

    From the command line, the backend is a flag. The standalone runner starts on the VM, as an engine does:

    --backend=vm|interp   execution backend (default vm; interp = tree-walking interpreter)
--check=strict|warn|off   static checker mode (default strict)
--budget=N            execution budget in seconds per execute (default 0 = unlimited)

    Static checking is strict in both places (see Static Checking) and the backend is the VM in both, so a script that behaves one way under jaiscript file.jai and another inside your host differs in what the host registers or sets; --backend=interp runs it on the interpreter to compare against the reference. The runner also lifts the engine's 5 second execution budget to unlimited; pass --budget=N to put one back.

    Backend construction is lazy. Creating an engine or setting the type costs nothing until a script actually runs.

    The parity contract​

    The two backends are held to byte-for-byte behavioral parity, including error text. This is not aspirational; it is machinery:

    • The full test suite (more than 3,000 tests) runs against both (jaiscript_tests and jaiscript_tests --backend=vm), and both must stay green on every commit.
    • A differential fuzzer (source/tests/fuzz/) generates random programs and fails on any output or error-text divergence between the backends; every divergence it has found is fixed and covered by a regression test.
    • Many individual suites additionally run their assertions in an explicit both-backends matrix on top of the global flag.

    The contract has exactly one documented, deliberate exception, with two faces: recursion depth. The call-depth caps differ: 256 active calls on the interpreter and 250,000 on the VM by default (engine::max_call_depth(backend, depth) sets either), and on the interpreter a native-stack headroom check can fire before its cap (about 150 to 200 levels on a 1 MB thread such as the standalone runner's). Recursion deeper than the interpreter allows still runs on the VM; past its cap each backend raises the same catchable text, Maximum recursion depth exceeded - possible infinite recursion, and the interpreter's stack guard raises Native stack exhausted before the call-depth cap: the host thread's stack bounds this recursion. And a bare self tail call (return f(args) outside any try) reuses its frame on the VM. Tail recursion runs to any depth there, while the interpreter keeps the depth cap for every shape (a runaway tail loop is stopped by the execution budget on the VM, exactly like while (true); see Safety Rails). Everything else, including error text, is byte-identical.

    Script callables execute through execution_backend::execute_callable, and thunks capture engine* + payload (never a backend pointer), so values, signals and callbacks work identically under both backends.

    What the choice actually costs​

    The shape of it: engine creation and cold one-shots are effectively identical on both backends. The moment a script repeats (a cached string, a jaibite, anything per-frame), the VM pulls decisively ahead, because its one-time compile is small (about a third of the parse both backends already pay) and cached, so it amortizes within the first few executions. The interpreter's only durable win is genuinely unique, never-repeated small strings on a warm engine, and even that vanishes as scripts grow. Class-heavy scripts run close to even warm: per-execute class redefinition/hot-reload machinery costs the same on both. The full regime-by-regime table (creation, cold and warm dispatch, jaibite rows, crossover points) is quantified in Performance.

    Recommendation​

    • Run the VM. It is the default: at parity or ahead on cold one-shots, well ahead on warm repeated scripts, and cumulatively ahead within the first few executions everywhere scripts repeat, which is what game scripts do.
    • Keep the interpreter as the oracle backend. Select it with set_backend(jai::backend_type::interpreter). Its value is not speed: reference-semantics simplicity, and being the second implementation that keeps the VM honest. It is also the marginal winner if your workload is truly unique-string one-offs.
    • There is deliberately no tiered/auto-promotion mode. The compile premium is a fraction of the parse both modes already pay, so promotion bookkeeping would buy nothing and cost a third semantic path; the 64-entry source LRU + jaibite already capture "hot script" with zero policy machinery.

    Practical pattern: make the backend a config/CLI flag (the examples do exactly this: examples/crawler/main.cpp --backend, examples/demoreel TAB-toggles per run) so any behavioral suspicion can be A/B'd against the other backend instantly.
