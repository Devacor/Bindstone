Backends: Tree-Walking Interpreter vs Bytecode VM​

Every engine runs your script through one parser and one AST, then hands it to one of two interchangeable execution backends (include/jaiscript/core/execution_backend.hpp) — a choice made once per engine, and A/B-able the moment behavior or speed raises an eyebrow:

  • backend_type::interpreter — the tree-walking interpreter. The default.
  • backend_type::vm — the bytecode VM (include/jaiscript/vm/): compiles the AST to chunks, environment-backed frames, fused superinstructions, counted-loop opcodes, fiber-based coroutines.
C++
// hosts/backends.cpp — verified
auto vm = jai::engine::make();
vm->set_backend(jai::backend_type::vm);     // BEFORE the first execute
vm->execute(script).as_int();               // 5050 — same answer as the interpreter

set_backend must happen before the first execute​

Once any script has run, defined functions and classes have captured the executing backend, so switching is refused with a thrown jai::runtime_error:

set_backend after execute() is unsupported: defined functions and classes capture the executing backend

There is also set_backend(std::unique_ptr<execution_backend>) for injecting a custom backend; backend_type::auto_select is a legacy alias for the interpreter — the engine never switches backends implicitly.

Backend construction is lazy — creating an engine or setting the type costs nothing until a script actually runs (engine.hpp::backend() accessor comment).

The parity contract​

The two backends are held to byte-for-byte behavioral parity, including error text. This is not aspirational; it is machinery:

  • The full Foundry suite — 2,000+ tests — runs against both (jaiscript_tests.exe and jaiscript_tests.exe --backend=vm), and both must stay green on every commit.
  • A differential fuzzer (source/tests/fuzz/) generates random programs and reports any output or error-text divergence between the backends. A 10,000-program campaign ran with zero crashes, and every divergence class it has ever found is fixed and pinned by a regression test.
  • Many individual suites additionally run their assertions in an explicit both-backends matrix on top of the global flag.

The contract has exactly one documented, deliberate exception: recursion deep enough to be pathological (but still legal) can trip the interpreter's environment guard slightly before the VM's in-loop frames would — both backends still raise the same catchable recursion error, just at marginally different depths. Everything else, including error text, is byte-identical.

Script callables execute through execution_backend::execute_callable, and thunks capture engine* + payload — never a backend pointer — so values, signals and callbacks work identically under both backends.

What the choice actually costs​

The shape of it: engine creation and cold one-shots are effectively identical on both backends. The moment a script repeats — a cached string, a jaibite, anything per-frame — the VM pulls decisively ahead, because its one-time compile is small (about a third of the parse both backends already pay) and cached, so it amortizes within the first few executions. The interpreter's only durable win is genuinely unique, never-repeated small strings on a warm engine, and even that vanishes as scripts grow. Class-heavy scripts run close to even warm: per-execute class redefinition/hot-reload machinery costs the same on both. The full regime-by-regime table — creation, cold and warm dispatch, jaibite rows, crossover points — is quantified in Performance.

Recommendation​

  • Use the VM as the default backend. It is at parity or ahead on cold one-shots, well ahead on warm repeated scripts, and cumulatively ahead within the first few executions everywhere scripts repeat — which is what game scripts do.
  • Keep the interpreter as the oracle backend. Its value is non-cost: reference-semantics simplicity, and being the second implementation that keeps the VM honest. It is also the marginal winner if your workload is truly unique-string one-offs.
  • There is deliberately no tiered/auto-promotion mode. The compile premium is a fraction of the parse both modes already pay, so promotion bookkeeping would buy nothing and cost a third semantic path; the 64-entry source LRU + jaibite already capture "hot script" with zero policy machinery.

Practical pattern: make the backend a config/CLI flag (the examples do exactly this — examples/crawler/main.cpp --backend, examples/demoreel TAB-toggles per run) so any behavioral suspicion can be A/B'd against the other backend instantly.
