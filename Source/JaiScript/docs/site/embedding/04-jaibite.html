jaibite: Parse Once, Run Many, Ship .jaibite​

A jai::jaibite (include/jaiscript/core/jaibite.hpp) is an engine-bound, pre-parsed script handle: engine->jaibite(source) lexes and parses once; every bite.execute() after that skips straight to execution. On the VM backend the bite also caches its compiled bytecode chunk (compiled_ slot), so re-execution is pure dispatch.

C++
// hosts/bite.cpp — compiled and run against the real lib
eng->add_function("host_bonus", [](jai::script_int base) -> jai::script_int { return base + 100; });
eng->execute("var acc = 0;");

jai::jaibite bite = eng->jaibite("acc = host_bonus(acc); acc");   // parse ONCE (throws parse_error here)
bite.execute();          // 100
bite.execute();          // 200 — engine state persists across runs
eng->execute(bite);      // 300 — equivalent engine-side form

Verified output: run1: 100, run2: 200, run3: 300.

Semantics are guaranteed identical to execute(string): both routes funnel through the same private execute_parsed() pipeline, "so the pre-parsed path can never drift semantically" (engine.hpp). Behavior across runs — state persistence, class redefinition, try/catch, coroutines — is pinned by semantics/engine_tests.hpp::jaibite_* (jaibite_state_persists_across_runs, jaibite_class_redefinition_across_runs, jaibite_coroutine_resume_across_runs, ...).

Rules:

  • Engine-bound. Never share a live jaibite across engines — interned symbol IDs are engine-specific. Moving a bite between engines goes through save/load, which relocates symbols (header comment, jaibite.hpp).
  • Parse errors throw at jaibite() creation (engine_tests.hpp::jaibite_parse_error_throws_at_creation); runtime errors throw at execute().
  • If the owning engine is destroyed, bite.execute() throws script_exception rather than crashing (jaibite_outlives_engine_safely).
  • bite.valid() — false for a default-constructed/empty bite.

When a jaibite pays​

From docs/execution_mode_metrics.md: creation = the parse (tiny script 3.8 µs, ~30-line script 67.5 µs, backend-identical); warm bite.execute() is 0.85 µs (interp) / 0.38 µs (VM) for a tiny script. The VM's one-time compile (~⅓ of parse) amortizes by the 3rd–4th execution. Anything you run per-frame or per-entity belongs in a bite. (The engine's 64-entry LRU source cache gives repeated execute(same_string) most of the same win without the handle; the bite adds determinism — no cache eviction — and save/load.)

Save / load: shipping .jaibite​

C++
std::vector<uint8_t> bytes = bite.save_bytes();   // or bite.save("level.jaibite")

auto other = jai::engine::make();                 // a DIFFERENT engine (other process, other run)
jai::stdlib::register_all(other);
other->add_function("host_bonus", ...);
auto loaded = other->jaibite_load_bytes(bytes);   // or other->jaibite_load(path)
loaded.execute();

Verified: a bite saved from one engine (107 bytes for the demo script) loads into a fresh engine and runs — using the loading engine's registrations (host_bonus returning +7 there produced 7).

What is serialized is the parsed AST, never the compiled chunk — a loaded bite recompiles lazily like a fresh one (jaibite.hpp::save comment; code-confirmed in docs/execution_mode_metrics.md, "parse vs compile attribution"). Loading re-interns every symbol and type_info into the loading engine, so engine-specific symbol IDs never leak across engines. save_bytes() exists specifically for host VFS/pack-file routing.

Failure modes: jaibite_load* throws jai::runtime_error on missing file, bad format, version mismatch, or corrupt data (engine.hpp doc comment; corrupt/truncated inputs covered by serialization/jaibite_serialization_tests.cpp).

The differential battery in jaibite_serialization_tests.cpp pins the strong guarantee: for every script shape (functions, defaults, ref params, classes + inheritance + statics, lambdas with captures, coroutines, maps/arrays, try/catch, uncaught-throw error text, registered C++ types), a fresh-parsed bite and a load(save(bite)) bite into a different engine must produce identical results and identical error text, twice each (the second loaded run exercises the lazily compiled cached VM chunk), on both backends.

The automatic disk cache​

Naming note (2026-07): the extension is .jaibite — the earlier short form .jaib was renamed; the file format and its JBIT magic are unchanged, and jai::k_jaibite_extension (jaibite.hpp) is the canonical constant. save()/jaibite_load() still take explicit paths; the extension is a convention there.

You usually don't need to ship bites by hand at all: every file-based load maintains the cache automatically (default ON). Whenever the engine loads a script file — execute_file, script-side include (all forms), script-side import — it keeps a sibling foo.jaibite next to foo.jai:

  • Fresh sibling (strictly newer by mtime and registration fingerprint matches): loaded instead of parsed — the parse is skipped entirely. A trusted checked-clean stamp also skips the static re-check, exactly like jaibite_load.
  • Anything else — edited source (source mtime ≥ sibling = stale), corrupt/truncated sibling, fingerprint mismatch — silently falls back to parsing the source and rewrites the sibling. An edited .jai always wins; hot reload is unaffected.
  • Write failures are silent and tolerated (read-only asset dirs, shipped games): the cache is an optimization, never an error. eng->jaibite_cache_write_failures() counts them for diagnostics.
  • String executes never touch disk; hosts that read files through their own VFS can route through eng->execute_file_source(resolvedPath, content) to keep the cache. Opt out per engine with eng->jaibite_cache(false) (pristine-directory requirements).

The cache is backend-agnostic (it stores the parsed AST): both backends skip the parse; the VM additionally reuses its lazily compiled chunk in-memory as always. Pinned by the jaibite_cache_* battery in language/include_import_tests.cpp — including the fresh-sibling-loads-while-source-is-unparseable proof, equal-mtime-is-stale, corrupt fallback + rewrite, fingerprint mismatch, and the unwritable-sibling tolerance, on both backends.

Registration fingerprint​

engine::registration_fingerprint() is an FNV-1a hash over the sorted registered overloaded-function / class / template-type names, plus (since 2026-07) every plain-global function registration — zero-arg add_function, add_variadic_function, single untyped bindings — with an arity-class marker. save_bytes() stamps it into the header; jaibite_load* compares it against the loading engine and sets bite.registration_mismatch() on difference. Version note: engines registering such plain functions produce a different fingerprint than pre-2026-07 builds, so their old .jaibite files report the advisory mismatch (loads never hard-fail).

Advisory only. A mismatched bite still loads and runs; errors surface at execute() only if the script actually touches the missing registration:

C++
auto bare = jai::engine::make();                  // no host_bonus registered
jai::stdlib::register_all(bare);
auto risky = bare->jaibite_load_bytes(bytes);
risky.registration_mismatch();                    // true   (verified)
risky.execute();                                  // throws "Undefined variable 'host_bonus'"

Caveat (verified empirically, see engine/INTENT_QUESTIONS.md): only functions that land in an overload set contribute to the fingerprint. A zero-parameter add_function lambda or an add_variadic_function registers as a plain global function and is invisible to it — an engine differing only in such functions reports registration_mismatch() == false. Typed functions with at least one parameter, classes and template types are always covered.

Checked-clean stamp (static checking integration)​

When static checking is active (see the Static Checking chapter), a bite created or executed under warn/strict carries its diagnostics:

  • bite.checked_clean() — checked, no error-severity diagnostics.
  • bite.check_diagnostics() — the check_report.
  • save() stamps a checked-clean bit beside the fingerprint (an existing header flags u32 — no format bump; old loaders ignore it).
  • On load the stamp is trusted only when the registration fingerprint matches the saving engine; otherwise the bite loads unchecked and is re-checked against the loading engine's surface on the strict/warn path (strict throws at load on errors).
  • A bite is checked once — registrations arriving later don't re-trigger; re-create the bite to re-check.

All pinned by semantics/static_check_tests.cpp::jaibite_save_load_stamp, jaibite_strict_gates_creation, jaibite_warn_carries_diagnostics, jaibite_execute_checks_lazily; load-side gate in engine.cpp::jaibite_load_bytes.
