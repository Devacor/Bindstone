jaibite: Parse Once, Run Many, Ship .jaibite​

A jai::jaibite (include/jaiscript/core/jaibite.hpp) is an engine-bound, pre-parsed script handle: engine->jaibite(source) lexes and parses once; every bite.execute() after that skips straight to execution. On the VM backend the bite also caches its compiled bytecode chunk, so re-execution is pure dispatch. It buys you two things: scripts you run repeatedly stop paying the parse, and shipped games boot from precompiled bites instead of source — usually without you managing a single file, because the engine maintains the disk cache for you (below).

C++
// hosts/bite.cpp — compiled and run against the real lib
eng->add_function("host_bonus", [](jai::script_int base) -> jai::script_int { return base + 100; });
eng->execute("var acc = 0;");

jai::jaibite bite = eng->jaibite("acc = host_bonus(acc); acc");   // parse ONCE (throws parse_error here)
bite.execute();          // 100
bite.execute();          // 200 — engine state persists across runs
eng->execute(bite);      // 300 — equivalent engine-side form

Verified output: run1: 100, run2: 200, run3: 300.

Semantics are guaranteed identical to execute(string): both routes funnel through the same private execution pipeline, so the pre-parsed path can never drift semantically. Everything that works across repeated execute() calls — state persistence, class redefinition, try/catch, coroutine handles — works identically across repeated bite.execute() runs, and is pinned by tests on both backends.

The rules:

  • The one rule: never share a live jaibite across engines. A bite carries interned symbol IDs that are specific to the engine that parsed it. To move a script between engines (or processes, or machines) go through save()/jaibite_load() — the save/load path relocates every symbol into the loading engine. Everything else about bites is convenience; this rule is the contract.
  • Parse errors throw at jaibite() creation; runtime errors throw at execute() — so a bite in hand is always syntactically valid.
  • If the owning engine has been destroyed, bite.execute() throws script_exception rather than crashing.
  • bite.valid() — false for a default-constructed/empty bite.

When a jaibite pays​

Creation costs the parse — once, and backend-identical. After that, a warm bite.execute() is the cheapest way the engine offers to run script, and the VM's one-time compile (a fraction of the parse) amortizes within the first few executions. Anything you run per-frame or per-entity belongs in a bite; the measured regime table is in Performance. (The engine's 64-entry LRU source cache gives repeated execute(same_string) most of the same win without the handle; the bite adds determinism — no cache eviction — and save/load.)

Instant boot: the automatic disk cache​

You usually don't need to ship bites by hand at all. Whenever the engine loads a script file — execute_file, script-side include (all forms), script-side import — it keeps a sibling foo.jaibite next to foo.jai (default ON), and next launch loads that instead of parsing. The parse simply leaves the boot path: a measured game file's load-and-run drops to well under half, the parse replaced by a small binary read (numbers in Performance). Across a game's whole script tree, that is the difference between a boot that parses and a boot that doesn't.

The cache is designed so you can forget it exists:

  • Fresh sibling (strictly newer than the source by mtime and the registration fingerprint matches): loaded instead of parsed — the parse is skipped entirely. A trusted checked-clean stamp also skips the static re-check, exactly like jaibite_load.
  • Anything else — edited source, corrupt/truncated sibling, fingerprint mismatch — silently falls back to parsing the source and rewrites the sibling. An edited .jai always wins; hot reload is unaffected.
  • Write failures are silent and tolerated (read-only asset dirs, shipped games): the cache is an optimization, never an error. eng->jaibite_cache_write_failures() counts them for diagnostics.
  • String executes never touch disk; hosts that read files through their own VFS can route through eng->execute_file_source(resolvedPath, content) to keep the cache. Opt out per engine with eng->jaibite_cache(false).

The cache stores the parsed AST, so it is backend-agnostic: both backends skip the parse, and the VM reuses its lazily compiled chunk in-memory as always. The whole matrix — a fresh sibling loading while the source is unparseable, equal-mtime staleness, corrupt fallback and rewrite, fingerprint mismatch, unwritable siblings — is pinned by tests on both backends.

Shipping .jaibite by hand​

When you want explicit control — pack files, downloadable content, a bake step — save and load bites yourself. The canonical extension is jai::k_jaibite_extension (.jaibite); save()/jaibite_load() take explicit paths, so the extension there is a convention.

C++
std::vector<uint8_t> bytes = bite.save_bytes();   // or bite.save("level.jaibite")

auto other = jai::engine::make();                 // a DIFFERENT engine (other process, other run)
jai::stdlib::register_all(other);
other->add_function("host_bonus", ...);
auto loaded = other->jaibite_load_bytes(bytes);   // or other->jaibite_load(path)
loaded.execute();

Verified: a bite saved from one engine (107 bytes for the demo script) loads into a fresh engine and runs — using the loading engine's registrations (a host_bonus returning +7 there produced 7).

What is serialized is the parsed AST, never the compiled chunk — a loaded bite recompiles lazily like a fresh one. Loading re-interns every symbol and type name into the loading engine, which is exactly why one .jaibite file serves any engine while live bites serve only their own. save_bytes() exists specifically for host VFS/pack-file routing. jaibite_load* throws jai::runtime_error on a missing file, bad format, version mismatch, or corrupt data.

The guarantee behind all of this is differential: for every script shape (functions, defaults, ref params, classes with inheritance and statics, lambdas with captures, coroutines, containers, try/catch, uncaught-throw error text, registered C++ types), a fresh-parsed bite and a load(save(bite)) bite in a different engine must produce identical results and identical error text, twice each, on both backends — a standing test battery, not a design intention.

Registration fingerprint​

A bite compiled against your engine's API surface may land in an engine with a different one. engine::registration_fingerprint() hashes the registered surface — overloaded functions, plain global function registrations (with an arity-class marker), classes, and template types. save_bytes() stamps it into the header; jaibite_load* compares it against the loading engine and sets bite.registration_mismatch() on difference.

Advisory only. A mismatched bite still loads and runs; errors surface at execute() only if the script actually touches the missing registration:

C++
auto bare = jai::engine::make();                  // no host_bonus registered
jai::stdlib::register_all(bare);
auto risky = bare->jaibite_load_bytes(bytes);
risky.registration_mismatch();                    // true   (verified)
risky.execute();                                  // throws "Undefined variable 'host_bonus'"

Checked-clean stamp (static checking integration)​

When static checking is active (see Static Checking), a bite created or executed under warn/strict carries its diagnostics:

  • bite.checked_clean() — checked, no error-severity diagnostics.
  • bite.check_diagnostics() — the check_report.
  • save() stamps a checked-clean bit beside the fingerprint, so a bake step's strict check travels with the file.
  • On load the stamp is trusted only when the registration fingerprint matches the saving engine; otherwise the bite loads unchecked and is re-checked against the loading engine's surface on the strict/warn path (strict throws at load on errors).
  • A bite is checked once — registrations arriving later don't re-trigger; re-create the bite to re-check.
