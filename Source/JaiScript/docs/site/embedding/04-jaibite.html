    jaibite: Parse Once, Ship Precompiled​

    A jai::jaibite (include/jaiscript/core/jaibite.hpp) is an engine-bound, pre-parsed script handle: engine->jaibite(source) lexes and parses once; every bite.execute() after that skips straight to execution. On the VM backend the bite also caches its compiled bytecode chunk, so re-execution is pure dispatch. It buys you two things: scripts you run repeatedly stop paying the parse, and shipped games boot from precompiled bites instead of source, usually without you managing a single file, because the engine maintains the disk cache for you (below).

    C++
    // compiled and run against the library
eng->add_function("host_bonus", [](jai::script_int base) -> jai::script_int { return base + 100; });
eng->execute("var acc = 0;");

jai::jaibite bite = eng->jaibite("acc = host_bonus(acc); acc");   // parse + check ONCE (both throw here)
bite.execute();          // 100
bite.execute();          // 200 — engine state persists across runs
eng->execute(bite);      // 300 — equivalent engine-side form

    Output: run1: 100, run2: 200, run3: 300.

    Semantics are guaranteed identical to execute(string): both routes funnel through the same private execution pipeline, so the pre-parsed path can never drift semantically. Everything that works across repeated execute() calls (state persistence, class redefinition, try/catch, coroutine handles) works identically across repeated bite.execute() runs. Both backends behave identically here; the test suite holds them to it.

    The rules:

    • The one rule: never share a live jaibite across engines. A bite carries interned symbol IDs that are specific to the engine that parsed it. To move a script between engines (or processes, or machines) go through save()/jaibite_load(). The save/load path relocates every symbol into the loading engine. Everything else about bites is convenience; this rule is the contract.
    • A bite in hand has already passed the front end. Parse errors throw at jaibite() creation, and so do static-check errors. Checking is strict by default, so jaibite() throws jai::static_check_error at creation exactly like execute() does (Static Checking). Runtime errors throw at execute().
    • If the owning engine has been destroyed, bite.execute() throws script_exception rather than crashing.
    • bite.valid(): false for a default-constructed/empty bite.

    When a jaibite pays​

    Creation costs the parse: once, and backend-identical. After that, a warm bite.execute() is the cheapest way the engine offers to run script, and the VM's one-time compile (a fraction of the parse) amortizes within the first few executions. Anything you run per-frame or per-entity belongs in a bite; the measured regime table is in Performance. (The engine's 64-entry LRU source cache gives repeated execute(same_string) most of the same win without the handle; the bite adds determinism, with no cache eviction, and save/load.)

    Instant boot: the automatic disk cache​

    You usually don't need to ship bites by hand at all. Whenever the engine loads a script file (execute_file, script-side include in all forms, script-side import), it keeps a sibling foo.jaibite next to foo.jai (default ON), and next launch loads that instead of parsing. The parse simply leaves the boot path: a measured game file's load-and-run drops to well under half, the parse replaced by a small binary read (numbers in Performance). Across a game's whole script tree, that is the difference between a boot that parses and a boot that doesn't.

    The cache is designed so you can forget it exists:

    • Matching sibling (its header records the exact source text, by size and hash, and the registration fingerprint matches): loaded instead of parsed, and the parse is skipped entirely. Mtimes never decide: a source copied into place with an older timestamp is judged by its bytes. A trusted checked-clean stamp also skips the static re-check, exactly like jaibite_load.
    • Anything else (other source text, corrupt/truncated sibling, fingerprint mismatch) silently falls back to parsing the source and rewrites the sibling. The .jai on disk always wins; hot reload is unaffected. The sibling is written to a temporary file and renamed into place, so another engine or process never reads part of one.
    • Write failures are silent and tolerated (read-only asset dirs, shipped games): the cache is an optimization, never an error. eng->jaibite_cache_write_failures() counts them for diagnostics.
    • String executes never touch disk; hosts that read files through their own VFS can route through eng->execute_file_source(resolvedPath, content) to keep the cache. Opt out per engine with eng->jaibite_cache(false). An engine whose filesystem privilege is disabled (eng->disable(jai::filesystem), Safety Rails) skips the cache entirely, and an explicit jaibite_load(path) or bite.save(path) throws a jai::runtime_error reading Insufficient privilege: filesystem.; the byte forms (save_bytes, jaibite_load_bytes) still work.

    The cache stores the parsed AST, so it is backend-agnostic: both backends skip the parse, and the VM reuses its lazily compiled chunk in-memory as always. The whole matrix (a matching sibling loading while the source is unparseable, older-mtime and same-mtime replacements, corrupt and truncated fallback and rewrite, fingerprint mismatch, unwritable siblings) is covered by the test suite.

    Shipping .jaibite by hand​

    When you want explicit control (pack files, downloadable content, a bake step), save and load bites yourself. The canonical extension is jai::k_jaibite_extension (.jaibite); save()/jaibite_load() take explicit paths, so the extension there is a convention.

    C++
    std::vector<uint8_t> bytes = bite.save_bytes();   // or bite.save("level.jaibite")

auto other = jai::engine::make();                 // a DIFFERENT engine (other process, other run)
jai::stdlib::register_all(other);
other->add_function("host_bonus", [](jai::script_int base) -> jai::script_int { return base + 7; });
other->execute("var acc = 0;");
auto loaded = other->jaibite_load_bytes(bytes);   // or other->jaibite_load(path)
loaded.execute();                                 // 7

    A bite saved from one engine (a hundred-odd bytes for the demo script) loads into a fresh engine and runs, using the loading engine's registrations and globals: the host_bonus registered there returns 7.

    What is serialized is the parsed AST, never the compiled chunk. A loaded bite recompiles lazily like a fresh one. Loading re-interns every symbol and type name into the loading engine, which is exactly why one .jaibite file serves any engine while live bites serve only their own. save_bytes() exists specifically for host VFS/pack-file routing. jaibite_load* throws jai::runtime_error on a missing file, bad format, version mismatch, or corrupt data (jaibite: failed to open file: level.jaibite, jaibite: truncated header, ...).

    The format is versioned, and the number moves whenever the parser gains a node, so a bite is readable only by builds that share its format version. An explicit jaibite_load* of a file from another version throws jaibite: unsupported format version M (expected N), where M is the file's version and N the build's, jai::detail::k_jaibite_version; a stale sibling in the automatic disk cache is simply reparsed and rewritten, silently. Practical rule: ship bites from the same build you ship the engine from, and never hand-carry a .jaibite across versions.

    The guarantee behind all of this is differential: for every script shape (functions, defaults, ref params, classes with inheritance and statics, lambdas with captures, coroutines, containers, try/catch, uncaught-throw error text, registered C++ types), a fresh-parsed bite and a load(save(bite)) bite in a different engine must produce identical results and identical error text, twice each, on both backends: a standing test battery, not a design intention.

    Registration fingerprint​

    A bite compiled against your engine's API surface may land in an engine with a different one. engine::registration_fingerprint() hashes the registered surface: overloaded functions, plain global function registrations (with an arity-class marker), classes, and template types. save_bytes() stamps it into the header; jaibite_load* compares it against the loading engine and sets bite.registration_mismatch() on difference.

    The flag itself is advisory; what a mismatch costs is a fresh check. The bite's checked-clean stamp is trusted only under a matching fingerprint (below), so under strict checking (the default) a mismatched bite is re-checked against the loading engine at load, and a name the loading engine does not have fails there, before anything runs. Under warn or off the bite loads and runs, and the error surfaces at execute() only if the script actually touches the missing registration:

    C++
    // compiled and run against the library
auto bare = jai::engine::make();                  // no host_bonus registered
jai::stdlib::register_all(bare);
bare->execute("var acc = 0;");
bare->jaibite_load_bytes(bytes);                  // strict: throws jai::static_check_error
// static check failed:
// <script>:1:7: error: use of undeclared identifier 'host_bonus'

bare->static_checking(jai::check_mode::warn);
auto risky = bare->jaibite_load_bytes(bytes);
risky.registration_mismatch();                    // true
risky.execute();                                  // throws "Undefined variable 'host_bonus'"

    Checked-clean stamp (static checking integration)​

    Checking is on by default, so this applies to every bite you make unless you opted down. Under strict, jaibite() throws jai::static_check_error at creation, the same gate execute() passes through. Under warn the report rides the bite instead (see Static Checking):

    • bite.checked_clean(): checked, no error-severity diagnostics.
    • bite.check_diagnostics(): the check_report.
    • save() stamps a checked-clean bit beside the fingerprint, so a bake step's strict check travels with the file.
    • On load the stamp is trusted only when the registration fingerprint matches the saving engine; otherwise the bite loads unchecked and is re-checked against the loading engine's surface on the strict/warn path (strict throws at load on errors).
    • A bite is checked once. Registrations arriving later don't re-trigger; re-create the bite to re-check. Parse-time type proofs (fast-path annotations the checker stamps on the AST, nothing you configure; see Static Checking, Proofs) are independent of the stamp: a loaded bite re-derives them, in every mode.
    • The stamp is per file, not per program. A leaf that checked clean inside one program (its names declared by a sibling unit) loads from its stamped sibling without a re-check when a different program reaches it, so a name that program never declares surfaces at run time as the ordinary Undefined variable, not at load. Edit the source or delete the sibling to force a fresh check.
