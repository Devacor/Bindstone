    Safety Rails​

    JaiScript's sandbox position (pillar 6 of docs/why_jaiscript.md in the repository): there is no sandbox API because safety is the default. A script can only touch what the host registered, and the language ships no built-in file, network, or system access (a bare engine's only voice is a basic print, and it can speak solely into the stream the host installed via set_output_stream: a log, a capture buffer, or a discarding sink). The registration surface is the allowlist. On top of that no-ambient-authority baseline sit four enforcement rails.

    1. Execution budget: terminal, uncatchable by script​

    C++
    eng->execution_budget(1.0 / 60);   // wall-clock seconds per execute()/resume()
eng->execution_budget();           // read back; 0 disables; DEFAULT: 1.0 second

    A script exceeding the budget raises an execution_budget_exceeded error that is terminal: every script catch is skipped: plain try/catch, nested catches, catches inside functions, lambdas, coroutines, and even the outer script's catch around a reentrant execute (host callback calling execute() mid-script). The failure always reaches the host; a script can never swallow its own timeout.

    C++
    // compiled and run against the library
eng->execution_budget(0.05);
eng->execute("var caught = 0; try { while (true) { } } catch (e) { caught = 1; } caught;");
// throws to C++: "Script execution budget exceeded - raise engine::execution_budget
//                 or break up the work: Script execution budget exceeded"
eng->execute("2 + 2").as_int();    // 4 — the engine survives; each execute gets a fresh deadline

    Why terminal: a catchable timeout is a denial-of-service kit. The differential fuzzer demonstrated a catch-and-retry loop that kept execute() from ever returning. The whole matrix (nested catches, catches inside functions, lambdas, and coroutines, reentrant execute boundaries, per-execute re-arming, the 1-second default) is covered by the test suite on both backends.

    Granularity: checked at loop back-edges and call entry, clock sampled every 1024 ticks, with no measurable hot-path cost, and straight-line C++ bindings are never interrupted mid-call (engine.hpp doc comment). Corollary: a single very slow host call can overshoot the deadline before the next check.

    2. Memory cap: deny-in-place, one catchable raise, then terminal​

    C++
    eng->memory_cap(256 * 1024);   // approximate bytes per top-level execute()/resume()
                                // 0 disables; DEFAULT: 0 (unlimited)
                                // 256 KB is small on purpose so the demo below trips it fast

    Accounting is a high-water mark charged at the heavy-value chokepoints: container growth (push/insert/repeat/concat), string concat, clone, environment growth. Frees are not credited back (v1 approximation, documented in engine.hpp). An allocation that would cross the cap is denied in place (the object never grows) and raises:

    • First raise per execute: an ordinary catchable script error, and the counter re-arms to zero so the script can free caches and continue working. This is the legit recovery path:
    jaiscript · under the 256 KB cap above
    var a = [];
try { while (true) { a.push("xxxxxxxxxx"); } }
catch (err) { a = []; }     // err == "Script memory cap exceeded (262144 bytes) -
                            //         raise engine::memory_cap or break up the work"

    The number in the text is the cap you set, in bytes.

    • Second raise in the same execute: terminal, exactly like a budget overrun. Every catch is skipped and execute() fails to the host: first raise caught by script, second raise thrown to C++.
    • Fresh execute = fresh allowance and raise count; reentrant executes share the outer call's allowance.

    The matrix (first-raise catchable, second-raise terminal, map-growth and environment-growth bombs, per-execute reset, zero-is-unlimited) is covered by the test suite, and the differential fuzz harness runs every generated program under a 64 MB cap.

    What the cap is not: an allocator hook. Frees aren't credited back, slot-stored locals aren't charged, and a single enormous operation can overshoot before the next check fires. It denies at the chokepoints it instruments. Treat it as a blast-radius limiter, not a byte-exact quota; if you need hard process-level limits, use OS job/cgroup machinery around the host.

    3. Checked integer overflow (compile-time policy)​

    Chosen at build time, applied via if constexpr so the losing policy costs zero at runtime (detail/integer_ops.hpp):

    • JAISCRIPT_CHECKED_OVERFLOW (the default: "safe by default"): overflowing + - *, unary -, and INT64_MIN / -1 raise a catchable runtime error.
    • JAISCRIPT_WRAP_ON_OVERFLOW: silent two's-complement wraparound (max speed).

    Either way arithmetic is never undefined behavior (computed in unsigned). The policy is applied consistently everywhere: interpreter fast paths, VM opcodes, counted-loop updates, ++/--, and even the parser's constant folder (which declines to fold rather than wrap; the differential fuzzer hunted down the bypasses). Hosts can introspect the build's policy:

    C++
    eng->throw_on_overflow();     // true in the default build
    jaiscript
    var x = 9223372036854775807;
try { x = x + 1; } catch (e) { print(e); }
print(x);                          // untouched: the overflowing store never happened
    output
    Integer overflow in '+'
9223372036854775807

    4. Recursion and parse-depth caps​

    • Script call depth: each engine owns separate caps, defaulting to 256 active calls on the interpreter and 10,000 on the VM. Both use the catchable text Maximum recursion depth exceeded - possible infinite recursion. Configure the caps between executions with the API below; parallel workers snapshot them at region entry. An explicitly supplied legacy JAI_MAX_CALL_DEPTH build macro seeds both defaults, but the host can still override each one.
    • Native-stack headroom: an independent Windows guard can raise the same recursion error before a call-depth cap is reached. Increasing a cap does not disable this guard or make native recursion safe on a smaller stack. Other platforms currently have no native-stack headroom measurement.
    • Parser recursion: MAX_PARSE_DEPTH = 250 (detail/parser.hpp) counts weighted parser recursion, not AST nodes. It limits the guarded paths, but is not a complete native-stack guarantee: recursive assignment and type parsing are not covered by that counter.
    • Saved-program nesting: the shared .jaibite reader and writer retain their 1000-level AST/type traversal limit and also check Windows native-stack headroom. Either condition raises jaibite: AST nesting too deep or jaibite: type nesting too deep; the serialized format is unchanged.
    • JSON text parsing: JAI_MAX_JSON_PARSE_DEPTH = 128 (json_archive.hpp) limits nested JSON input to from_json.
    C++
    eng->max_call_depth(jai::backend_type::interpreter, 256);
eng->max_call_depth(jai::backend_type::vm, 10000);
auto vmLimit = eng->max_call_depth(jai::backend_type::vm);

    The setter accepts values from 1 through INT_MAX and refuses changes during execution or an active parallel region. Both overloads require a built-in backend type. An ordinary uncaught recursion error adds the category suffix : Maximum environment recursion depth exceeded; a native callback wrapper may additionally append : C++ exception.

    On the VM, a bare self tail call (return f(args) outside any try) reuses its frame and runs in constant space without accumulating call depth. A runaway tail loop is stopped by the execution budget, just like while (true). The interpreter does not perform this tail-call optimization. Ordinary VM script-to-script calls use in-loop frames, but constructors and C++ callbacks can still recurse natively.

    Putting it together: running untrusted script​

    C++
    auto eng = jai::engine::make();          // nothing registered = nothing reachable
eng->execution_budget(0.005);            // 5 ms per execute
eng->memory_cap(16 * 1024 * 1024);       // 16 MB high-water
eng->set_output_stream(myLogStream);     // print speaks only into this stream
// static checking is already strict — nothing to turn on
// register ONLY the API surface the script should have
eng->add_function("move_to", ...);

    There is a fifth rail you get without asking for it, and it fires earliest of all: strict checking (the default) rejects a script that reaches for anything you did not register, before a statement runs. An untrusted script that calls open_file or touches a global you never bound fails at load with a jai::static_check_error naming the line, not at run time, halfway through whatever it was doing (Static Checking). The checker is a convenience, not the boundary: a script can declare the name with extern and load anyway, and then hit the same wall at run time, because the name was never registered. The allowlist is the registration surface; the checker just tells you earlier.

    That is the whole configuration. Budget and cap exhaustion are terminal; overflow and recursion are catchable script errors; and there is nothing ambient to escape to. Reachability is opt-in at every layer: a type in the binary (even a self-registering jai::registrar) enters an engine only through an explicit bind_registrar or dynamic_binder call (the binder chapter's three doors). The serializers are hardened separately against hostile data: type and property names arriving in payloads are never executed, and oversized array/map length prefixes are rejected instead of pre-allocated (see Serialization).
