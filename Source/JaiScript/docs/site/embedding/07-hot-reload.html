Hot Reload​

Hot reload is not a bolt-on file watcher — it is what redefinition means in JaiScript. Executing a class Foo { ... } declaration when Foo already exists redefines the class and migrates every live instance in place. Executing a function f(...) declaration rebinds the global. The host's job is only to re-run the new source (engine->execute(newSource) / script-side include); the engine does the rest. The design promise (docs/why_jaiscript.md §5): the reload always succeeds — iteration speed is the point, an edit never bricks a running session.

Instance migration rules​

Verified live (hosts/reload.cpp — one engine, two executes):

C++
eng->execute(R"( class Player { int hp = 100; float speed = 1.0; string name = "Unnamed"; }
                 var p = Player(); p.hp = 62; p.name = "Alice"; )");

eng->execute(R"( class Player {
                     string hp = "0";          // retyped
                     string name = "Unnamed";  // kept
                     int level = 1;            // new
                     // speed removed
                     void hot_reload_migrate() { level = 5; }
                 } )");
hp: string 62                  <- retyped field CONVERTED (int 62 -> "62")
name: Alice                    <- same-name field KEPT its runtime value
level (set by migrate hook): 5 <- new field defaulted, then hook ran
speed removed: 1               <- removed field gone (access now throws)

Migration cost is linear in live instances and fields; 100 instances migrate fast enough to sit in a keypress handler (hot_reload_tests.cpp::performance_stress_test).

The hot_reload_migrate hook​

If the new class defines void hot_reload_migrate(), it runs once per live instance during the reload, after field migration — and inside the hook the old removed fields are still readable, which is what makes real data conversions possible:

jaiscript
class Config {
    auto version = 2;
    auto settings = {};          // new field
    // flags removed
    void hot_reload_migrate() {
        if (this.flags == 42) {  // OLD field still visible here
            this.settings = {"debug": true, "level": 5};
        }
    }
}

Chained across versions v1→v2→v3→... each reload runs only the incoming class's hook (hot_reload_tests.cpp::hot_reload_migrate_lifecycle). Robustness rules: an error in one instance's hook doesn't abort migration of the others (migrate_hook_error_is_isolated), and a hook that constructs new instances of the same class can't hang the reload (migrate_hook_constructing_instance_terminates — the execution budget backstops it).

Code on the live call stack​

Redefining a function (or class) while it is executing — e.g. a host callback fires mid-script and re-executes a script file — follows one rule: frames already on the stack finish with their old bodies; the global binding is replaced immediately, so recursion and all later calls resolve the new one; the new definition persists.

v1 damage(10): 10
v2 damage(10): 30        <- hosts/reload.cpp, verified

Pinned hard in hot_reload_correctness_tests.cpp: function_redefined_mid_call_persists (a recursive function swaps ITSELF mid-recursion: old frames complete on the old body, the recursive call already resolves the new one, and the new binding survives), self_redefinition_mid_call_persists_after_return, and reentrant_execute_preserves_this_in_ctor_and_method / reentrant_execute_swallowed_throw_does_not_leak_into_outer_run (a reentrant execute() neither clobbers the suspended outer run's environment nor leaks its exceptions into it). Coroutines suspended at reload keep their old bodies until rebuilt.

One pinned quirk (class_reload_mid_recursion_keeps_globals_coherent): a class method mid-recursion when its own class is reloaded fails to resolve sibling methods for the remainder of that one call (consistently, both backends) — afterwards the instance, the class, and new instances all work on the new bodies.

Live usage: the games' --dev modes​

Both shipped examples dogfood this:

  • **examples/roguelike** (--dev, key R): reload_scripts() in scripts/main.jai simply re-includes every rule file mid-game — "Classes hot-reload with instance migration; live coroutines (monster brains) keep their old bodies until rebuilt. G and RNG live in state.jai, which is deliberately skipped" (comment in the script). The pattern to copy: split rules (reloadable) from state (not re-executed).
  • **examples/demoreel**: live-coding — edit a scene file while it renders, reload on the fly.

include re-runs a file every time by design (PHP-style template semantics) — the forcing form. import is the cached module system with file_timestamp default behavior, and its mtime check happens when the import statement executes — reload is pull-based, flowing through normal execution. There is no watcher thread and no out-of-band reload sweep, deliberately: a module re-running has side effects, and those land exactly where control flow puts them. The host pattern is simply to re-execute the script entry point (per frame, per tick, on a keypress) — any import it reaches whose file changed re-imports on the way through, unchanged files cost one mtime check. engine::reset_import(s) is the narrow escape hatch (a regenerated file whose mtime didn't advance past timestamp granularity, or forcing a re-run under once mode), not the mechanism; set_import_behavior(once|always|file_timestamp) (engine.hpp).

Interaction with the rest of the engine​

  • Source cache / static checker: new source text is a new parse-cache entry, so a checked engine re-checks reloaded code automatically (static_check_tests.cpp::hot_reload_new_source_is_rechecked).
  • jaibite: class redefinition works across repeated bite executions too (engine_tests.hpp::jaibite_class_redefinition_across_runs).
  • Serialization: for C++-side class evolution, versioned archives + post_load_hook are the analogous migration story (see Serialization chapter); hot_reload_migrate is the script-side twin for live sessions.
