Serialization​

Two layers, one system: script-level to_json/from_json builtins for script values, and a C++ archive framework (JSON + binary through one interface, include/jaiscript/serialization/, spec in docs/SERIALIZATION.md and docs/JaiScript_BinarySerialization.md) for host types — designed as the Cereal replacement, with compatible member/free serialize/save/load dispatch.

Script side: to_json / from_json​

jaiscript
// snippets/json_roundtrip.jai — verified, both backends identical
class Player {
    int hp = 0;
    float speed = 0.0;
    string name = "";
}
auto p = Player();
p.hp = 42; p.speed = 1.5; p.name = "hero";

var j = to_json(p);
print(j);                      // {"_type_":"Player","hp":42,"speed":1.5,"name":"hero"}

var q = from_json(j);          // reconstructs a Player via the _type_ discriminator
print(type_of(q.hp) + " " + to_string(q.hp) + ", " + q.name);   // int 42, hero

// Typed fields ENFORCE on the way in: a float payload into an int field converts
// through the same table '=' uses (7.9 -> 7).
var r = from_json("{\"_type_\": \"Player\", \"hp\": 7.9, \"speed\": 2, \"name\": \"clone\"}");
print(type_of(r.hp) + " " + to_string(r.hp) + ", " + type_of(r.speed));  // int 7, float

// Plain values and containers round-trip too.
var m = from_json(to_json({"a": [1, 2.5, "three", true, null]}));
print(to_json(m));             // {"a":[1,2.5,"three",true,null]}

Key facts, each pinned:

  • Typed-field enforcement on deserialize: declared field types are stored on the class definition, and every write path — including from_json — converts through the same field kernel that = uses (float→int truncates, int→string via to_string; var fields stay dynamic). Pinned by semantics/strong_types_tests.cpp ("JSON round-trip preserves typed fields", "JSON float into int field truncates").
  • The class must be defined (or registered) in the engine before from_json sees its _type_; an unknown _type_ yields plain data rather than an instance.
  • Floats round-trip at full precision (std::to_chars shortest-round-trip; -0.0, infinities handled — fuzz fix FZ-NEG-ZERO, convenience_function_tests.cpp:: json_infinity_roundtrips).
  • Hostile-text hardening: parse depth capped at JAI_MAX_JSON_PARSE_DEPTH = 128, trailing garbage rejected, invalid unicode escapes are serialization errors, lone surrogates become replacement chars (json_reader_* tests).

C++ side: the convenience API​

C++
// hosts/serialize.cpp — compiled and run, verified
#include <jaiscript/serialization/convenience.hpp>

struct SaveGame {
    int level = 0; double time_played = 0; std::string hero; std::vector<int> inventory;
    template<typename Archive>
    void serialize(Archive& ar) {          // one method, both directions, both formats
        ar("level", level);
        ar("time_played", time_played);
        ar("hero", hero);
        ar("inventory", inventory);
    }
};

SaveGame save{7, 123.5, "Alice", {1, 2, 3}};
std::string json = jai::to_json(*eng, save);                  // human-readable
SaveGame loaded  = jai::from_json<SaveGame>(*eng, json);

std::vector<uint8_t> blob = jai::to_binary(*eng, save);       // compact little-endian
SaveGame fromBin = jai::from_binary<SaveGame>(*eng, blob);    // 114 bytes for this demo

Verified output (JSON is pretty-printed over several lines by default — indent parameter; condensed here):

{ "_type_": "", "level": 7, "time_played": 123.5, "hero": "Alice", "inventory": [1, 2, 3] }
loaded: level=7 hero=Alice items=3
binary: 114 bytes, hero=Alice

Also available: to_binary_string/from_binary_string, to_base64/from_base64, and Context& overloads that thread a user context pointer to nested load calls (json_with_user_context). The binary format is explicitly little-endian portable (binary_little_endian_portable).

Dispatch priority (Cereal-style — provide either serialize OR save/load)​

For a type T the archive picks, in order: native handling (primitives, std::vector/ map/unordered_map/array/pair, shared_ptr/weak_ptr/unique_ptr) → member save/load → member serialize → free save/load via ADL → free serialize via ADL → JAI_STATIC_BINDER compile-time properties → automatic property_owner<T> fallback (all JAI_PROPERTY fields). No match = static_assert. For smart pointers to non-default-constructible types, load_and_construct (member or ADL) is checked first. (docs/SERIALIZATION.md; exercised across serialization/convenience_function_tests.cpp — member_serialize_json/binary, explicit_save_load_json/binary, property_owner_json/binary_roundtrip, blended_*.)

Private members: friend jai::access (private_serialize_friend_jai_access).

Smart pointers, polymorphism, graphs​

  • shared_ptr dedupe: aliased pointers serialize once ($id) and re-alias on load (shared_ptr_json_roundtrip asserts the loaded copies share one object).
  • weak_ptr reconstruction works even for forward references (the weak_ptr appears in the stream before its owner) — weak_ptr_forward_reference_json/binary, serialization/weak_ptr_backref_tests.cpp.
  • Polymorphic roots: shared_ptr<Base> holding a Derived writes a $type discriminator and reconstructs the derived type on load, gated by registered assignability edges (dynamic_binder::base_class records them; suites polymorphic_serialization_tests.cpp, inheritance_serialization_tests.cpp, factory_deserialization_tests.cpp).
  • Versioning/migration: .version(n) on the binder stamps class versions; .post_load_hook([](T& self, int version){ ... }) runs after load for migration; .deserialization_factory(...) constructs non-default-constructible types (archive-only / context-only / context+archive signatures auto-detected).

Security posture (untrusted payloads)​

serialization/serialization_security_tests.cpp pins that deserialization never executes payload-controlled names: hostile _type_/property names in JSON, binary, and base64 are data, not code (from_json_type_name_not_executed, from_json_property_name_not_executed, from_binary_type_name_not_executed, from_base64_type_name_not_executed), and oversized array/map length prefixes in binary data are rejected instead of pre-allocated (binary_oversized_array_length_rejected, binary_oversized_map_length_rejected).

Which layer to use​

  • Script gameplay state (the crawler's save file is exactly this): script-side to_json(G) / from_json(text) — one line each way, typed fields re-enforced on load.
  • Host/engine objects, editor documents, network payloads: the C++ archives — JSON while debugging, to_binary when size/speed matter, same serialize method either way.
  • Pre-parsed script code is its own format: .jaibite via jaibite::save (see the jaibite chapter) — ASTs, not values.
