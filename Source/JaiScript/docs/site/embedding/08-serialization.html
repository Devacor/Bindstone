    Serialization​

    Two layers, one system.

    Script side: the to_json / from_json builtins turn any script value into text and back: one line each way.

    C++ side: an archive framework that writes JSON or a compact binary through one interface (include/jaiscript/serialization/). It is a drop-in for Cereal-shaped code: the same member/free serialize / save / load dispatch.

    The part worth knowing before you write any of it: binding a class for scripting does not make it archivable by itself. The C++ archives need what the class declares for them: a member or free serialize / save / load, or JAI_PROPERTY fields on a property_owner. What the dynamic_binder chain adds is the class's name for the script-value path, and a jai::registrar around the same chain gives the identity polymorphic saves need (below).

    Script side: to_json / from_json​

    jaiscript
    class Player {
    int hp = 0;
    float speed = 0.0;
    string name = "";
}
auto p = Player();
p.hp = 42; p.speed = 1.5; p.name = "hero";

var j = to_json(p);
print(j);

var q = from_json(j);          // reconstructs a Player via the _type_ discriminator
print(type_of(q.hp) + " " + to_string(q.hp) + ", " + q.name);

// A float payload landing in an int field: the load converts, it does not trust.
var r = from_json("{\"_type_\": \"Player\", \"hp\": 7.9, \"speed\": 2, \"name\": \"clone\"}");
print(type_of(r.hp) + " " + to_string(r.hp) + ", " + type_of(r.speed));

// Plain values and containers round-trip too.
var m = from_json(to_json({"a": [1, 2.5, "three", true, null]}));
print(to_json(m));
    output
    {"_type_":"Player","hp":42,"speed":1.5,"name":"hero"}
int 42, hero
int 7, float
{"a":[1,2.5,"three",true,null]}

    The interesting line is the third one. The payload said "hp": 7.9 and the field is declared int, so the load converted it (through the very same table = uses) and you got 7. Nothing about a save file is trusted more than an assignment is.

    A second argument pretty-prints: to_json(v, n) indents n spaces per level, and to_json(v) (or n = 0) writes one line.

    jaiscript
    class Player { int hp = 42; string name = "hero"; array<int> bag = [1, 2]; }
print(to_json(Player(), 2));
    output
    {
  "_type_": "Player",
  "hp": 42,
  "name": "hero",
  "bag": [
    1,
    2
  ]
}

    Key facts:

    • Typed-field enforcement on deserialize: declared field types are stored on the class definition, and every write path, including from_json, converts through the same field kernel that = uses (float→int truncates, int→string via to_string; var fields stay dynamic). A hostile or sloppy save file cannot sneak a string into an int hp.
    • The class must be defined (or registered) in the engine before from_json sees its _type_. An unknown _type_ is data, not an error: from_json("{\"_type_\": \"NoSuchClass\", \"hp\": 3}") hands you a plain map with both keys intact.
    • A known _type_ is constructed as Name() would construct it (the default constructor and the field initializers run, then the payload writes its fields). A constructor that throws or raises an error fails the from_json call with that error, catchable like any call's.
    • Values a JSON object cannot spell travel tagged, in the same $ family as the archives' $id: a char is {"$char": 122} (its code, 0..255), and a map whose keys are not all strings (or an empty one declared with such a key type) is {"$map": [[1, "sword"], [2, "bow"]]}, each key and value written by the same rules. from_json reads both back, so a char field and a map<int, string> field round-trip. A single-key object of any other shape ({"$char": 300}, a $map whose entries are not pairs) stays a plain map.
    • Handles keep their sharing. A shared_ptr<T> (what new T() yields) writes its object once, at its first appearance, as {"$shared_ptr_id": 1, "$shared_ptr_data": {...}}, and every later handle to the same object as {"$shared_ptr_id": 1}; a weak_ptr is {"$weak_ptr_id": 1} in the same numbering (with its object as "$weak_ptr_data" when it is the first reference), and an empty handle is null. The load hands back handles to one object per id, in any order and through cycles, so two slots that shared an object share it again; a weak pointer whose object nothing else in the save holds loads expired. to_binary / to_base64 keep the same graph. An id whose object the save never wrote fails the load with Invalid shared_ptr ID: 4.
    • Floats round-trip at full precision (std::to_chars shortest-round-trip; -0.0 keeps its sign). JSON has no spelling for an infinity or a NaN, so to_json writes null for them; to_base64 / from_base64 keep the exact bits.
    • A payload nests as deep as memory allows: parsing, rebuilding and writing walk values on work lists, so a save that loaded on one machine loads on another whatever its depth (a host record type's own recursion stops at the host thread's stack or JAI_MAX_HOST_RECORD_DEPTH = 1024 records). Hostile-text hardening: trailing garbage rejected, invalid unicode escapes are serialization errors, lone surrogates become replacement chars.

    Saving game state to a file​

    A save is to_json written to a file, and a load is the file read back through from_json. File access belongs to the host: the standalone runner provides write_file, read_file and file_exists, and an embedding host registers its own (they run through its virtual filesystem, its save folder, its cloud sync). app_data_dir(name) answers the platform's per-user data folder.

    jaiscript
    class Hero { string name = "ada"; int gold = 0; array<string> bag = []; }
class SaveGame { int version = 1; Hero hero; map<string, bool> flags; }

SaveGame game;
game.hero.gold = 120;
game.hero.bag.push("lantern");
game.flags["met_the_raccoon"] = true;
write_file("save1.json", to_json(game, 2));

SaveGame loaded = from_json(read_file("save1.json"));
print(loaded.hero.name, " ", loaded.hero.gold, " ", loaded.hero.bag[0], " ", loaded.flags["met_the_raccoon"]);
    output
    ada 120 lantern true

    A field added to the class after a save loads with its initializer, because from_json builds the object first and then writes the fields the file has. A version field like the one above lets a loader convert older files explicitly.

    C++ side: the convenience API​

    C++
    #include <jaiscript/serialization/convenience.hpp>

struct SaveGame {
    int level = 0; double time_played = 0; std::string hero; std::vector<int> inventory;
    template<typename Archive>
    void serialize(Archive& ar) {          // one method, both directions, both formats
        ar("level", level);
        ar("time_played", time_played);
        ar("hero", hero);
        ar("inventory", inventory);
    }
};

SaveGame save{7, 123.5, "Alice", {1, 2, 3}};
std::string json = jai::to_json(*eng, save);                  // human-readable
SaveGame loaded  = jai::from_json<SaveGame>(*eng, json);

std::vector<uint8_t> blob = jai::to_binary(*eng, save);       // compact little-endian
SaveGame fromBin = jai::from_binary<SaveGame>(*eng, blob);    // 114 bytes for this demo

    Output, with the JSON written by jai::to_json(*eng, save, 0): the third argument is the indent, 2 by default, and 0 writes one line. The root record opens with a _type_ tag, empty because to_json opens it with no name, and a plain struct's fields then follow flat; a C++ record nested inside it carries no _type_. (An owning pointer at the root sits under a value0 slot in its pointer shape instead: $id/$type/$val for a shared_ptr, the shape the binder chapter shows, and $val alone for a unique_ptr.)

    {"_type_": "","level": 7,"time_played": 123.5,"hero": "Alice","inventory": [1,2,3]}
loaded: level=7 hero=Alice items=3
binary: 114 bytes, hero=Alice

    Also available: to_binary_string/from_binary_string, to_base64/from_base64, and Context& overloads (jai::from_json<T>(*eng, json, ctx)) that thread a user context pointer to nested load calls. The binary format is little-endian on every platform, so a blob written on one machine loads on another.

    The loads that return T by value (from_json<T>, from_binary<T>, from_binary_string<T>, from_base64<T>) build a local T and return it, so T must be movable. A property_owner deletes its move constructor (its property manager points at its members), so it loads as jai::from_json<std::shared_ptr<T>>, which also keeps a derived object's $type.

    Dispatch priority (Cereal-style: provide either serialize OR save/load)​

    For a type T the archive picks, in order: primitives (arithmetic types, enums, std::string) → member save (writing) or load (reading) → member serialize → automatic property_owner<T> handling (every level's JAI_PROPERTY fields) → the built-in standard types (std::vector, map, unordered_map, array, pair, optional, variant, tuple, the sets, shared_ptr/weak_ptr/unique_ptr) → free serialize found by ADL → free save (writing) or load (reading) found by ADL. Members come first: a property_owner type that also declares save/load uses them, and can call save_owned_properties(ar) / load_owned_properties(ar) inside them to write its JAI_PROPERTY fields beside the hand-written ones, and a type with a member function never reaches a free one. A type with save but no load loads through its serialize (and the reverse). Free functions are found only in their two-parameter form (serialize(Archive&, T&), save(Archive&, const T&), load(Archive&, T&)); one with a version parameter is not found. A member save, load or serialize with a std::uint32_t version parameter is found and preferred over the one-parameter form (Versions says what it receives).

    No match is not a compile error: the archive throws jai::serialization_error when it reaches the value (Type '...' is not serializable. Add save/load, serialize, property_owner, or ADL functions — or mark the property transient., and is not deserializable on a load). A test that saves and loads each type catches it before a shipped save does. JAI_STATIC_BINDER (a compile-time property table some hosts declare instead of property_owner) is not part of this dispatch: its jai_static_type<T>::save / load runs for a statically bound property inside another statically bound type, and a statically bound type handed to the archive directly needs one of the functions above.

    A shared_ptr or weak_ptr load builds its object through load_and_construct when the type declares one: a static member static void load_and_construct(Archive&, jai::serialization::construct<T>&) with exactly those two parameters (<jaiscript/serialization/construct.hpp>); a free function or a form with a version parameter is not found. Without one, the archive default-constructs the object and loads it normally: a public default constructor, or a private one when the type declares friend jai::access;. A type with neither raises serialization_error. A unique_ptr always default-constructs, the same two ways.

    Private members: friend jai::access.

    The archive inside save, load and serialize​

    Named properties are the normal form; the unnamed calls exist for hand-written layouts. A writer:

    CallWrites
    ar.serialize("name", value), ar("name", value)a named property; value goes through the dispatch above
    ar(JAI_NVP(x), JAI_NVP(y)), ar(make_nvp("name", value))named properties, the key spelled by the macro (the variable's name) or the pair
    ar(obj)obj's own save or serialize, in place
    ar.write_element(value)the next element between begin_array and end_array
    ar.write_int8 … write_int64, write_uint8 … write_uint64, write_float32, write_float64, write_bool, write_stringone unnamed primitive
    begin_object(type_name, version) / end_object(), begin_array(size) / end_array(), begin_map(size) / write_map_key(key) / end_map()structure

    A reader mirrors it:

    CallReads
    ar.serialize("name", value), ar("name", value), ar(nvp)the named property into value; a record without it throws jai::serialization_error (Property 'name' not found during deserialization)
    ar(obj)obj's own load or serialize, from the current record
    ar.read_element(value)the next element between begin_array and end_array
    ar.has_property("name"), ar.seek_property("name")whether the current record has the property; positions the reader at it (false when it is absent)
    ar.read_int32(), ar.read_string(), … (the writer's widths)one unnamed primitive
    begin_object(type_name, version) (fills both) / end_object(), size_t n = begin_array() / end_array(), begin_map() / read_map_key(key) / end_map()structure
    ar.get_version()the version of the record opened last (Versions)

    Every failure in either direction throws jai::serialization_error, a jai::runtime_error.

    Versions and missing fields​

    Both formats are self-describing: every record names its properties, so a reader finds a property by name, never by position. The automatic property_owner load reads the properties the record and the class share. A property the record lacks keeps its initializer and a property the class no longer declares is skipped, so adding or removing a JAI_PROPERTY needs no migration code.

    A hand-written load asks for what it reads: ar("name", v) requires the property, so a field newer than some saves is read under ar.has_property("name") and keeps its initializer for a record written before it existed.

    The archives keep no class version for a C++ type. A record they open themselves carries none: in JSON it has no "_type_" or "_version_" key, and the binary writer stores an empty type name and version 0. Only the root record that to_json / to_binary open is named, with an empty type name and version 1 (which JSON leaves unwritten). A member save, load or serialize with a std::uint32_t version parameter compiles and is called, but the number is not a layout version. A save always receives 0. A load reached through a named read (ar("name", obj), a JAI_PROPERTY, a non-polymorphic pointer's $val) receives the version stored in that record, which reads as 1 in JSON (no "_version_" key) and 0 in binary unless a hand-written save opened the record with begin_object(type_name, version); every other load (ar(obj), a polymorphic pointer's $val) receives 0. ar.get_version() answers the version of the record opened last.

    A binder chain's .version(n) does not reach these records either. The binary archive stores it when it writes a bound object held as a script value, and that archive's load passes the stored number to the class's post_load_hook. Script-side from_json runs post_load_hook too, with the payload's "_version_" key when it has one and 1 otherwise; to_json writes no "_version_".

    What is left for a version is a field whose meaning changes: a unit, an encoding, one field split into two. Such a type writes its version as an ordinary property and defaults it for records that predate it, as From Cereal does:

    C++
    template<class Archive>
void save(Archive& ar) const {
    ar("format", std::uint32_t(2));
    ar(JAI_NVP(health));
    ar(JAI_NVP(experience));
}

template<class Archive>
void load(Archive& ar) {
    std::uint32_t format = 1;
    if (ar.has_property("format")) { ar("format", format); }
    ar(JAI_NVP(health));
    if (format >= 2) {
        ar(JAI_NVP(experience));
    } else {
        int level = 0;
        ar("level", level);
        experience = level * 100;
    }
}

    Wire formats​

    Both formats run the same calls; the writer decides the bytes. JSON writes a record as an object of its properties; a record opened with a type name (the root, or a hand-written begin_object(type_name, version)) leads with "_type_", and with "_version_" when the version is above 1. The binary writer is little-endian: a record is the byte 0x01, its type name (a uint32 length, then the bytes; empty for a record the archive opens itself) and a uint32 version (0 for such a record), then, when the record closes, its property count, every property name, every property's byte size, the values, and 0x02. An array is 0x03, a count, the elements and 0x04; a map is 0x05 … 0x06; null is 0x00. The names and sizes up front let a reader jump to a property by name and skip the ones it does not know without parsing them.

    Pointers have the same record shapes in both formats, keyed by the archive's per-save object ids:

    ValueWritten as
    shared_ptr, first time its object is written{"$id": N, "$val": {...}}; through a base pointer holding a registered derived class, {"$id": N, "$type": "Derived", "$val": {...}}
    shared_ptr to an object already written{"$id": N}, which the load re-aliases
    weak_ptr{"$ref": N}, with the object's "$val" (and "$type") inline when the weak pointer is its first reference in the save; an expired one is null
    unique_ptr{"$val": {...}}, by the pointer's static type with no $type: a unique_ptr<Base> holding a derived object writes only the Base fields and loads a Base, so a polymorphic owner is a shared_ptr<Base>
    a null pointernull

    Migrating from Cereal​

    A Cereal-serialized type moves over with spelling changes: CEREAL_NVP becomes JAI_NVP, friend class cereal::access becomes friend jai::access, member and free serialize / save / load keep their shape, and CEREAL_REGISTER_TYPE becomes a jai::registrar or a property_owner base. The files do not move: these archives do not read Cereal's format, so existing data is converted once, loaded with Cereal and saved with JaiScript. From Cereal, in the Code Migrations, maps every Cereal construct (and the Boost.Serialization spellings), converts a small save game, keeps both libraries in one function during the transition, and covers converting existing files.

    Smart pointers, polymorphism, graphs​

    • shared_ptr dedupe: aliased pointers serialize once ($id) and re-alias on load. Loaded copies share one object, exactly like the graph you saved.
    • weak_ptr reconstruction works even for forward references (the weak_ptr appears in the stream before its owner).
    • Polymorphism needs a serialization identity. Saving a shared_ptr<Base> that holds a Derived writes a $type discriminator and loads the Derived back, provided Derived has a name the archives know. A property_owner type has one from its declaration (dynamic_binder). A plain class bound with dynamic_binder gets one from a jai::registrar, whose jai::bases<...> tag records the edge the load checks; .base_class<B>() alone is the script-side edge, and a save through the base pointer without a registrar raises Cannot serialize unregistered polymorphic type 'class Monster' through pointer-to-base 'class Actor'. Register it with jai::registrar<T, Context, jai::bases<Base>>("Name") or derive from jai::property_owner<T, Base>. (the type names are the compiler's typeid spellings, MSVC's here):
      C++
      // examples/embed_quickstart: Monster derives Actor, both plain classes with serialize()
static jai::registrar<Monster, void, jai::bases<Actor>> monsterRegistrar("Monster", [](jai::dynamic_binder<Monster>& b) {
    b.base_class<Actor>()
     .constructor<std::string, int64_t>()
     .property("hp", &Monster::hp)
     .method("hurt", &Monster::hurt);
});

jai::bind_registrar(*eng);                            // binds every registrar into this engine
std::shared_ptr<Actor> boss = std::make_shared<Monster>("Troll", 40);
auto json = jai::to_json(*eng, boss);                 // "$type": "Monster"
auto back = jai::from_json<std::shared_ptr<Actor>>(*eng, json);   // a Monster again
      The chain's .version(n), .post_load_hook(...) and .deserialization_factory(...) serve a bound object the binary archive writes as a script value (Versions); a C++ pointer load constructs through load_and_construct or the default constructor. The chain itself is documented in dynamic_binder.
    • A script class layered over a C++ object serializes as itself. An object a script has extended writes $type (the script class), $script (its script fields) and $val (the C++ payload) through every archive path, and a load rebuilds the hybrid. See Script-Extensible Objects.
    • Signal connections ride save files. Named script-text receivers on signal properties serialize with their object; pass the engine as the load context (jai::from_json<std::shared_ptr<T>>(*eng, json, *eng)) and they re-arm on load, firing on the next emit. Function-object receivers (script lambdas, C++ callbacks) are runtime-only and skipped, never errored on. The worked round-trip is in the binder chapter.

    Security posture (untrusted payloads)​

    A dedicated security suite pins that deserialization never executes payload-controlled names: hostile _type_/property names in JSON, binary, and base64 are data, not code, and oversized array/map length prefixes in binary data are rejected instead of pre-allocated, so a 12-byte payload can't request a 2 GB allocation. A payload does choose which of the engine's classes a load builds: a type name it carries runs that class's zero-argument constructor and its post_load, as any load of that class would.

    The load itself runs no payload text, but two things in a payload reach code. A signal property (JAI_SIGNAL_PROPERTY) saves its script-text receivers as their source, and a load re-arms them, so each one runs as an execute of that text, in the engine's global scope with every API the host registered, the next time its signal fires. A payload carrying signal properties therefore carries script: load such objects only from a trusted source, or into an engine that runs untrusted script under the safety rails. And a payload chooses which classes the load constructs: a _type_ or $type naming a class the engine defines runs that class's own code (on from_json, a script class's constructor and field initializers, the setters of the properties the payload writes, and its post_load; a hybrid's field initializers and post_load; a C++ type's load_and_construct or default constructor and its load), never code the payload supplies.

    Which layer to use​

    • Script gameplay state (the crawler's save file is exactly this): script-side to_json(G) / from_json(text). One line each way, typed fields re-enforced on load.
    • Host/engine objects, editor documents, network payloads: the C++ archives. JSON while debugging, to_binary when size/speed matter, same serialize method either way. A network payload that holds signal properties carries script (Security posture).
    • Pre-parsed script code is its own format: .jaibite via jaibite::save (see jaibite). ASTs, not values.
