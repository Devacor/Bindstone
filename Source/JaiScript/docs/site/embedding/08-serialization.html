    Serialization​

    Two layers, one system.

    Script side: the to_json / from_json builtins turn any script value into text and back — one line each way.

    C++ side: an archive framework that writes JSON or a compact binary through one interface (include/jaiscript/serialization/; spec in docs/SERIALIZATION.md and docs/JaiScript_BinarySerialization.md). It is a drop-in for Cereal-shaped code — the same member/free serialize / save / load dispatch.

    The part worth knowing before you write any of it: a class you have already bound for scripting is most of the way to serializable. The dynamic_binder chain doubles as the serialization declaration for polymorphism, versioning, and construction. One declaration, both jobs.

    Script side: to_json / from_json​

    jaiscript
    class Player {
    int hp = 0;
    float speed = 0.0;
    string name = "";
}
auto p = Player();
p.hp = 42; p.speed = 1.5; p.name = "hero";

var j = to_json(p);
print(j);

var q = from_json(j);          // reconstructs a Player via the _type_ discriminator
print(type_of(q.hp) + " " + to_string(q.hp) + ", " + q.name);

// A float payload landing in an int field: the load converts, it does not trust.
var r = from_json("{\"_type_\": \"Player\", \"hp\": 7.9, \"speed\": 2, \"name\": \"clone\"}");
print(type_of(r.hp) + " " + to_string(r.hp) + ", " + type_of(r.speed));

// Plain values and containers round-trip too.
var m = from_json(to_json({"a": [1, 2.5, "three", true, null]}));
print(to_json(m));
    output
    {"_type_":"Player","hp":42,"speed":1.5,"name":"hero"}
int 42, hero
int 7, float
{"a":[1,2.5,"three",true,null]}

    The interesting line is the third one. The payload said "hp": 7.9 and the field is declared int, so the load converted it — through the very same table = uses — and you got 7. Nothing about a save file is trusted more than an assignment is.

    Key facts:

    • Typed-field enforcement on deserialize: declared field types are stored on the class definition, and every write path — including from_json — converts through the same field kernel that = uses (float→int truncates, int→string via to_string; var fields stay dynamic). A hostile or sloppy save file cannot sneak a string into an int hp.
    • The class must be defined (or registered) in the engine before from_json sees its _type_. An unknown _type_ is data, not an error: from_json("{\"_type_\": \"NoSuchClass\", \"hp\": 3}") hands you a plain map with both keys intact.
    • Floats round-trip at full precision (std::to_chars shortest-round-trip; -0.0 and infinities handled).
    • Hostile-text hardening: parse depth capped at JAI_MAX_JSON_PARSE_DEPTH = 128, trailing garbage rejected, invalid unicode escapes are serialization errors, lone surrogates become replacement chars.

    C++ side: the convenience API​

    C++
    #include <jaiscript/serialization/convenience.hpp>

struct SaveGame {
    int level = 0; double time_played = 0; std::string hero; std::vector<int> inventory;
    template<typename Archive>
    void serialize(Archive& ar) {          // one method, both directions, both formats
        ar("level", level);
        ar("time_played", time_played);
        ar("hero", hero);
        ar("inventory", inventory);
    }
};

SaveGame save{7, 123.5, "Alice", {1, 2, 3}};
std::string json = jai::to_json(*eng, save);                  // human-readable
SaveGame loaded  = jai::from_json<SaveGame>(*eng, json);

std::vector<uint8_t> blob = jai::to_binary(*eng, save);       // compact little-endian
SaveGame fromBin = jai::from_binary<SaveGame>(*eng, blob);    // 114 bytes for this demo

    Output (JSON is pretty-printed over several lines by default — the indent parameter; condensed here). Every archived object opens with a _type_ tag; the root's is empty because to_json opens the root record with no name, and a plain struct's fields then follow flat. (An owning pointer at the root sits under a value0 slot with its $id/$type/$val instead — the shape the binder chapter shows.)

    { "_type_": "", "level": 7, "time_played": 123.5, "hero": "Alice", "inventory": [1, 2, 3] }
loaded: level=7 hero=Alice items=3
binary: 114 bytes, hero=Alice

    Also available: to_binary_string/from_binary_string, to_base64/from_base64, and Context& overloads that thread a user context pointer to nested load calls (json_with_user_context). The binary format is explicitly little-endian portable (binary_little_endian_portable).

    Dispatch priority (Cereal-style — provide either serialize OR save/load)​

    For a type T the archive picks, in order: native handling (primitives, std::vector/ map/unordered_map/array/pair, shared_ptr/weak_ptr/unique_ptr) → member save/load → member serialize → free save/load via ADL → free serialize via ADL → JAI_STATIC_BINDER (a compile-time property table some hosts declare instead of property_owner; see docs/SERIALIZATION.md) → automatic property_owner<T> fallback (all JAI_PROPERTY fields). No match = static_assert, so an unserializable type fails at compile time, not in a shipped save. For smart pointers to non-default-constructible types, load_and_construct (member or ADL) is checked first. Full spec: docs/SERIALIZATION.md.

    Private members: friend jai::access.

    Smart pointers, polymorphism, graphs​

    • shared_ptr dedupe: aliased pointers serialize once ($id) and re-alias on load — loaded copies share one object, exactly like the graph you saved.
    • weak_ptr reconstruction works even for forward references (the weak_ptr appears in the stream before its owner).
    • Polymorphism and versioning ride the binding you already wrote. The same dynamic_binder chain that exposes a class to script is also its serialization declaration: .base_class<B>() records the assignability edges that let a shared_ptr<Base> holding a Derived write a $type discriminator and reconstruct the derived type on load; .version(n) + .post_load_hook(...) handle class evolution and migration; .deserialization_factory(...) constructs non-default-constructible types. One declaration, three payoffs — script access, polymorphic save/load, and migration. The chain itself is documented in dynamic_binder.
    • A script class layered over a C++ object serializes as itself. An object a script has extended writes $type (the script class), $script (its script fields) and $val (the C++ payload) through every archive path, and a load rebuilds the hybrid — see Script-Extensible Objects.
    • Signal connections ride save files. Named script-text receivers on signal properties serialize with their object; pass the engine as the load context — jai::from_json<std::shared_ptr<T>>(*eng, json, *eng) — and they re-arm on load, firing on the next emit. Function-object receivers (script lambdas, C++ callbacks) are runtime-only and skipped, never errored on. The worked round-trip is in the binder chapter.

    Security posture (untrusted payloads)​

    A dedicated security suite pins that deserialization never executes payload-controlled names: hostile _type_/property names in JSON, binary, and base64 are data, not code — and oversized array/map length prefixes in binary data are rejected instead of pre-allocated, so a 12-byte payload can't request a 2 GB allocation.

    Which layer to use​

    • Script gameplay state (the crawler's save file is exactly this): script-side to_json(G) / from_json(text) — one line each way, typed fields re-enforced on load.
    • Host/engine objects, editor documents, network payloads: the C++ archives — JSON while debugging, to_binary when size/speed matter, same serialize method either way.
    • Pre-parsed script code is its own format: .jaibite via jaibite::save (see jaibite) — ASTs, not values.
