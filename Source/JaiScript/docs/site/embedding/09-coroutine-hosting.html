Coroutine Hosting​

Script coroutines are the engine's built-in answer to per-entity behaviors, cutscenes, and multi-frame AI: calling a coroutine function returns a handle; resume() runs to the next yield, done() reports completion. Each backend owns its continuation representation behind one interface (interpreter: saved environment + AST continuation replay; VM: fibers/frames — include/jaiscript/core/coroutine.hpp, coroutine_backend_state).

Script surface​

jaiscript
// snippets/coroutine_tour.jai — verified, both backends identical
coroutine int countdown(int from) {
    for (int i = from; i > 0; --i) { yield i; }
    return 0;
}

auto c = countdown(3);
while (!c.done()) { print(to_string(c.resume())); }   // 3, 2, 1, 0
                                                       // (the final resume delivers the return value)
var seen = [];
for (auto v : countdown(4)) { seen.push(v); }          // range-for drives coroutines
print(to_json(seen));                                  // [4,3,2,1] — return value not included

Coroutine methods work too — the handle pins the receiver alive across suspension and this stays bound (coroutine.hpp::set_receiver; used in anger by examples/crawler's boss):

jaiscript
// snippets/coroutine_method.jai — verified, both backends identical
class Boss {
    int phase = 0;
    coroutine int fight() { phase = 1; yield 10; phase = 2; yield 20; return 99; }
}
auto b = Boss();
auto c = b.fight();
c.resume();   // 10, b.phase == 1 — mutations through the receiver are visible live

Pinning suite: language/coroutine_tests.cpp (yield/resume sequencing, done() transitions, multiple simultaneous handles, range-for driving, sum-until-done loops).

Driving from C++, pattern 1: through executes (the simple way)​

A handle stored in an engine global persists **across separate execute() calls** — each execute resumes exactly where the last left off. This is the frame-loop pattern: create behaviors once, tick them per frame with tiny resume scripts.

C++
// hosts/coro.cpp — compiled and run, verified
eng->execute(R"( coroutine int spawner(int n) {
                     for (int i = 1; i <= n; ++i) { yield i * 10; }
                     return -1;
                 }
                 var c = spawner(3); )");

for (int i = 0; i < 4; ++i) {
    auto v = eng->execute("c.resume();");                 // 10, 20, 30, -1
    bool finished = eng->execute("c.done()").as<bool>();  // false ×3, then true
}

Cross-execute persistence is specifically pinned — including the nasty case where the coroutine's source line is re-executed in between (redeclaring c) and where the bite form is used: coroutine_tests.cpp::coroutine_resume_across_executes_with_redeclare, semantics/engine_tests.hpp::jaibite_coroutine_across_runs / jaibite_coroutine_resume_across_runs.

Driving from C++, pattern 2: the native handle​

The script value is a jai::coroutine_handle in an object holder — you can pull it out once and drive it with zero script round-trips:

C++
// hosts/coro.cpp — verified
#include <jaiscript/core/coroutine.hpp>

eng->execute("var c2 = spawner(2);");
auto holder = eng->execute("c2").get_object_holder();
auto handle = std::static_pointer_cast<jai::coroutine_handle>(holder->data);

while (!handle->done()) {
    jai::checked_result<jai::script_value> step = handle->resume(eng.get());
    if (!step) break;                     // error channel (checked_result)
    step.value().as_int();                // 10, 20, then -1 (the return value)
}

Verified output: C++ resume -> 10, C++ resume -> 20, C++ resume -> -1.

API notes (coroutine.hpp):

  • resume(engine*) returns checked_result<script_value> — test it before using the value; a failed coroutine reports status::failed.
  • done() == completed || failed; get_status() exposes created/running/suspended/completed/failed.
  • The shared_ptr you extracted keeps the coroutine (and, for method coroutines, its receiver) alive — this is the supported way to own a behavior from C++.

Semantics worth knowing before you build on them​

  • **The final resume() of a completed coroutine delivers the return value** (the -1 / 99 above), and typed coroutine returns convert to the declared type (coroutine_tests.cpp::coroutine_final_typed_return_converts). Range-for consumes only the yielded values.
  • **Resuming past the end of a coroutine with no return** is the one open, deliberately-suppressed backend divergence (interpreter repeats the last yield, VM yields null; ledger source/tests/fuzz/known_divergences.md KD-CORO-RESUME-PAST-END, triaged: the interpreter is wrong). Always either give coroutines a return or gate on done() — both patterns are backend-identical.
  • Budget interaction: the execution budget applies per execute()/resume() call, and a budget overrun inside a coroutine is terminal like everywhere else — a catch around the yield cannot swallow it (execution_budget_tests.cpp::budget_terminal_skips_catch_inside_coroutine).
  • Coroutine parameters bind by value on both backends — even reference-shaped arguments (vm_backend_tests.cpp::coroutine_ref_param_lvalue_binds_by_value, coroutine_ref_param_identifier_binds_by_value, run on both backends); captures and closure state behave like lambdas.
  • Hot reload: a suspended coroutine keeps its old body until it finishes; new invocations get the new definition (see the Hot Reload chapter and the crawler's boss brain).
