    Signals & Observable Properties​

    Gameplay is event-shaped: a door opens, a wave spawns, three unrelated systems need to hear about it without the door knowing any of them exist.

    JaiScript ships two small C++ frameworks for exactly that. jai::signal is a typed multicast event whose receivers can be C++ lambdas or script; jai::observable_property<T> is a value that announces its own changes. Together they are how a host engine wires gameplay events to script.

    This chapter is your tour: firing and receiving signals from C++, observable values, and the three routes a signal takes to become script-connectable. How signal members get onto bound classes in the first place (the one-declaration JAI_SIGNAL_PROPERTY route and the machinery beneath it) is the binder chapter's deep dive. Headers: include/jaiscript/signals/, include/jaiscript/properties/.

    jai::signal: private emitter, public view​

    The founding idiom, and the one worth copying: the class owns a private emitter and exposes a public signal view. Outsiders can connect, only the owner can fire.

    C++
    class Door {
private:
    jai::signal_emitter<void(int)> onOpenSignal;
public:
    jai::signal<void(int)> onOpen;                    // public connect surface
    Door() : onOpen(onOpenSignal) {}
    void configure(jai::engine* eng) {
        onOpenSignal.script_engine(eng)               // enable script receivers
                    .parameter_names({"width"});      // names visible to script snippets
    }
    void open(int width) { onOpenSignal(width); }     // only the owner emits
};

Door door;
door.configure(eng.get());

auto cppConn    = door.onOpen.connect([](int w) { std::cout << "C++ receiver: opened to " << w << "\n"; });
auto scriptConn = door.onOpen.connect(
    "print(\"script receiver: opened to \" + to_string(width));");

door.open(42);          // both receivers fire
scriptConn = nullptr;   // dropping the receiver disconnects
door.open(7);           // only the C++ receiver remains

    Output:

    C++ receiver: opened to 42
script receiver: opened to 42
C++ receiver: opened to 7

    API essentials (signals/signal_decl.hpp)​

    • Connection lifetime = receiver lifetime. connect(...) is [[nodiscard]] and returns signal<T>::shared_receiver_type (alias jai::receiver<T>::shared_type); hold it in a member, drop it to disconnect. Alternatively use owned named connections (connect("id", callback) / disconnect("id")), where the emitter owns the receiver, or connect_oneshot(...) for fire-once.
    • Script receivers come in two forms: a source snippet (fired with parameter_names bound, as above) or a script function value (connect(id, script_value fn)). A failing receiver, C++ or script of either form, throws out of the emit, and the receivers after it in that pass do not run (When a receiver fails).
    • emit_while(...) treats receivers as predicates (stop propagation on false); receivers can block()/unblock() themselves.
    • Thread safety is on by default (recursive mutex around connect/disconnect/emit, so callbacks may modify the signal while it fires); define JAI_SIGNALS_NO_THREADSAFE for single-threaded max performance.
    • Header hygiene: hot-path headers should include signals/signal_decl.hpp only; signals/signal.hpp (the umbrella) or signal_impl.hpp is needed in TUs that actually fire script receivers. It pulls the engine glue.

    All of it (C++ and script receivers, oneshot, named connections, serialization of signal-bearing types) is covered by a dedicated test suite.

    observable_property​

    C++
    #include <jaiscript/properties/property_manager.hpp>
#include <jaiscript/properties/property_serialization.hpp>   // property<T> vtable lives here
#include <jaiscript/properties/observable_property.hpp>

jai::property_manager mgr;
jai::observable_property<int> hp(mgr, "hp", 100);

auto watch = hp.on_change.connect([](const int& oldV, const int& newV) {
    std::cout << "hp: " << oldV << " -> " << newV << "\n";
});
hp = 75;              // emits (100 -> 75)
hp += 10;             // arithmetic ops emit too (75 -> 85)
hp.set_silent(50);    // NO signal — the loading/initialization path
std::cout << "final hp: " << hp.get() << "\n";   // 50

    Output: hp: 100 -> 75, hp: 75 -> 85, final hp: 50.

    Semantics from the header (properties/observable_property.hpp): assignment emits only on actual change (old != new); on_change is a public signal<void(const T&, const T&)> over a private emitter (same idiom); ++/--/compound ops all emit; set_silent mutates without notifying. Properties register themselves with their property_manager (that's what powers schema-driven auto_bind and automatic serialization of JAI_PROPERTY fields).

    One linking gotcha: a standalone TU that instantiates property<T> needs properties/property_serialization.hpp (or anything that pulls serialization/archive_impl.hpp). The property's virtual serialize methods are defined there. dynamic_binder.hpp includes it already, so binder-using TUs never notice.

    Connecting from script​

    Script sees every signal, however its class was registered, as the same three-verb surface: connect(name, handler), disconnect(name), connected(name). Handlers come in the same two receiver forms C++ uses: a function (script lambda: parameters bind positionally from the emit arguments, no naming required) or a script-text snippet (runs with the emitter's parameter_names in scope). C++ emits fire both. There are three routes a signal takes to reach script, from most to least automatic.

    1. Auto-bound: the one-declaration route​

    For a property_owner class registered the one-declaration way from the binder chapter, declaring JAI_SIGNAL_PROPERTY(void(int64_t), onWave) was the entire script registration. auto_bind surfaces the member, and script connects immediately. The Spawner from that chapter again:

    jaiscript · needs the Spawner registration from the binder chapter
    auto s = Spawner();
s.onWave.connect("hud", [=](int wave) -> void {
    print("wave {} incoming", wave);
});
s.spawn_wave();
s.spawn_wave();
    output
    wave 1 incoming
wave 2 incoming

    This is the default route for engine classes. Reach for it first. Script-text receivers connect through the same verb (s.onWave.connect("logger", "print(\"wave logged\");")) and are the receivers that can ride save files, named or unnamed; the binder chapter's serialization section shows one surviving a JSON round-trip and firing after load.

    2. Any signal member, one binder line​

    A class that isn't a property_owner exposes a plain jai::signal<Sig> or signal_emitter<Sig> member (any signature) with one .property line. Here the Door from above:

    C++
    jai::dynamic_binder<Door>(*eng, "Door")
    .constructor<>()
    .method("open", &Door::open)
    .property("onOpen", &Door::onOpen)     // the whole script exposure
    .build();
    jaiscript · needs the host registration above
    var d = Door();
d.onOpen.connect("watch", [=](int w) -> void { print("opened to {}", w); });
d.open(42);
d.onOpen.disconnect("watch");
d.open(7);
print("silent after disconnect: {}", !d.onOpen.connected("watch"));
    output
    opened to 42
silent after disconnect: true

    Both routes hand script one generic engine-registered Signal view over a type-erased operations table. One class serves every signature. The mechanism, and the two honest edges worth knowing before shipping (a view is a member read of a live bound object and dangles past its owner; text receivers connected through the view see whatever parameter_names the owner set in C++), are covered in the binder chapter's signals section.

    3. bind_signal_type: the explicit typed form​

    When you want a named script-visible type for one signature, jai::bind_signal_type<Sig>(engine, "Name") (signals/signal_binding.hpp) registers signal<Sig> under "Name" and signal_emitter<Sig> under "NameEmitter", each with the same three verbs:

    C++
    jai::bind_signal_type<void(int)>(*eng, "IntSignal");   // "IntSignal" + "IntSignalEmitter"

    Connecting never requires it. Routes 1 and 2 cover every signature generically. Reach for the typed form when:

    • You want the signature to have a name. A registered type name makes signals of that shape first-class citizens of the registration surface, visible to registration-time type checks and nameable in configure lambdas (binder.bound_engine() is where registrars call it).
    • You want to pre-register the surface independent of any owning class. The registration is idempotent (is_type_registered guards it), so shared signal signatures can be bound once at engine setup.
    • Precedence. A typed registration wins: .property member reads of that signature hand out the typed object instead of the generic view. Behavior is identical (same verbs, same receivers), so this is an opt-in nicety, never a requirement.

    Notes that apply to all three routes​

    • What the checker sees. A bound class is a declared name, so auto s = Spawner(); passes strict; the signal member itself is a binder property, which the checker leaves untyped. connect / disconnect / connected and their arguments are checked at run time, never at load. A handler lambda's body is checked like any other lambda. (Rules in Static Checking.)
    • observable_property<T> members registered via the property schema (auto_bind on a property_owner) surface to script as transparent wrappers: player.score + 5 forwards to the underlying int, while player.score.on_change resolves on the wrapper, identically on both backends.
    • When C++ invokes a script function directly outside a normal call (converted callbacks, signal receivers), wrap the invocation in jai::engine::external_call_guard. Without it, reference parameters would bind against whatever script call happens to be in flight (engine.hpp; the signal glue does this for you).

    How this compares: Boost.Signals2, Qt, sigslot​

    If you have used a C++ signal library, most of jai::signal will look familiar: a typed multicast event, callables connected to it, every receiver run in connection order when it fires. The differences sit where a scripting engine needs what a pure C++ library never does (script receivers, connections that ride a save file) and in a few deliberate choices about ownership and errors.     Lightweight header-only sigslot libraries usually take Boost's shape with fewer features: a signal object anyone can emit, connect returning a connection handle (often with a scoped variant that disconnects on destruction), lifetime tracking through an observer base class or a weak pointer, and thread safety chosen by a template or compile-time switch. None of them runs script or saves its connections, so where this section says Boost, read that family too.

    Declaring: only the owner fires​

    A Boost signal is its whole interface: whoever can reach the object can both connect and call operator(), so a class that wants to keep emission to itself keeps the signal private and writes its own forwarding connect. Qt signals are member functions that moc implements, and any code holding the object can call them; keeping emission inside the class is a convention.

    JaiScript splits the two roles into two types. signal_emitter<Sig> connects and emits; signal<Sig> is a facade over a reference to an emitter with only the connecting half (connect, connect_oneshot, disconnect, connected, observer_count). The owner keeps the emitter private and builds the public facade from it in its constructor, so the compiler enforces who can fire. JAI_SIGNAL_PROPERTY declares exactly that pair, and script holds the same line: a facade member read from script has no emit; script fires a signal only when the host binds the emitter itself. The facade holds a reference, so a copy of it is valid only while the owning object lives.

    Connection lifetime and ownership​

    The handle is the connection. connect returns a shared_ptr to the receiver (signal<Sig>::shared_receiver_type, also spelled receiver<Sig>::shared_type) and the emitter keeps only a weak reference. The connection lives exactly as long as someone holds that pointer: reset it, or let the member holding it die, and the receiver stops firing; the emitter drops the dead entry after its next emit. Boost and Qt default the other way: a connection outlives its handle until someone calls disconnect or the signal is destroyed, and Boost's scoped_connection is the closest match to JaiScript's default. The unnamed connect overloads are [[nodiscard]] because discarding their result disconnects at once.

    Tying a connection to an object means letting the object hold the handle: a member, or a receiver_owner (signals/receiver_owner.hpp), which holds receivers of any signature and is built into every property_owner as track(...). When the object dies its handles die, and the connections with them. Boost turns this around: the slot watches the object (slot_type(f).track(ptr), or track_foreign for std::shared_ptr), the connection ends when the tracked object expires, and the tracked object is kept alive while its slot runs. JaiScript keeps the receiver alive for the length of its own call, but nothing pins an object the callback captured. Qt needs no code at all for QObject receivers: destroying the sender, the receiver or the context object of a functor connection disconnects it, and a functor connected without a context object lives as long as the sender.

    Named connections (connect("id", ...)) belong to the emitter: they last until disconnect("id"), clear() or the emitter's death, and connecting again under an id that is already connected takes the name over: the earlier receiver stops firing unless C++ still holds its handle. Script connects only this way. If the emitter dies first, a handle stays safe to hold and its receiver's connected() reports false.

    Script receivers and hot reload​

    A receiver is a C++ callable, a script-text receiver or a script function receiver, and both script forms connect from either side. From C++, connect("text") returns a handle like any other, while connect("id", "text") and connect("id", fn) (a function script_value) are named connections. From script, obj.sig.connect("name", handler) takes a function or lambda, or a string of source. A function receiver receives the emit's arguments positionally; a text receiver runs its source with the arguments bound as locals under the emitter's parameter_names (arg_0, arg_1, ... when none are set), on the engine the emitter was given with script_engine(eng). Boost connects C++ callables only. Qt's QML engine connects JavaScript handlers to signals, a separate mechanism from moc's C++ slots.

    Under hot reload, connections are C++ state on the emitter, so a reload neither drops nor duplicates them, and re-running the code that connects under a name replaces the receiver of that name. What a receiver runs after the reload depends on its form:

    • A text receiver runs its source each time the signal fires, so the names in it resolve to whatever is defined at that moment, reloaded definitions included.
    • A lambda resolves the program-scope names it calls when it runs, so [=](int w) -> void { on_wave(w); } reaches a reloaded on_wave.
    • A named function passed directly (connect("hud", on_wave)) is the function value it was when connected and keeps that body; wrap it in a lambda, or re-run the connect, to follow reloads.

    Connections that save​

    JAI_SIGNAL_PROPERTY gives the signal a hidden property that serializes the emitter with the owner's other properties, in JSON or binary. It writes the signal's parameter_names and each script-text receiver with its source and parameter names, a named one by id; loading rebuilds those receivers on the archive's engine and reconnects them, a named one under its id and an unnamed one held by the emitter, ready to fire. C++ callbacks and script function receivers are runtime-only: a function value is not text, so it is not written. Neither Boost nor Qt saves connections as part of an object's state; there the host reconnects after a load.

    When a receiver fails​

    A failing receiver throws out of the emit, whatever its kind: a C++ callback's exception, a script-text receiver's error and a script function receiver's error alike. The receivers after it in that pass do not run. The emitter stays consistent as the exception unwinds (disconnects queued during the emit, fired one-shots and dead entries are still cleaned up), so the emit site can catch the exception and fire again. When script triggered the emit through a bound method, the error is that call's run-time error, and a script try/catch around the call catches it.

    Boost behaves the same way: an exception from a slot propagates out of the signal call and the remaining slots do not run. Qt documents an exception thrown from a slot invoked through a connection as undefined behavior unless the slot handles it, and a queued slot runs from the event loop, where there is no emitter to throw to.

    Threads​

    Unless JAI_SIGNALS_NO_THREADSAFE is defined, each emitter owns one recursive mutex, held by connect, disconnect, connected, observer_count, clear and the whole of an emit, receivers included. That is the guarantee, and it has three consequences:

    • Emits of one signal from different threads run one after another, and a connect or disconnect from another thread waits for an emit in progress to finish.
    • A receiver may connect, disconnect or re-emit the same signal while it fires (the mutex is recursive). A receiver disconnected during an emit can still run later in that pass; it leaves the list when the outermost emit returns. A receiver connected during an emit runs in the same pass.
    • Because the lock is held while receivers run, a receiver must not wait on another thread that is connecting to or emitting the same signal.

    Nothing else is locked: block()/unblock() (on the emitter or a receiver), script_engine(...) and parameter_names(...) are plain state, set up before the signal is shared. Receivers run on the emitting thread, and a script receiver runs on its engine there, so a signal with script receivers is emitted on the thread that is using that engine (one engine serves one thread at a time).

    Boost.Signals2 locks internally so connect, disconnect and invocation can be called from different threads at once; it runs slots without holding the signal's own lock, and its mutex type is a template parameter (dummy_mutex for single-threaded use). Qt adds what neither library has, delivery across threads: a queued connection copies the arguments into an event for the receiver's thread and runs the slot from that thread's event loop, and the default automatic connection chooses queued delivery when the receiver lives in another thread. JaiScript has no queued delivery; a host that emits from a worker and wants receivers on its main thread hands the emit to that thread itself.

    Combiners and return values​

    A signature may return a value, but emit and operator() return nothing: each receiver's result is discarded. The one aggregate is emit_while, available when the signature returns bool: it runs receivers in order, stops at the first that returns false and returns false, otherwise true (a blocked signal returns true without running any). Boost generalizes this with combiners: the combiner receives an iterator range over the slots' results, invoking each slot as it is dereferenced, and the default returns an optional holding the last slot's result (empty when no slot ran). Qt documents signals as returning void and has no combiner.
