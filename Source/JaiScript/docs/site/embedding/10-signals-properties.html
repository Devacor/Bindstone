Signals & Observable Properties​

Gameplay is event-shaped: a door opens, a wave spawns, three unrelated systems need to hear about it without the door knowing any of them exist. JaiScript ships two small C++ frameworks for exactly this — jai::signal, a typed multicast event whose receivers can be C++ lambdas or script, and jai::observable_property<T>, a value that announces its own changes — and they are how the MutedVision engine wires gameplay events to script. This chapter is the user's tour: firing and receiving signals from C++, observable values, and the three routes a signal takes to become script-connectable. How signal members get onto bound classes in the first place — the one-declaration JAI_SIGNAL_PROPERTY route and the machinery beneath it — is the binder chapter's deep dive. Headers: include/jaiscript/signals/, include/jaiscript/properties/.

jai::signal — private emitter, public view​

The founding idiom, used throughout the MutedVision engine: the class owns a private emitter and exposes a public signal view — outsiders can connect, only the owner can fire.

C++
// hosts/signals.cpp — compiled and run, verified
class Door {
private:
    jai::signal_emitter<void(int)> onOpenSignal;
public:
    jai::signal<void(int)> onOpen;                    // public connect surface
    Door() : onOpen(onOpenSignal) {}
    void configure(jai::engine* eng) {
        onOpenSignal.script_engine(eng)               // enable script receivers
                    .parameter_names({"width"});      // names visible to script snippets
    }
    void open(int width) { onOpenSignal(width); }     // only the owner emits
};

Door door;
door.configure(eng.get());

auto cppConn    = door.onOpen.connect([](int w) { /* C++ receiver */ });
auto scriptConn = door.onOpen.connect(
    "print(\"script receiver: opened to \" + to_string(width));");

door.open(42);          // both receivers fire
scriptConn = nullptr;   // dropping the receiver disconnects
door.open(7);           // only the C++ receiver remains

Verified output:

C++ receiver: opened to 42
script receiver: opened to 42
C++ receiver: opened to 7

API essentials (signals/signal_decl.hpp)​

  • Connection lifetime = receiver lifetime. connect(...) is [[nodiscard]] and returns signal<T>::shared_receiver_type (alias jai::receiver<T>::shared_type); hold it in a member, drop it to disconnect. Alternatively use owned named connections — connect("id", callback) / disconnect("id") — where the emitter owns the receiver, or connect_oneshot(...) for fire-once.
  • Script receivers come in two forms: a source snippet (fired with parameter_names bound, as above) or a script function value (connect(id, script_value fn)). Script-receiver errors route to engine::report_script_error (host-installable sink) instead of throwing into the emit site.
  • emit_while(...) treats receivers as predicates (stop propagation on false); receivers can block()/unblock() themselves.
  • Thread safety is on by default (recursive mutex around connect/disconnect/emit, so callbacks may modify the signal while it fires); define JAI_SIGNALS_NO_THREADSAFE for single-threaded max performance.
  • Header hygiene: hot-path headers should include signals/signal_decl.hpp only; signals/signal.hpp (the umbrella) or signal_impl.hpp is needed in TUs that actually fire script receivers — it pulls the engine glue.

All of it — C++ and script receivers, oneshot, named connections, serialization of signal-bearing types — is pinned by a dedicated test suite.

observable_property​

C++
// hosts/signals.cpp — verified
#include <jaiscript/properties/property_manager.hpp>
#include <jaiscript/properties/property_serialization.hpp>   // property<T> vtable lives here
#include <jaiscript/properties/observable_property.hpp>

jai::property_manager mgr;
jai::observable_property<int> hp(mgr, "hp", 100);

auto watch = hp.on_change.connect([](const int& oldV, const int& newV) { ... });
hp = 75;              // emits (100 -> 75)
hp += 10;             // arithmetic ops emit too (75 -> 85)
hp.set_silent(50);    // NO signal — the loading/initialization path
hp.get();             // 50

Verified output: hp: 100 -> 75, hp: 75 -> 85, final hp: 50.

Semantics from the header (properties/observable_property.hpp): assignment emits only on actual change (old != new); on_change is a public signal<void(const T&, const T&)> over a private emitter (same idiom); ++/--/compound ops all emit; set_silent mutates without notifying. Properties register themselves with their property_manager (that's what powers schema-driven auto_bind and automatic serialization of JAI_PROPERTY fields).

One linking gotcha: a standalone TU that instantiates property<T> needs properties/property_serialization.hpp (or anything that pulls serialization/archive_impl.hpp) — the property's virtual serialize methods are defined there. dynamic_binder.hpp includes it already, so binder-using TUs never notice.

Connecting from script​

Script sees every signal — however its class was registered — as the same three-verb surface: connect(name, handler), disconnect(name), connected(name). Handlers come in the same two receiver forms C++ uses: a function (script lambda — parameters bind positionally from the emit arguments, no naming required) or a script-text snippet (runs with the emitter's parameter_names in scope). C++ emits fire both. There are three routes a signal takes to reach script, from most to least automatic.

1. Auto-bound — the one-declaration route​

For a property_owner class registered the one-declaration way from the binder chapter, declaring JAI_SIGNAL_PROPERTY(void(int64_t), onWave) was the entire script registration — auto_bind surfaces the member, and script connects immediately. The Spawner from that chapter again:

jaiscript
auto s = Spawner();
s.onWave.connect("hud", [=](int wave) -> void {
    print("wave {} incoming", wave);
});
s.spawn_wave();
s.spawn_wave();
output
wave 1 incoming
wave 2 incoming

This is the default route for engine classes — reach for it first. Named script-text receivers connect through the same verb (s.onWave.connect("logger", "print(\"wave logged\");")) and are the receivers that can ride save files; the binder chapter's serialization section shows one surviving a JSON round-trip and firing after load.

2. Any signal member, one binder line​

A class that isn't a property_owner exposes a plain jai::signal<Sig> or signal_emitter<Sig> member — any signature — with one .property line. Here the Door from above:

C++
jai::dynamic_binder<Door>(*eng, "Door")
    .constructor<>()
    .method("open", &Door::open)
    .property("onOpen", &Door::onOpen)     // the whole script exposure
    .build();
jaiscript
var d = Door();
d.onOpen.connect("watch", [=](int w) -> void { print("opened to {}", w); });
d.open(42);
d.onOpen.disconnect("watch");
d.open(7);
print("silent after disconnect: {}", !d.onOpen.connected("watch"));
output
opened to 42
silent after disconnect: true

Both routes hand script one generic engine-registered Signal view over a type-erased operations table — one class serves every signature. The mechanism, and the two honest edges worth knowing before shipping (a view is a member read of a live bound object and dangles past its owner; text receivers connected through the view see whatever parameter_names the owner set in C++), are covered in the binder chapter's signals section.

3. bind_signal_type — the explicit typed form​

When you want a named script-visible type for one signature, jai::bind_signal_type<Sig>(engine, "Name") (signals/signal_binding.hpp) registers signal<Sig> under "Name" and signal_emitter<Sig> under "NameEmitter", each with the same three verbs:

C++
jai::bind_signal_type<void(int)>(*eng, "IntSignal");   // "IntSignal" + "IntSignalEmitter"

Connecting never requires it — routes 1 and 2 cover every signature generically. Reach for the typed form when:

  • You want the signature to have a name. A registered type name makes signals of that shape first-class citizens of the registration surface — visible to registration-time type checks and nameable in configure lambdas (binder.bound_engine() is where registrars call it).
  • You want to pre-register the surface independent of any owning class — the registration is idempotent (is_type_registered guards it), so shared signal signatures can be bound once at engine setup.
  • Precedence. A typed registration wins: .property member reads of that signature hand out the typed object instead of the generic view. Behavior is identical — same verbs, same receivers — so this is an opt-in nicety, never a requirement.

Notes that apply to all three routes​

  • observable_property<T> members registered via the property schema (auto_bind on a property_owner) surface to script as transparent wrappers: player.score + 5 forwards to the underlying int, while player.score.on_change resolves on the wrapper — pinned by tests on both backends.
  • When C++ invokes a script function directly outside a normal call (converted callbacks, signal receivers), wrap the invocation in jai::engine::external_call_guard — without it, reference parameters would bind against whatever script call happens to be in flight (engine.hpp; the signal glue does this for you).
