    Performance Notes​

    How fast is it, and how do you write fast code in it? This chapter is the site's one home for both answers: the design that makes the VM quick, the cost model that makes your code quick, and every measured number: microbenchmarks against Lua, Squirrel, and ChaiScript (head-to-head suites in source/tests/performance/, MSVC x64 Release, min-of-5), the embedding cost sheet, and complete games measured end-to-end. The long-form report is docs/PERFORMANCE.md; this page adds a newer machine's numbers on top of it, and says which is which at the top of the measured section. One caveat travels with all of it: the benchmark harness reports integer µs with real run-to-run variance. Compare bands and medians, not ±1 µs deltas.

    What the VM does for you​

    You write ordinary script; the bytecode VM earns its keep below the waterline:

    • Fused superinstructions and register temps. The compiler collapses the common shapes (sum += a[i] * 2.0, compare-and-branch, element-read-into-local, nested arithmetic through frame-slot temporaries) into single dest-addressed opcodes, so a hot statement is one dispatch, not five, and intermediate results never touch the operand stack. A fused compound loop runs in the low tens of nanoseconds per iteration (the numbers are below).
    • Counted loops without ceremony. for (int i = 0; i < n; ++i) compiles to dedicated loop opcodes; there is no per-iteration environment allocation, and variable resolution is inline-cached.
    • Typed arrays. array<int> / array<float> keep raw primitive buffers behind the same script API as ordinary arrays: a 13.6k-element pixel grid drops from 435 KB to 109 KB, a value-semantics clone becomes a memcpy, and element access skips boxing entirely. This is the intended container for bulk numeric data.
    • Calls stay in the loop. Script calls never recurse natively. Frames are pooled and pushed inside the dispatch loop, and arguments bind zero-copy from the stack window.
    • In-language parallelism. parallel_for / parallel_transform run bodies that the engine can prove safe across a worker pool, deterministic by construction (identical results and hashes at any worker count), reaching 4.8× over the serial loop at 8 workers on a 4C/8T machine for a 100k-element map.
    • Thin values. script_value is 32 bytes, static-assert-gated: two per cache line.
    • Two backends, one contract. The tree-walking interpreter is the oracle that keeps the VM honest. The full test suite and a differential fuzzer hold both to byte-identical behavior (see Backends), so the fast paths above carry no semantic drift, and any workload can A/B the backends to separate "slow" from "wrong".
    • Safety that stays out of the profile. Checked integer overflow detects with intrinsics (not division), the execution-budget clock samples every 1024 ticks, and the idle debugger hook is one predictable branch per statement. None of them is measurable in hot loops.

    What idiomatic-fast code looks like​

    jaiscript
    // The fast shape: typed locals, typed arrays, & params, compound element stores.
array<int> pix = [];
for (int i = 0; i < 64; ++i) { pix.push(0); }

function shade(array<int>& dst, int base) {      // & = no copy, writes land in the caller
    for (int i = 0; i < dst.size(); ++i) {
        dst[i] += base + (i & 7);                // compound element store: one fused op
    }
}

shade(pix, 100);
int sum = 0;
for (int i = 0; i < pix.size(); ++i) { sum += pix[i]; }
print("sum = {}", sum);

function square(int x) { return x * x; }
array<int> nums = [];
for (int i = 1; i <= 8; ++i) { nums.push(i); }
var squares = parallel_transform(nums, square);   // deterministic at any worker count
print(to_json(squares));
    output
    sum = 6624
[1,4,9,16,25,36,49,64]

    The rules this example encodes, in priority order:

    • Declare types. int and auto locals ride slot storage and the typed fast paths; var is the dynamic opt-out and costs accordingly.
    • Pass anything heavy by &. Value semantics means a by-value parameter deep-copies unless the callee provably only reads it (then the argument binds in place at reference speed, see the elision); & is the cheap-by-design idiom, and it makes mutation visible in the signature. Decision guidance: Value Semantics; the three-way measurements (value vs & vs shared_ptr) are below.
    • Use array<int>/array<float> for bulk numeric data: grids, pools, geometry tables. Same API, flat storage.
    • Prefer compound element stores. a[i] += v is one fused dispatch, measurably cheaper than spelling out the read-modify-write.
    • Define classes once. Executing a class declaration does redefinition/hot-reload bookkeeping; keep class definitions out of per-frame scripts and re-run only the code that ticks.

    The cost model​

    The intuition, cheapest to dearest (every rung quantified in the measured section below):

    • Typed-local arithmetic and fused element ops are the floor. A hot fused loop iteration is tens of nanoseconds; a single statement is sub-microsecond on either backend.
    • Function calls are the unit of cost. A script call in a tight loop costs roughly ten fused-loop iterations on the VM; method invocation adds receiver binding and dispatch on top. Loop- and method-shaped code is where JaiScript holds its own; call-dense recursion is where rivals with cheaper frames pull ahead.
    • Value semantics is a tax you opt out of with &. Assignment and by-value parameters deep-copy; reference parameters and var& declarations are the cheap-by-design idiom. Decision guidance: Value Semantics; three-way measurements: below.
    • Class declaration is bookkeeping, not construction. Executing a class declaration pays redefinition/hot-reload machinery every time: cheap once, wasteful per-frame.
    • Engine lifecycle sits far above script cost. Creating an engine and registering the stdlib cost hundreds of warm executes. Reuse engines; never build one per evaluation.

    What's slower, and what to use instead​

    • Call-dense recursion. Lua runs fib(15) ~4.5× faster and Squirrel ~2.4×; the cost is per-call frame setup, not opcode count. Bare self tail calls are the exception: on the VM, return f(args) reuses the live frame (constant stack space, no depth limit, ~40 ns per call), so accumulator-style tail recursion runs at loop speed and any depth. The caveat applies to non-tail shapes like fib's f(n-1) + f(n-2): most game scripts are loop- and method-shaped, where the gap is small to none. Keep naive deep non-tail recursion out of per-frame hot paths, or express the algorithm iteratively.
    • By-value copies of big structures. Use & parameters and var& declarations for anything heavy. The BST benchmark written with & runs 65 µs on the reference machine against 462 µs for the naive by-value spelling (~7×; the older report machine measured the same pair at ~3.7×): by-value deep-copies a subtree at every recursion level, and that copy is the whole difference.
    • Bulk per-element pixel pushing. Software rendering (tens of thousands of scripted element reads and stores per frame) is where any tagged-value VM pays list price against Lua (GLOOM serial takes 3.55× Lua 5.4.8 time in the matched 2026-09-08 snapshot at c85ea0dd; the padding bands appear below). The mitigations, in order: typed arrays for the grids, parallel_transform for the bulk stages (it roughly halved GLOOM's dominant stage), and binding the one innermost loop to C++ if the budget still doesn't close. Full game sim is not the problem: DOOM's entire playsim ticks in under half a millisecond on the VM.
    • Per-execute class redefinition. Re-executing class declarations pays hot-reload bookkeeping every time (~250 µs for a 30-line class script, both backends equally). Define classes once; per-frame scripts should call, not declare.

    Measured results​

    Three altitudes: the raw cost sheet for embedders, microbenchmarks against three rival runtimes, and complete games measured end-to-end. Sources are named per table.

    Two machines appear below; never compare a number from one with a number from the other. The report machine is a 2016-era 4-core/8-thread laptop: it produced docs/PERFORMANCE.md in July 2026, and the cost sheet, the dispatch regimes, the aliasing table, the parallel-scaling figures and the five-way GLOOM report all come from it. The reference machine is a current desktop-class 24-thread CPU: the head-to-head table, the GLOOM row and the DOOM rows were measured there, at a later build. It runs everything faster, and the VM's call path improved between the two runs, so the recursion gap reads ~4.5× against Lua here and ~6.7× in the report. Read ratios within one table.

    • VM compilation costs about one third of parsing (tiny: parse 3.8 µs, compile ~1.5 µs; 30-line: parse 67.5 µs, compile ~21 µs) and is cached (in the source-cache entry or the jaibite), so it amortizes by the 3rd–4th execution in every re-execution regime.
    • The interpreter's only durable win is genuinely unique, never-repeated small strings on a warm engine, worth 1.3–5 µs per execution, gone entirely at ~30 lines.
    • Class-heavy scripts see only ~4% VM advantage warm: per-execute class redefinition/hot-reload machinery costs the same on both.
    • The automatic jaibite disk cache turns file loads from parse-bound to IO-bound: a measured 535-line game file's load-and-run drops from 5.8 ms to 2.4 ms: the ~3.4 ms parse replaced by a sub-millisecond binary load (see jaibite for the mechanism).

    What the debugger costs​

    The debugger is designed to be free until a session attaches. The 1000-iteration hot-loop script from the cost sheet, report machine, min-of-3, µs per run:

    configurationinterpretervm
    no debugger constructed14947
    controller constructed, no session14846
    session enabled, no breakpoints14850
    session enabled, breakpoint in a cold file14651
    session enabled, breakpoint whose line collides with the hot statement16564

    The two disabled rows sit on the pre-debugger band exactly; an armed session costs the VM ~10% (it detects statement edges per dispatch iteration); the only expensive row is the deliberate worst case: a breakpoint in another file whose line number matches the hot statement, one bounded string compare per collision.

    read-only compute, pass Creature& c6.24.81.0

    The structure-heavy version of the same story, on the node-aliasing BST benchmark (15 nodes): in-place & params are ~1.35× faster than the shared_ptr return-and-reassign shape (that delta is the shape, not a per-access penalty), and both are ~3.5× faster than naive by-value, which deep-copies subtrees at every recursion level.

    The five-way report is worth reading beyond the numbers: the same enemy brain is ~23 lines of coroutine or generator method in JaiScript, Lua, Squirrel, and Python. In ChaiScript, which has no coroutines, it is a 50-line hand-lowered state machine. Expressiveness parity is table stakes; the differentiators are speed and what the language lets you say directly.

    Style is near-free, and provably so. GLOOM exists in a second complete flavor, examples/gloom_idiomatic, a full rewrite in modern class-based style: subsystem classes, an enemy hierarchy with virtual coroutine brains, typed classes for the record types instead of string-keyed maps (examples/gloom_idiomatic/IDIOMATIC_COST.md). It produces bit-identical state and frame hashes to the flat original on both backends at every worker count, and measures within noise on the interpreter and ~4–7% behind on the VM. The moral for code review: choose the architecture you want to maintain; the per-pixel hot stages are held to the flat shape by the parallel-admission rules either way, and that is where the time goes.

    Measuring yourself​

    Build the test executable with the benchmark suites enabled (-DJAISCRIPT_ENABLE_BENCHMARKS=ON at configure time, Release; see docs/BUILD.md, "Comparison benchmarks", for where the rival runtimes' sources go) and then:

    jaiscript_tests "Performance Benchmarks" --verbose [--backend=vm]
jaiscript_tests "Squirrel Performance Comparison" --verbose
jaiscript_tests "Lua (sol2) Performance Comparison" --verbose   # needs the Lua + sol2 checkout

    Measure Release builds only. A Debug build of the engine runs script ~25–40× slower, and no number taken from one means anything. Run min-of-3 and compare medians; the integer-µs harness cannot resolve sub-µs changes (use a dedicated ns micro-bench for those). For end-to-end embedding costs (engine create, parse, compile, warm dispatch, crossover points) the methodology and full tables are in docs/execution_mode_metrics.md, summarized in the cost sheet above. The whole-game harnesses that ship reproduce too: jai_gloom.exe --smoke and jai_demoreel --smoke run each game headless on both backends and print ms per tick or frame next to the parity hashes (each example's README has the flags).
