Performance Notes​

Honest numbers, with their sources. The benchmark suites live in source/tests/performance/ (Release BENCHMARKS config, -DJAISCRIPT_ENABLE_BENCHMARKS=ON): benchmark_suite.cpp ("Performance Benchmarks"), squirrel_comparison.cpp, sol2_comparison.cpp (Lua 5.4), and chaiscript_comparison.cpp. Two standing caveats from the project's own docs: the harness reports integer µs/iteration with ±50% run-to-run variance (compare min-of-3, don't trust ±1 µs deltas), and all comparative numbers below are from the VM-perf branch, July 2026, MSVC x64 Release.

Single-operation costs (order-of-magnitude intuition)​

From docs/PERFORMANCE.md (Release, interpreter era — the VM is at or below these on everything today):

operationcost
single arithmetic op<1 µs
function call~2–4 µs
class creation~4–11 µs
method invocation~5–9 µs
hot loop, per iteration~45 ns (VM, post op_compound_fused: 1000-iteration loop ≈ 45 µs)
engine creation~40–65 µs (+ ~35–40 µs lazy backend init on first execute)
stdlib registration~130–215 µs

Warm dispatch costs are in the Backends chapter (docs/execution_mode_metrics.md): a warm repeated tiny script is ~0.6 µs on the VM (~0.38 µs via jaibite), 1.7–1.8× faster than the interpreter.

The comparison story​

From docs/why_jaiscript.md ("The receipts" / "The honest tradeoffs"), backed by the comparison suites:

  • vs Squirrel (squirrel_comparison.cpp): the VM wins 13 of 19 head-to-head benchmarks, loses 6 (13W/6L). Method invocation, factorial, and the hot loop flipped to wins during the VM-perf pass; the residual losses are deep recursion and parts of the loop family. Squirrel is characterized in the project notes as "the beatable one".
  • vs Lua 5.4 via sol2 (sol2_comparison.cpp): mixed — JaiScript wins trivial statements, range-for, map ops and null-checks; Lua's function calls are ~10× cheaper, which shows up as roughly 5× (docs' fib figure) to ~11× (suite worst case) on call-dense recursion microbenchmarks like naive fib. Lua is "the tough yardstick".
  • vs ChaiScript (chaiscript_comparison.cpp, BENCHMARK_BASELINE.md): 1.4–6.3× faster across the board (function calls 3.5×, class creation 5.3×, fib 5.8×) — and that baseline predates the VM work.

What's fast (and why)​

The VM-perf pass closed the interpreter/VM gap and then some; the machinery behind the numbers (all landed, both backends green):

  • Loops: counted-for compiles to dedicated opcodes (op_cfor_prep/back) with a generic bytecode fallback for exotic cases; scope elision skips per-iteration environment allocation (the original 7.7× hot-loop deficit was exactly this); environment-lookup inline caches kill the per-iteration hash lookups.
  • Fused superinstructions: op_binary_fused, op_fused_cmp_jump, and op_compound_fused collapse the common x += f * 2.0 / compare-and-branch shapes — the compound fusion alone took the comparison hot loop from 118 to 45 µs (−62%).
  • In-loop call frames: script calls no longer recurse natively — call records are pooled and pushed/popped inside the run loop; method calls dispatch flattened, with zero-copy argument binding from the stack window.
  • Thin values: script_value is 32 bytes (was 56), static-assert-gated, two per cache line — measured as layout/copy headroom rather than a benchmark step, and documented that honestly (docs/thin_value_rebaseline.md: all 44 benchmarks within noise at integer-µs resolution).
  • Cheap safety: the checked-overflow policy is branch-free on the wrap build and intrinsic-based (_mul128) on the checked build; the budget clock samples every 1024 ticks — neither shows up in hot-path measurements.
  • Type-ladder dividends: typed (int) and inferred (auto) locals ride slot-based storage and typed fast paths; var stays fully dynamic and costs accordingly.

What's slower (and the plan)​

  • Call-dense recursion is the one structural gap vs Lua (docs/why_jaiscript.md: "~5× on a fib microbenchmark"; the sol2 suite's worst call-dense cases run higher). The project's diagnosis (VM-perf branch notes): opcode counts are at parity with Lua (~7 ops per fib call); the cost is per-call frame setup — structural, not micro. The committed fix is the flat-stack / register-window VM rewrite — docs/why_jaiscript.md describes it as "on the roadmap, not a hope"; Squirrel's same-architecture calls demonstrate the headroom. Until it lands: game scripts that are loop- and method-shaped see a small-to-none gap; avoid deep naive recursion in per-frame hot paths.
  • Value semantics copies: passing a big structure by value deep-copies it. The idiom is & parameters for anything heavy — the by-ref BST benchmark runs ~3× closer to Lua than the by-value variant (the remainder is the same call-cost story; the by-value number is kept in the suite as the honest feature-cost figure).
  • Class-heavy scripts: per-execute class redefinition/hot-reload bookkeeping dominates medium class scripts (~250 µs for the 30-line metric script) equally on both backends — batch class definitions once, don't re-execute them per frame.

Measuring yourself​

# Release BENCHMARKS build, then:
jaiscript_tests.exe "Performance Benchmarks" --verbose [--backend=vm]
jaiscript_tests.exe "Squirrel Performance Comparison" --verbose
jaiscript_tests.exe "Lua (sol2) Performance Comparison" --verbose   # needs HAVE_SOL2/lua checkout

Run min-of-3 and compare medians; the integer-µs harness cannot resolve sub-µs changes (use a dedicated ns micro-bench for those — Source/JaiScript/CLAUDE.md). For end-to-end embedding costs (engine create, parse, compile, warm dispatch, crossover points) the methodology and full tables are in docs/execution_mode_metrics.md, reproduced in the Backends chapter.
