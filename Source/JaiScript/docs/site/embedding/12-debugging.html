Debugging JaiScript​

JaiScript ships a step-debugger core — set breakpoints, pause a running script, inspect and edit variables, step, and resume — plus a VS Code extension for syntax highlighting. This page shows what works today and how to drive it by hand.

Status (phase 3.2 — VS Code attach works). Three pieces work right now on the interpreter backend: (1) editor syntax highlighting; (2) the debugger core driven from C++; and (3) the DAP debug_connector — a dependency-free TCP server that lets VS Code attach and stop on breakpoints you click in the gutter, step (over/into/out), see the stop location, and read in-scope variables. Still to come: a multi-frame call stack, live variable editing / evaluate, conditional breakpoints, and the VM backend hook. The full design is in docs/DEBUGGER_DESIGN.md.

Syntax highlighting (VS Code)​

The extension lives in Source/JaiScript/tools/vscode-jaiscript/. It highlights .script, .jai, and .jaibite files — the full keyword set, the int/auto/var type ladder, function/lambda/class, backtick template strings with ${expr} interpolation, all operators (including <=> and ?.), numeric literals, and the stdlib builtins. The grammar is generated straight from the real lexer's keyword table, so it stays truthful (e.g. int64 is not a keyword and is deliberately not highlighted as one).

Load it the quickest way — open the extension folder in VS Code and press F5 to launch an Extension Development Host, then open any .script file:

shell
code Source/JaiScript/tools/vscode-jaiscript
# in the new window: press F5  ->  "Extension Development Host" opens
# open any Assets/**/main.script  ->  it is highlighted

To install it persistently instead, package it to a .vsix and install that:

shell
cd Source/JaiScript/tools/vscode-jaiscript
npm install
npx vsce package                       # produces jaiscript-*.vsix
code --install-extension jaiscript-*.vsix

Syntax highlighting is entirely standalone — it needs no engine build and no running app. (The extension also declares a jaiscript attach debug type for later; it is inert until the debug_connector lands.)

Attach from VS Code​

The jai::debug_connector is a self-contained DAP server: it speaks the Debug Adapter Protocol directly on a raw OS socket (WinSock / BSD sockets — no asio, no Node adapter, no external tool), runs on its own thread, and drives the engine's debugger(). VS Code's built-in DAP client connects straight to the port. One line of host code turns it on:

C++
#include <jaiscript/debug/connector.hpp>

// One connector per engine (typical). The engine keeps it alive and stops it — joining
// its thread and detaching the controller — before teardown, so a paused script can
// never wedge the host. The jai::debug::listen() convenience builds the connector, attaches
// it, and returns it (the whole host-side wiring in one line):
auto conn = jai::debug::listen(*eng);                 // default port jai::debug::default_port (52472)
// auto conn = jai::debug::listen(*eng, 40000);       // custom port
// eng->set_debug_connector(nullptr);                 // detach + release
//
// listen() is exactly this, if you want to hold the pieces yourself:
// eng->set_debug_connector(std::make_shared<jai::debug::debug_connector>(52472));

It is compiled only when the JAISCRIPT_ENABLE_DEBUGGER CMake option is on (the default for desktop dev/editor builds; turn it off for shipping / mobile and no socket code is built at all). Then, in VS Code, add an attach configuration and press F5 while the host is running:

.vscode/launch.json
{
  "version": "0.2.0",
  "configurations": [
    { "type": "jaiscript", "request": "attach", "name": "Attach to JaiScript",
      "host": "127.0.0.1", "port": 52472 }
  ]
}

Set breakpoints in the gutter of your .jai/.script file, attach, and the running engine stops there — you get the stop location highlighted, step over/into/out, continue, pause, and the Variables pane showing in-scope locals (read-only for now).

Breakpoints bind by file path. A node only carries a real path if the engine parsed it with one — so run gameplay scripts through execute_file(path, vars) or import (both stamp every node with the file's std::filesystem::canonical() path), not the bare execute(source) (which stamps "<script>"). The connector normalizes the path VS Code sends to the same canonical form before matching, so a breakpoint binds regardless of drive-letter case or forward/backslashes — the two spellings don't have to be byte-identical. A .jaibite unit debugs against its original .jai source unchanged — it round-trips the source path per node. See jaibite and the filename-plumbing note in the design doc.

Try it: the example hosts​

All three bundled demos (examples/roguelike, examples/crawler, examples/demoreel) accept --debug: it forces the interpreter backend (the one with the hook) and stands up the connector via jai::debug::listen(). The connector is tied to the engine's lifetime — it listens for the whole run, so you can attach (and detach and re-attach) at any time; breakpoints you set bind on the next statement. Open Source/JaiScript in VS Code (the workspace ships a .vscode/launch.json with the Attach to JaiScript config on port 52472), then:

shell
jai_rogue.exe --debug            # boots immediately; listening on 127.0.0.1:52472 the whole run
# in VS Code, whenever you like: F5 (Attach to JaiScript) -> set breakpoints in scripts/*.jai
jai_rogue.exe --debug-wait       # same, but HOLD boot until you attach + press Enter
                                 #   (use this to catch boot-time code: dungeon gen, class init)
jai_rogue.exe --debug-port 40000 # attach on a different port

The roguelike and crawler load their scripts with import, so every scripts/*.jai node already carries a canonical path. The demoreel normally concatenates every scene into one precompiled .jaibite unit (stamped "<script>" — nothing to bind); under --debug it instead loads each scene through execute_file on a single interpreter engine, so scenes/*.jai breakpoints bind (TAB backend-swap is disabled in that mode, since the VM has no hook yet).

Under the hood this is the same wire protocol proven by the Debugger Connector foundry suite (source/tests/debug/debugger_connector_tests.cpp), which drives a real loopback socket through the whole loop — handshake → setBreakpoints → run → stopped → stackTrace → scopes → variables → stepIn/next → continue — with no editor in the loop.

The debugger core (C++ API)​

Every engine owns a lazily-created jai::debug::controller, reached with engine->debugger() (include/jaiscript/debug/controller.hpp). It is transport-agnostic: the same object a future DAP socket will drive, you can drive directly today.

The essential contract: a script runs on one thread and blocks at a breakpoint; a different thread drives it and inspects state. The controller's control-side calls (breakpoints, resume, step) are safe from any thread; inspection (reading/editing variables) must run on the parked script thread, which you arrange by handing the controller a closure via post_command().

C++
#include <jaiscript/core/engine.hpp>
#include <jaiscript/debug/controller.hpp>
#include <thread>

auto eng = jai::engine::make();          // interpreter backend (the one with the hook today)
auto& dbg = eng->debugger();

// 1. React to stops. Fires ON the script thread the instant it parks.
dbg.set_on_stopped([&](const jai::debug::stop_info& si) {
    // si.reason is "breakpoint" | "step" | "pause";  si.file / si.line / si.depth
    // Signal your driver thread here (a condition_variable, a queue, ...).
});

// 2. Set breakpoints and arm the session. A script run via execute(src) is attributed
//    to "<script>"; one run via execute_file(path) is attributed to that path — so key
//    breakpoints on whichever file name the script carries.
dbg.set_breakpoints("<script>", {3});
dbg.set_enabled(true);                   // also suspends the wall-clock budget while attached

// 3. Run the script on its own thread — it will block at line 3.
std::thread script([&] {
    eng->execute("var x = 1;\n"         // line 1
                 "var y = 2;\n"         // line 2
                 "var z = x + y;\n");   // line 3  <- stops BEFORE this runs
});

When it stops, inspect and steer it from your driver thread. Reads run on the parked thread via post_command; stepping and resuming are direct calls:

C++
// ...after your on_stopped fired and you know it is paused (dbg.is_paused() == true):

// Inspect: the closure runs on the parked script thread, against live state.
dbg.post_command([&] {
    jai::script_value x = dbg.get_variable("x");   // 1  (line 1 ran; line 3 hasn't)
    // dbg.set_variable("x", eng->make_value(41)); // edit it live if you like
});

// Step / continue (all safe from the driver thread):
dbg.step_into();   // stop at the next statement, any depth
dbg.step_over();   // next statement at this depth or shallower
dbg.step_out();    // next statement shallower than this one
dbg.resume();      // continue until the next breakpoint / completion

script.join();

The full, runnable version — breakpoint → read a variable → step → resume, plus a disconnect-safety case — is the Debugger suite in source/tests/debug/debugger_tests.cpp. Run it with jaiscript_tests.exe "Debugger".

How it works​

  • The hook. The interpreter tests one plain cached pointer per statement (at dispatch_stmt/dispatch_decl); with no session enabled that predictable branch is the hook's entire cost — no atomics, no locks, no lookups on the statement path, ever. Transport-side changes (attach, breakpoint edits, pause) are pulled into the script thread's cache only at its debug sync points: execute() entry and the same every-1024-ticks sampling the script-timeout clock uses.
  • Breakpoints live in a published snapshot the script thread caches locally; per statement they filter through an 8 KB line bloom, so with a session attached and no breakpoint on a statement's line the cost stays a couple of branches.
  • Park & pump. On a stop the script thread blocks in the hook on one mutex + one condition variable (predicate-guarded, so a resume racing the stop is never lost). While parked it drains posted closures — that is how the other thread inspects live environment state without ever touching engine data itself.
  • Stepping is computed from call-stack depth: into = next statement any depth; over = depth ≤ the stop; out = depth < the stop.
  • Budget. While a session is armed the interpreter skips wall-clock deadline checks (a script paused at a breakpoint is never killed by the 1 s cap) and re-arms a fresh deadline the moment the session ends.
  • detach() force-resumes a parked thread and disarms — the safety valve for a client disconnect or app shutdown, so a paused script can never wedge the host.

Performance notes. The debugger is designed to cost nothing when you are not using it, and almost nothing when you are: with no debugger constructed, with a connector listening but no client, with a session attached and no breakpoints, and with breakpoints only in cold files, the hot-loop benchmark is flat within run-to-run noise (~145 µs/iteration in every configuration; both backends hold their pre-debugger bands). The one measurable case is a breakpoint whose line number collides with a hot statement's line in another file (~+10%, bounded by one string compare per collision). Consequences of the sync-point design: a breakpoint set or a pause requested mid-execution takes effect within ~1024 statements or at the next execute(), whichever comes first — stepping is exact and immediate, since the step state is re-synced at every stop. The full cost model is in docs/DEBUGGER_DESIGN.md.

Today this is wired on the interpreter backend only; drive debugged scripts with jai::engine::make() (the default) or set MV_SCRIPT_INTERPRETER=1 in Bindstone. The VM carries a no-op stub of the same hook so wiring is identical when its statement-boundary hook lands.

What's next​

  • Multi-frame call stack — the connector reports the top frame today; walking the interpreter's call_stack_ gives the full stack in the editor's Call Stack pane.
  • Live variable editing + evaluate — setVariable routed through the int/auto type ladder, and REPL/watch expression evaluation on the parked frame (watch/hover read-only by convention).
  • Conditional breakpoints + logpoints.
  • VM backend hook — statement-boundary stops in the bytecode VM (the backend Bindstone ships), naming a stopped frame's locals lazily via the interner's reverse lookup.

The concurrency & lifecycle contract these build on — and the reasons each corner matters — is documented in full in docs/DEBUGGER_DESIGN.md.
