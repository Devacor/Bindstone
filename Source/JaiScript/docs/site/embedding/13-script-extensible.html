Script-Extensible Objects: extend​

A script class can derive a bound C++ class, and the script decides which object becomes which class. The host constructs and owns its objects exactly as before; a script hands one of them a class with extend(object, Class), and from that moment the object is that class everywhere — typed fields, overrides, methods — no matter which road brings it back into script. This chapter covers the script surface, the one-line host surface, who owns what, and how it serializes. Every example below is taken from source/tests/serialization/polymorphic_serialization_tests.cpp and runs on both backends; the mechanism is specified in docs/script_extensible.md.

One object, one identity​

The shape this exists for is a game whose C++ spawns creatures and whose scripts define what each kind of creature does. C++ never names a script class; it hands the creature over and the script extends it:

jaiscript
class Voidling : ServerCreature {
    int chompCount = 0;
    double blinkCooldown = 0.0;
    bool tick(double dt) override { blinkCooldown = blinkCooldown - dt; return false; }
}

// the host's three hooks: it passes the C++ creature, the script says what it becomes
self.spawn  = [=](var& creature) -> void { extend(creature, Voidling).spawn(); };
self.update = [=](var& creature, double dt) -> void { creature.update(dt); };
self.death  = [=](var& creature) -> void { creature.death(); };

After extend, every road back into script — a bound method returning shared_ptr<Creature>, a signal argument, a container element, a serialized shared_ptr<Base>, the host's next update call — hands script the Voidling, not a sliced view of its base. That is C++'s own rule, "a base pointer to a derived object is the derived object", carried across the boundary. The object is a hybrid: one script instance that owns or references the C++ object through a private _cpp_object field and carries the script layer (fields, overrides) on top.

extend(object, Class)​

extend is an engine-core builtin (every engine has it, sandboxes included). Class is the bare class name — its constructor value carries the definition — or a string. It works in place: the instance the handle already holds is re-classed where it stands, so nothing needs rebinding and every other handle to the same object follows.

jaiscript
class Voidkin : Creature {              // Creature is a bound C++ class
    int chomp = 3;
    string speak() override { return "voidkin"; }
}
class Voidspawn : Voidkin {
    int fangs = 1;
    string speak() override { return "voidspawn"; }
}

extend(raw, Voidkin);                    // raw arrived as a plain C++ handle; now it IS a Voidkin
raw.chomp = 17;
print(extend(raw, Voidkin).chomp);      // idempotent: the same class returns the live layer
print(extend(raw, "Voidkin").chomp);    // a string names the class too

extend(raw, Voidspawn);                  // re-derive in place
print(raw.chomp, " ", raw.fangs, " ", raw.speak());
output
17
17
17 1 voidspawn

The rules, all pinned by tests:

  • The class must derive the object's C++ class (through any chain of script classes). Anything else is refused, naming both classes.
  • Same class: no-op. The current layer is returned.
  • Another class: re-derive. Every field both classes declare keeps its value (chomp above), the new class's own fields take their initializers (fangs), the new overrides dispatch, and fields only the old class declared stay reachable. No constructor runs — field initializers do, in declaration order, base first — so a class meant for extension needs no constructor.
  • Every handle follows. A handle taken before the extend resolves to the layer on its next member access: reads, writes, getters, setters and bound methods all reach it.
  • Pure script objects re-derive too. extend(p, Pt3) on a script-only instance re-classes it in place under the same rule (Pt3 must derive p's class).
  • Refusals are catchable in script (try { extend(x, Wrong); } catch (e) { ... }) and thrown from the C++ entry point.

Write it as a statement — extend(kin, Voidling); kin.chompCount = 1; — or chain it. A var q = extend(p, C) binding follows the language's value-semantics rules for call results; the object p holds is already the re-classed one either way.

Host side: script_extensible and engine::extend​

Every property_owner is script-extensible for free: it derives the jai::script_extensible mixin, a 32-byte slot that lets the object carry its own layer back to script (a type with nothing to reflect can derive the mixin directly; a type that can derive nothing still works through an engine-owned lookup). Under multiple inheritance the first extensible base's slot is the one used, re-exported as jai_script_slot(). The host surface is small:

C++
auto creature = std::make_shared<Creature>();          // C++ constructs and owns, as always

script_value layer = eng->extend(creature, "Voidkin");  // the same thing the builtin does
eng->add_global_extended("hero", creature, "Voidkin");    // extend-on-bind: handed over already extended

std::shared_ptr<class_instance> live = eng->script_layer(*creature);   // the live layer, or null
std::string state = creature->script_layer_to_json();   // {"$type":"Voidkin","$script":{"chomp":17}}
creature->script_layer_from_json(state);                 // hydrate in place (re-derives on another $type)

std::string fields = eng->script_layer_detach(creature); // the fields as JSON; the object carries no layer now

Nothing is registered, cast, keyed, or looked up by hand, and C++ never bakes a class name into a binding: engine::extend exists for hosts that want it, but the idiomatic shape keeps the choice in script.

Ownership​

Ownership follows creation, and neither direction cycles:

  • A hybrid the script constructed (Voidkin()) owns its C++ object; the object's slot only points back.
  • An object that was extended owns its layer for its lifetime. The layer references the object without owning it (a raw pointer for member access, a weak pointer for shared_ptr extraction), so the host stays free to destroy the object whenever it likes. If a script still holds the layer when the object dies, the layer is retired: its own script fields stay readable, but any C++ member access reports instead of dangling.
  • A type without the slot cannot own anything, so its extended layers are engine-owned (and keep the object alive) until script_layer_detach.

Copies follow the C++ base. Assignment of a hybrid (var b = a;) deep-copies — a copyable base copies its C++ object too, giving two identities — while a hybrid over a base without a copy function is nocopy automatically, exactly as a derived class of a nocopy script class is. By-value capture ([=]) shares a hybrid, like any engine object.

Serialization​

A hybrid serializes as itself. Through any C++ archive path — a shared_ptr<Base> field, a container, a save file — the writer emits $type = the script class name, $script = the script-level fields, and $val = the C++ base's ordinary payload; the reader rebuilds the C++ object through the base's registered load, extends it with the script class, hydrates the fields, and calls post_load(self, 1) if the class defines one. JSON and binary, back-references included, and the script-level to_json(v) / from_json(s) do the same for a script value. Because extension runs field initializers before hydration, a field that was never written during play still loads with its declared default.

C++
std::shared_ptr<Creature> original = eng->execute("v").as<std::shared_ptr<Creature>>();
auto loaded = roundtrip_binary(*eng, original);           // a fresh object...
eng->script_layer(*loaded) != nullptr;                    // ...carrying its Voidkin layer   (verified)

Moving a layer between engines​

A layer belongs to exactly one engine (its symbols, its class definition). Extending an object in engine B while engine A holds its layer moves it: the fields travel by name, the new layer is hydrated in B, and A's layer is retired. For slot-carrying types that is one call — b->extend(obj, "Voidkin"); a type without the slot needs the explicit pair b->extend(obj, "Voidkin", a->script_layer_detach(obj)), since no engine can see into another's lookup. Layers are movable, never shared between threads — the same rule every script value follows.

Errors and cost​

Inside the engine every refusal is an error code — extend_rejected (the class does not derive the object's class, the argument is not a class, arity) and script_layer_retired (a detached, moved, or outlived layer reached for its object) — so script catches them like any runtime error; the C++ engine::extend throws at its boundary.

The lookup that hands script the layer is a pointer read on the object's slot; it replaces the wrapper the boundary used to allocate on every crossing. On the Bindstone arena pilots (three 150-second matches), the class-based creature scripts run 4–9% faster than the same logic kept in host-side variable maps, with byte-identical outcomes.
