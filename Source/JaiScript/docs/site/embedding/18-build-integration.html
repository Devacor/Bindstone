    Building JaiScript into a Host​

    JaiScript has no dependencies and builds with any C++20 compiler; MSVC 19.51 (Visual Studio 18), Clang 20 and GCC 16 are the verified ones. This page gives each way into a project in full: CMake, Visual Studio's MSBuild, Xcode, and an installed package. The quickstart has the short version of each.

    What every build needs​

    SettingValueWhy
    Sourcessource/jaiscript.cpp, or every .cpp under source/implementation/ (never both)The library is compiled with your program; see One file or per file.
    Include pathinclude/Every header is included as <jaiscript/...>.
    Language standardC++20The headers are written in C++20.
    Exceptions and RTTIon (every compiler's default)Errors reach the host as exceptions, and bound classes are matched by type.
    MSVC/bigobj; /EHsc and /permissive- (the defaults of a new Visual Studio project)The binder's templates overflow the default object-file section limit, in your files as well as the library's.
    GCC and Clang-ffp-contract=offKeeps the compiler from fusing a*b+c into one instruction, so floating-point results match on every platform and both backends.
    MinGW GCC-Wa,-mbig-objThe COFF counterpart of /bigobj.
    Windows librariesws2_32The debugger's socket transport. MSVC and clang targeting MSVC pick it up from the source; a GNU linker needs it named.
    Optional defineJAISCRIPT_ENABLE_DEBUGGERCompiles in the debugger's socket transport for VS Code attach (Debugging). Leave it out for shipping and mobile builds. Define it for every file or for none.

    Compile JaiScript's files with the same settings as yours: the same runtime library, the same NDEBUG and the same defines. Setting them once at the project level does that. A mismatch changes class layouts between your code and the library and fails at run time, typically as an assertion in strong_ptr.hpp.

    One file or per file​

    source/jaiscript.cpp includes every implementation file, so adding that one file adds the whole library. It is the simplest route and the right default when you use JaiScript without changing it: the library compiles as one unit, once, and stays built.

    The files under source/implementation/ are the same library split into about forty units. Add them all instead (a wildcard does it) when you work on JaiScript itself or want the library to compile in parallel: an edit to one implementation file rebuilds only that file. Turn on parallel compilation (MSBuild's /MP, Ninja and Xcode by default) to get the benefit. Adding both sets defines everything twice.

    CMake​

    The library is one CMake target, JaiScript::jaiscript. Linking it brings everything in the table above.

    As a subproject. Put the JaiScript folder (the one holding its top-level CMakeLists.txt) inside your project; a copy elsewhere takes a binary directory as well, add_subdirectory(path/to/JaiScript jaiscript). As a subproject only the library builds (the runner, tests, examples and language server stay off) and its MSVC runtime follows yours. A complete host:

    CMakeLists.txt
    cmake_minimum_required(VERSION 3.20)
project(my_game CXX)
add_subdirectory(JaiScript)
add_executable(my_game main.cpp)
target_link_libraries(my_game PRIVATE JaiScript::jaiscript)
    shell
    cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
build/my_game

    With FetchContent. The same target, fetched at configure time instead of copied in:

    CMakeLists.txt
    include(FetchContent)
FetchContent_Declare(jaiscript GIT_REPOSITORY https://github.com/Devacor/JaiScript.git GIT_TAG master)   # or a release tag
FetchContent_MakeAvailable(jaiscript)
target_link_libraries(my_game PRIVATE JaiScript::jaiscript)

    Options set before the add_subdirectory or FetchContent_MakeAvailable (or with -D) turn the tools back on: JAISCRIPT_BUILD_RUNNER, JAISCRIPT_BUILD_TESTS, JAISCRIPT_BUILD_EXAMPLES, JAISCRIPT_BUILD_LSP. JAISCRIPT_ENABLE_DEBUGGER=OFF compiles the debugger's socket code out.

    Visual Studio (MSBuild)​

    In the IDE. Add JaiScript\source\jaiscript.cpp to the project (Add → Existing Item). Then open the project's Properties, choose All Configurations and your platform, and under C/C++:

    • General → Additional Include Directories: add the JaiScript\include folder, for example $(SolutionDir)JaiScript\include.
    • Language → C++ Language Standard: ISO C++20 Standard (/std:c++20). Leave Conformance mode at Yes (/permissive-).
    • Command Line → Additional Options: /bigobj.
    • Code Generation → Enable C++ Exceptions: Yes (/EHsc), the default.
    • Preprocessor → Preprocessor Definitions: add JAISCRIPT_ENABLE_DEBUGGER if you want VS Code attach.

    For the per-file route, add the .cpp files under JaiScript\source\implementation instead of jaiscript.cpp, and set General → Multi-processor Compilation to Yes.

    In a property sheet. The same settings fit in one file a project imports, which keeps them in source control and out of the project file. Save this beside your project as jaiscript.props:

    jaiscript.props
    <?xml version="1.0" encoding="utf-8"?>
<Project xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
  <PropertyGroup>
    <JaiScriptDir Condition="'$(JaiScriptDir)'==''">$(MSBuildThisFileDirectory)JaiScript\</JaiScriptDir>
    <JaiScriptPerFile Condition="'$(JaiScriptPerFile)'==''">false</JaiScriptPerFile>
  </PropertyGroup>
  <ItemDefinitionGroup>
    <ClCompile>
      <AdditionalIncludeDirectories>$(JaiScriptDir)include;%(AdditionalIncludeDirectories)</AdditionalIncludeDirectories>
      <LanguageStandard>stdcpp20</LanguageStandard>
      <ConformanceMode>true</ConformanceMode>
      <ExceptionHandling>Sync</ExceptionHandling>
      <AdditionalOptions>/bigobj %(AdditionalOptions)</AdditionalOptions>
      <PreprocessorDefinitions>JAISCRIPT_ENABLE_DEBUGGER;%(PreprocessorDefinitions)</PreprocessorDefinitions>
    </ClCompile>
  </ItemDefinitionGroup>
  <ItemGroup Condition="'$(JaiScriptPerFile)'!='true'">
    <ClCompile Include="$(JaiScriptDir)source\jaiscript.cpp" />
  </ItemGroup>
  <ItemGroup Condition="'$(JaiScriptPerFile)'=='true'">
    <ClCompile Include="$(JaiScriptDir)source\implementation\**\*.cpp" />
  </ItemGroup>
</Project>

    Import it in the .vcxproj after Microsoft.Cpp.props:

    my_game.vcxproj (excerpt)
    <Import Project="$(VCTargetsPath)\Microsoft.Cpp.props" />
<Import Project="jaiscript.props" />

    A Directory.Build.props can carry the ItemDefinitionGroup for every project in a folder; keep the ClCompile items in the one project that should compile the library. msbuild my_game.vcxproj /p:Configuration=Release /p:Platform=x64 builds it from a developer prompt, and /p:JaiScriptPerFile=true /p:MultiProcessorCompilation=true selects the per-file route.

    Xcode​

    Add JaiScript/source/jaiscript.cpp to your target (it appears under Build Phases → Compile Sources), or the files under source/implementation/ for the per-file route. Then set, in the target's Build Settings (the setting name in parentheses is what an .xcconfig uses):

    Build settingValue
    Header Search Paths (HEADER_SEARCH_PATHS)$(SRCROOT)/JaiScript/include
    C++ Language Dialect (CLANG_CXX_LANGUAGE_STANDARD)C++20 (c++20)
    C++ Standard Library (CLANG_CXX_LIBRARY)libc++ (the default)
    Enable C++ Exceptions (GCC_ENABLE_CPP_EXCEPTIONS)Yes (the default)
    Enable C++ Runtime Types (GCC_ENABLE_CPP_RTTI)Yes (the default)
    Other C++ Flags (OTHER_CPLUSPLUSFLAGS)$(inherited) -ffp-contract=off
    Preprocessor Macros (GCC_PREPROCESSOR_DEFINITIONS)Release: NDEBUG=1. Add JAISCRIPT_ENABLE_DEBUGGER=1 to a desktop development build for VS Code attach; leave it out on iOS.

    Xcode's Release configuration does not define NDEBUG by itself; without it the library's internal assertions stay on and cost speed.

    Debug and Release​

    • A Debug build checks the library's internal invariants with assertions and runs a few times slower than Release. Profile and measure Release builds.
    • Release defines NDEBUG. In CMake and in Visual Studio's Release configuration that is automatic; in Xcode add it (above).
    • MSVC whole-program optimization (/GL with /LTCG) applies to JaiScript like any other code: it speeds the VM up a few percent and makes every Release link much slower. A CMake build of the library alone turns it off with JAISCRIPT_LTCG=OFF.
    • Deeply recursive scripts need native stack. A host thread that runs scripts with deep recursion wants a larger stack than the platform default (the library's own test runner links 128 MB on Windows); the engine raises a catchable error instead of crashing when the stack runs low.

    An installed package​

    Build and install the library once per configuration (Debug and Release share a prefix; the Debug library is jaiscriptd), then find it from CMake:

    shell
    cmake -S JaiScript -B build-jai -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=C:/libs/jaiscript -DJAISCRIPT_LTCG=OFF -DJAISCRIPT_BUILD_TESTS=OFF -DJAISCRIPT_BUILD_EXAMPLES=OFF -DJAISCRIPT_BUILD_LSP=OFF
cmake --build build-jai
cmake --install build-jai
    CMakeLists.txt
    cmake_minimum_required(VERSION 3.20)
project(my_game CXX)
find_package(JaiScript 0.5 CONFIG REQUIRED)        # configure with -DCMAKE_PREFIX_PATH=C:/libs/jaiscript
add_executable(my_game main.cpp)
target_link_libraries(my_game PRIVATE JaiScript::jaiscript)
set_property(TARGET my_game PROPERTY MSVC_RUNTIME_LIBRARY "${JaiScript_MSVC_RUNTIME_LIBRARY}")

    The last line matters on MSVC. A standalone JaiScript build uses the static runtime (/MT, /MTd) unless you pass CMAKE_MSVC_RUNTIME_LIBRARY, while a CMake project defaults to the DLL runtime; the package records the runtime its library was built with in JaiScript_MSVC_RUNTIME_LIBRARY, and without the line the link fails with LNK2038: mismatch detected for 'RuntimeLibrary'. Linking a prebuilt library from another build system, compile your files with the definitions it was built with: its runtime, NDEBUG for a Release library, and JAISCRIPT_ENABLE_DEBUGGER unless it was configured off.

    The runner, for trying scripts​

    A standalone build of JaiScript builds the command-line runner as the target jaiscript_runner; its binary is jaiscript:

    shell
    cmake -S JaiScript -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build --target jaiscript_runner
build/bin/jaiscript hello.jai                   # run a file; no argument starts a REPL
build/bin/jaiscript --backend=interp --check=warn hello.jai

    The runner registers the whole standard library plus file and console functions, runs on the VM like every engine (the interpreter is one call away), and lifts the execution budget (--budget=N puts one back).

    The headers a host includes​

    C++
    #include <jaiscript/core/engine.hpp>              // engine, script_value, the error types
#include <jaiscript/core/dynamic_binder.hpp>      // dynamic_binder, convert_script_function
#include <jaiscript/stdlib/stdlib.hpp>            // jai::stdlib::register_all
#include <jaiscript/serialization/convenience.hpp> // jai::to_json / from_json / to_binary / from_binary
#include <jaiscript/core/engine_time.hpp>         // eng->time(): the clock scripts read
#include <jaiscript/debug/connector.hpp>          // jai::debug::listen (VS Code attach)

    <jaiscript/jaiscript.hpp> pulls the core, the binder and the archives in one include (not the standard library).
