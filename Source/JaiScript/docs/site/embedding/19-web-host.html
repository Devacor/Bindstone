    jaiweb: a Web Application Host​

    jaiweb serves a JaiScript program as a web application. It is a host like any other on these pages, built from the same engine calls: an HTTP/1.1 server, a request handed to one script function, the program's imports reached before every request, and SQLite bound as a class. Because the imports are reached per request, a saved edit applies to the next request with no restart, and an edit that fails its check is reported while the app keeps serving the code it had.

    The host lives in tools/jaiweb: the C++ (sockets, HTTP, SQLite) and the script library apps import (lib/web.jai and lib/session.jai). The library itself carries nothing web-specific.

    Running an app​

    The jaiweb CMake target builds bin/jaiweb beside the runner (option JAISCRIPT_BUILD_WEB, on by default). Point it at the app's entry file:

    shell
    jaiweb tools/jaiweb/examples/guestbook/app.jai
jaiweb: serving tools/jaiweb/examples/guestbook/app.jai on http://127.0.0.1:8080/ (files from .../guestbook/public)
GET / 200 1.21 ms
GET /style.css 200 0.31 ms (file)
POST /sign 303 2.40 ms
jaiweb: reloaded views.jai
GET / 200 1.87 ms

    Each request logs one line: method, path, status and time. Ctrl+C stops the server; the engine is destroyed with it, which closes every database.

    A first app​

    An app imports web.jai and defines Response handle(Request req). A Router is the usual body of handle:

    jaiscript — app.jai (under jaiweb)
    import "web.jai";

Database db = open_database("notes.db");        // relative to the app's folder
db.execute("CREATE TABLE IF NOT EXISTS notes (id INTEGER PRIMARY KEY, text TEXT NOT NULL)");

int requests;                                   // no initializer: the count survives every reload

Router routes = Router();
routes.get("/", (Request req) => {
    requests += 1;
    return html(`<h1>${requests} requests</h1>`);
});
routes.get("/notes", (Request req) => db.query("SELECT id, text FROM notes"));   // a value answers JSON
routes.post("/notes", (Request req) => {
    db.execute("INSERT INTO notes (text) VALUES (?)", req.form()["text"]);
    return redirect("/notes");
});
routes.get("/notes/:id", (Request req) => {
    var note = db.query_one("SELECT id, text FROM notes WHERE id = ?", req.param("id"));
    return note == null ? not_found() : json(note);
});

Response handle(Request req) { return routes.dispatch(req); }

    A handler answers a Response, a string (an HTML page), null (204 No Content) or any other value, which is sent as JSON. The checker sees the whole program before anything runs, so a misspelled field or a string passed where an int is declared fails the load with a listing, exactly as in any other host.

    Request and Response​

    Both are script classes in lib/web.jai, so their source is the reference and an app can read or extend them.

    RequestWhat it holds
    method, path, target, query_string, versionthe request line: path percent-decoded and without the query, target as it arrived
    query, cookies, paramsmap<string, string>: the parsed query (+ is a space), the Cookie header, the route's captures
    headers, header(name)names lowercased; header("Content-Type") reads any spelling
    body, form(), files(), json()the raw body; its urlencoded or multipart fields; its uploads as map<string, Upload> (filename, content_type, data, size(), save(path)); from_json of it
    cookie(name), param(name), remote_addr"" when absent; the peer's address
    ResponseWhat it does
    Response(), Response(status), Response(status, body)status, headers and body are plain fields
    header(name, value)sets a header
    set_cookie(name, value, options), clear_cookie(name)one Set-Cookie per call; the value is percent-encoded; options max_age, expires, path ("/"), domain, secure, http_only (true), same_site ("Lax")
    html(text), plain_text(text), json(value)a body with its Content-Type; each takes an optional status
    redirect(url)303 See Other by default, the answer to a form post
    file(path, content_type)a file streamed from disk, relative to the app's folder, typed by its extension unless one is given
    not_found(text)a 404

    The host adds the text helpers HTTP needs as functions: url_encode, url_decode, parse_query, parse_cookies, parse_multipart, http_date, content_type_for and random_token(bytes), a hex string from the operating system's secure random source; build_query(map) is script. Pages escape what visitors wrote with html_escape; the guestbook's views.jai writes its templates as functions returning backtick strings, with every visitor value passed through it.

    Routing​

    Router has get, post, put, patch, delete, any and add(method, pattern, handler). Routes match in the order they were added. /posts/:id captures one path segment as req.params["id"], /files/*rest captures the rest of the path. A HEAD request takes the GET route and is answered without its body; a path that only other methods match answers 405 with an Allow header; no match is a 404. before(filter) runs a filter ahead of every route: null lets the request through, anything else is the answer, which is where a sign-in check goes.

    SQLite​

    open_database(path) opens or creates a database file (relative to the app's folder; ":memory:" for a scratch one) and returns a Database, a C++ class bound with dynamic_binder. Copies of one share its connection, which closes with the last of them.

    jaiscript (under jaiweb)
    int changed = db.execute("UPDATE posts SET title = ? WHERE id = ?", title, id);
array<map<string, var>> rows = db.query("SELECT id, title FROM posts WHERE author = ?", author);
var post = db.query_one("SELECT * FROM posts WHERE id = :id", {"id": id});   // one map binds by name
int count = db.value("SELECT COUNT(*) FROM posts");
db.transaction(() => {
    db.execute("INSERT INTO posts (title) VALUES (?)", title);
    db.execute("INSERT INTO audit (what) VALUES (?)", "post");
});

    Parameters are always bound (?, ?NNN, :name, @name, $name), never spliced into the SQL, and the count must match the statement's. Values bind from int, float, bool, string and null; columns come back as int, float, string (TEXT, and a BLOB as its bytes) or null. Each SQL text is prepared once and kept until the database closes. A text of several statements given to execute runs them all, which suits a schema. transaction(fn) commits when fn returns and rolls back when it raises, then raises again; inside another transaction it is a savepoint. begin, commit, rollback, last_insert_id, changes, in_transaction, is_open and close are there too. Every SQLite failure is a catchable error carrying SQLite's message: SQLite error: no such table: posts. Files open in WAL mode.

    Sessions​

    lib/session.jai keeps sessions in a table of the app's database. The cookie carries only a 256-bit random id; the data stays on the server as JSON.

    jaiscript (under jaiweb)
    import "session.jai";

SessionStore sessions = SessionStore(db);

routes.post("/sign-in", (Request req) => {
    Session s = sessions.load(req);              // the visitor's session, or a new empty one
    sessions.rotate(s);                          // a fresh id once the visitor signs in
    s.set("user", req.form()["name"]);
    s.set("flash", "Welcome back.");
    Response r = redirect("/");
    sessions.save(s, r);                         // the row and the cookie, when the session changed
    return r;
});

    Session has get(key, fallback), has, set, erase and take (read once, for a message shown after a redirect). SessionStore has load, save, rotate, destroy and purge_expired; cookie_name, max_age and secure_cookie are fields.

    Hot reload​

    Before each request the host executes import("app.jai") with the engine's import check on every reach (Reloading from a running program). An unchanged program costs one stamp check per file. When a file has changed, the module is parsed and checked together with everything it imports, then runs as its own unit:

    • its functions and classes replace the old ones in place, and live instances migrate (Hot Reload);
    • its top-level statements run again, so a Router built with an initializer is rebuilt from the new code and every route reflects it;
    • a variable declared without an initializer (int requests;, map<string, var> cache;) keeps the value it holds.

    An edit that fails to parse or check is logged once with its listing, and the app answers every request with the code it had until the file is saved again:

    console
    jaiweb: the edit was rejected; serving the code the app had:
static check failed:
views.jai:7:25: error: cannot initialize 'n' declared 'int' with 'string'
    string footer() { int n = "three"; return "..."; }
                            ^
GET / 200 0.84 ms
jaiweb: reloaded views.jai
GET / 200 1.66 ms

    The library files reload the same way: an edit to web.jai applies to the next request.

    Static files​

    For GET and HEAD, a path that names a file under the static root is served before the app sees the request. The root is --root, or the app's public/ folder when it exists; a folder serves its index.html. A file is sent with a Content-Type from its extension, a weak ETag, Last-Modified and Cache-Control: no-cache, so a browser revalidates each time and sees an edited file on its next load (304 Not Modified otherwise). Files stream from disk in slices. Dot-files and paths that leave the root, percent-encoded or not, are never served.

    Errors, limits and the threading model​

    One thread runs the network loop and the script. The loop keeps every connection moving (reading, writing, streaming files) and hands complete requests to the script one at a time, so a slow handler delays the requests behind it. HTTP/1.1 and 1.0 are served with keep-alive and pipelining, bodies by Content-Length or chunked, and Expect: 100-continue.

    FailureAnswer
    a run-time error or an uncaught throw in a handler500; the error and its trace are logged, and the page shows them to a browser on the same machine only
    a handler that runs past --budget500 through the execution budget (Safety Rails); the engine serves on
    a body over --max-body (2 MiB by default)413 before the body is read
    a request head over 64 KiB431 (414 for a request line alone)
    a malformed request, both Content-Length and Transfer-Encoding400; another HTTP version is 505, another transfer coding 501
    a request that takes longer than --timeout to arrive, or a response to leavethe connection closes
    more than 512 open connections503

    A connection holds one response at a time: the next request is read once the last response has left, so a client that never reads cannot pile responses up. There is no TLS; a deployment puts a reverse proxy that terminates HTTPS (Caddy, nginx) in front and sets secure_cookie on the session store.

    Options​

    OptionMeaning
    --port Nthe port (default 8080; 0 picks a free one, named in the first line)
    --host ADDRthe IPv4 address to listen on (default 127.0.0.1; 0.0.0.0 for every interface)
    --root DIRthe static root (default: the app's public/ folder when it exists)
    --max-body Nthe largest request body, with K or M allowed (default 2M)
    --timeout Sseconds a request may take to arrive and a response to leave (default 30)
    --budget Sthe execution budget per request (default 30; 0 is unlimited)
    --backend vm|interp, --check strict|warn|offthe engine's backend and checker mode, as for the runner
    --allow-shutdownPOST /__jaiweb/shutdown from the same machine stops the server, for scripts and tests that drive it
    --quietno request log

    Every file function of the runner (read_file, write_file, list_dir and the rest) and the full standard library are registered too. tools/jaiweb/examples/guestbook is a complete app: templates, a form, a session, SQLite storage, a JSON API and a stylesheet. tools/jaiweb/tests/jaiweb_test.py starts the host on a free port and drives every behavior on this page over HTTP, on both backends.
