    Value Semantics & References​

    If you read only one chapter of this guide, read this one. The single most common ambush for a newcomer lives here: JaiScript copies by default, everywhere. Assignment copies. Function arguments copy. Even class instances copy. If you mutate a copy, the original never hears about it, and nothing warns you.

    The ambush: mutations on copies vanish silently​

    jaiscript
    auto a = [1, 2, 3];
auto b = a;          // assignment COPIES the array
b[0] = 99;
print("a[0] = {}  (the original is untouched)", a[0]);
print("b[0] = {}", b[0]);

function double_all(arr) {
    for (auto& x : arr) { x *= 2; }   // mutates the local COPY
}
auto nums = [1, 2, 3];
double_all(nums);                     // parameter passed BY VALUE
print("after double_all(nums): nums[0] = {}  <- mutation vanished!", nums[0]);
    output
    a[0] = 1  (the original is untouched)
b[0] = 99
after double_all(nums): nums[0] = 1  <- mutation vanished!

    This applies to class instances too. Unlike Python/JS/Lua/C#, objects are values:

    jaiscript
    class Point {
    int x = 0;
    void set(int v) { x = v; }             // methods mutate their own instance
}
auto p = Point();
p.x = 1;
auto q = p;          // class instances COPY on assignment too
q.x = 99;
print("p.x = {}  q.x = {}", p.x, q.x);

function try_mutate(o) { o.x = 77; }       // by-value param: mutation is lost
try_mutate(p);
print("after try_mutate(p): p.x = {}", p.x);

p.set(42);                                 // method calls DO mutate the receiver
print("after p.set(42):    p.x = {}", p.x);
    output
    p.x = 1  q.x = 99
after try_mutate(p): p.x = 1
after p.set(42):    p.x = 42

    So: methods mutate their receiver; free functions receive copies. When a mutation "doesn't stick", check whether you passed the object by value.

    Escape hatch 1: & reference parameters​

    Declare a parameter with & and the callee binds the caller's variable. Works with explicit types (int& x) and with auto& (any type):

    jaiscript
    function bump(int& x) { x += 1; }         // typed by-ref parameter
auto n = 41;
bump(n);
print("after bump(n): {}", n);

function fill(auto& arr, v) { arr.push(v); }   // auto& works for any type
auto items = [];
fill(items, "sword");
print("items.size() = {}", items.size());

class Hero { int hp = 10; }
function heal(auto& who) { who.hp += 5; }
auto h = Hero();
heal(h);                                   // & is how object mutations survive a call
print("h.hp = {}", h.hp);
    output
    after bump(n): 42
items.size() = 1
h.hp = 15

    Reference parameters survive pass-through chains, block and loop scopes, methods, globals, and recursion. The aliasing follows the value wherever the call takes it.

    Escape hatch 2: field and element lvalues as ref arguments​

    You can pass obj.field or arr[i] straight into a & parameter. Element references re-resolve through the container, so they stay correct even if the array reallocates its storage:

    jaiscript
    function bump(int& x) { x += 1; }
class Hero { int hp = 10; }
auto h = Hero();
bump(h.hp);                 // field lvalue passes by reference
print("h.hp = {}", h.hp);

auto arr = [5, 6, 7];
bump(arr[1]);               // array element lvalue passes by reference
print("arr[1] = {}", arr[1]);
for (int i = 0; i < 64; ++i) { arr.push(0); }   // force reallocation
bump(arr[1]);               // element refs re-resolve through the container
print("arr[1] after realloc = {}", arr[1]);
    output
    h.hp = 11
arr[1] = 7
arr[1] after realloc = 8

    Shrinking the array out from under an element reference stops the script with Reference to a removed array element rather than corrupting memory, on both backends. This one is not catchable: it is an invariant of the reference model, not a script error.

    Escape hatch 3: reference declarations (auto&)​

    auto& r = x; declares an alias. References chain, and element references survive reallocation just like ref params:

    jaiscript
    var v = 1;
auto& g = v;         // reference declaration: g aliases v
auto& h = g;         // references chain
h = h + 3;
print("v = {}", v);

var arr = [7, 8];
auto& x = arr[1];    // element reference
for (int i = 0; i < 64; ++i) { arr.push(0); }
x = 42;              // still writes through after the array reallocated
print("arr[1] = {}", arr[1]);
    output
    v = 4
arr[1] = 42

    References respect the type system, and builtin methods work through them. A write through an auto& bound to a typed array's element converts when compatible and rejects when not (exactly like writing to the element directly), and calling a string/array/map method through a reference mutates the referent in place:

    jaiscript
    array<int> nums = [1, 2, 3];
auto& e = nums[0];
e = 9.7;                       // converts to the element type, like any typed write
print("after e = 9.7: {}", to_json(nums));
try {
    e = "nope";                // incompatible writes are rejected through refs too
} catch (err) {
    print("caught: {}", err);
}
var s = "  hello  ";
auto& r = s;
r.trim();                      // string methods work through ref declarations
print("[{}]", s);
    output
    after e = 9.7: [9,2,3]
caught: Cannot assign 'string' to element of type 'int'
[hello]

    Escape hatch 4: range-for with auto&​

    jaiscript
    auto nums = [1, 2, 3];
for (auto x : nums) { x *= 2; }       // copies: original unchanged
print("after value loop: {}", nums[0]);
for (auto& x : nums) { x *= 2; }      // references: mutates in place
print("after ref loop:   {}", nums[0]);
    output
    after value loop: 1
after ref loop:   2

    Escape hatch 5: shared_ptr<T> (opt-in reference semantics)​

    When you want an object shared by handle (entity registries, cross-references), declare it shared_ptr<T>. Copies of the handle alias the same object:

    jaiscript
    class P { int x = 3; }
shared_ptr<P> sp = P();
auto alias = sp;
alias.x = 99;
print("sp.x = {} (shared!)", sp.x);
function poke(o) { o.x = 42; }
poke(sp);
print("after poke: {}", sp.x);
    output
    sp.x = 99 (shared!)
after poke: 42

    new P() is the direct spelling for a handle (shared_ptr<P> sp = P(); wraps a value the same way), and every copy of the handle shares the object. weak_ptr<T> observes a handle without owning it:

    jaiscript
    class P { int x = 3; }
shared_ptr<P> sp = P();
weak_ptr<P> w = sp;
print("expired: {}", w.expired());
auto l = w.lock();
l.x;
    output
    expired: false
== result: 3

    Note the guard rail: P p = P(); weak_ptr<P> w = p; raises at run time: a value has no shared owner to observe, so only a shared_ptr (or new P()) can seed a weak_ptr. A weak_ptr<P> field or static takes a shared handle the same way a declaration does.

    The handle keeps sharing inside a copy, exactly as a std::shared_ptr member does in C++. Copying a class instance, an array or a map copies every value member and element and shares every shared_ptr and weak_ptr one:

    jaiscript
    class Node { int v = 1; }
class Holder { shared_ptr<Node> link; Node own; Holder() { link = new Node(); own = Node(); } }
Holder a = Holder();
Holder b = a;          // b.own is a copy; b.link is the same Node as a.link
b.link.v = 5;
b.own.v = 50;
print(to_string(a.link.v) + " " + to_string(a.own.v) + " " + to_string(same_object(a.link, b.link)));
    output
    5 1 true

    The same holds for array<shared_ptr<Node>> and map<string, shared_ptr<Node>>: a copy of the container is a new container whose handles point at the old objects. Cloning through a handle is an explicit act: copy the object the handle names (Node fresh = a.link;, a value declaration from a handle) and wrap it again.

    Escape hatch 6: cast<T&> and cast<shared_ptr<T>>​

    cast comes in three forms, and the difference between them is exactly this chapter's subject: cast<T>(e) is a copy, cast<T&>(e) is a reference to the same object, cast<shared_ptr<T>>(e) is a handle sharing it. The reference form earns its place here as the strict-mode fix for a classic situation: a base-typed variable holding a derived object, and you need a member only the derived class declares.

    jaiscript
    class Base { int a = 1; }
class Derived : Base { int t = 9; }

Base h = Derived();          // a Base-typed slot; the object inside is still a Derived
// print(h.t);               // load error: no member 't' in class 'Base'
print("alias:        ", cast<Derived&>(h).t);   // cast<T&>: a reference to the SAME object
cast<Derived&>(h).t = 5;                        // writes go through it
print("after write:  ", cast<Derived&>(h).t);

shared_ptr<Derived> s = cast<shared_ptr<Derived>>(h);   // cast<shared_ptr<T>>: a handle sharing it
s.t = 77;
print("via handle:   ", cast<Derived&>(h).t);

Derived copy = cast<Derived>(h);   // the value form COPIES - a separate object from here on
copy.t = 0;
print("original:     ", cast<Derived&>(h).t, "  copy: ", copy.t);
    output
    alias:        9
after write:  5
via handle:   77
original:     77  copy: 0

    Two things to keep in mind. The value form applied to a handle or a reference still copies, and because that is almost never what you meant, the checker warns about it (cast<C>(h) copies the instance - use cast<C&>(h) to alias it or cast<shared_ptr<C>>(h) to share it). And a cast to an unrelated class raises the catchable Cannot cast 'X' to 'T' at run time; the checker never second-guesses the operand, since saying cast is how you tell it you know better. The primitive forms, the char rules and the full contract are in the Type Ladder.

    Choosing a strategy​

    The short version: passing by value pays for a deep copy that grows with the payload; & and shared_ptr alias the same object at essentially the same cost. All three strategies are quantified side by side in Performance.

    The copy is elided when it cannot be observed. A by-value class, array or map parameter that the callee only reads binds the argument itself, with no copy at all, when the engine can prove the copy would make no difference: the body never stores through the parameter or calls a mutating method on it, never compares it, aliases it, returns it, passes it on whole or in a nested loop, and only reads members and elements whose declared type is a primitive or a string; and the callee, with everything it calls, writes nothing but its own locals (the same purity the parallel bodies are held to). Anything outside that shape keeps the clone, so the semantics never change, only the cost: a read-only helper taking a struct by value runs at reference speed. Objects of a nocopy class still raise when passed by value, whatever the callee does. The proof is per function, computed on the first call and redone whenever definitions change; engine::parameter_alias(false) turns the elision off for a differential check.

    Decision guide:

    • Plain values (default) for scalars, strings (O(1) shared copies), small structs, and anywhere you want snapshot semantics. Stop when the object carries containers and sits in a hot path: the per-call deep copy is the one cost here that grows with the object.
    • T& params / auto& decls when a function needs to see or mutate the caller's object: cheapest aliasing, fastest shape for in-place algorithms. Constraint: references are aliases, not storage. Plain assignment stores a value through them, and a reference can't live in a field or container. & can't be your data model.
    • shared_ptr<T> (new T(...)) when identity must outlive the call: fields holding objects, containers of entities, registries, trees/graphs where nodes hold nodes. Same cost as & at call boundaries. Copies follow the declaration: if the object was declared shared_ptr (new T(...)), var/auto copies share the handle (as in C++: copying a shared_ptr copies the handle, not the object); if it was declared a value (MyType(5)), copies deep-copy.

    A var holding a handle. You can skip this on a first read. A var that holds a handle behaves exactly like a typed handle wherever the typed spelling would be legal; the only thing var adds is accepting what a typed holder would reject. What = does to such a variable depends on what is on the right:

    • A handle on the right (p = new Foo();) rebinds p.
    • A value of a compatible class (the held class or a subclass) assigns into the shared object, so every alias sees it, exactly what a shared_ptr<Foo> variable does. Foo() is a value, new Foo() is a handle: the same distinction the typed rungs draw.
    • A value of an unrelated class, or a primitive (p = Bar();, p = 5;) rebinds p to an independent copy. This is the one move var adds, and it sits precisely where a typed holder would raise.
    • auto q = p; taken from a var-held handle locks q as a shared_ptr<Foo>; the typed rungs themselves are unchanged.

    The same four moves, in order, with alias watching. same_as asks whether two handles point at one object; the general form is same_object(x, y), which answers identity for handles, references, containers and instances alike, because == compares values memberwise (see Equality):

    jaiscript
    class Foo { int x = 1; }
class Bar { int y = 2; }
var p = new Foo();
var alias = p;            // a var copy of a handle shares the handle, as in C++
p.x = 10;
print("alias.x = ", alias.x);
Foo f = Foo(); f.x = 77;
p = f;                    // a compatible VALUE assigns INTO the shared object
print("alias.x = ", alias.x, "  same object: ", p.same_as(alias));
p = new Foo();            // a HANDLE rebinds p; alias keeps the old object
p.x = 5;
print("alias.x = ", alias.x, "  p.x = ", p.x);
p = Bar();                // an unrelated value rebinds p to an independent copy
print("p.y = ", p.y, "  alias.x = ", alias.x);
    output
    alias.x = 10
alias.x = 77  same object: true
alias.x = 77  p.x = 5
p.y = 2  alias.x = 77

    Rule of thumb: values by default; & when a call needs the real thing; new/shared_ptr when the alias needs to live somewhere.

    clone vs copy (host API note)​

    Inside script, assignment of value-declared objects behaves as a (deep) copy, as shown above (shared_ptr-declared objects share the handle instead). On the C++ side the rule is inverted: copying a jai::script_value is a cheap O(1) shallow handle copy (heavy types sit behind strong_ptr), and value.clone() is the explicit deep copy. Don't confuse the two worlds: script = copies; C++ = aliases.
