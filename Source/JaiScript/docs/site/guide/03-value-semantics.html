Value Semantics & References​

Read this chapter before writing any JaiScript. The single most common ambush for new users lives here: JaiScript copies by default — everywhere. Assignment copies. Function arguments copy. Even class instances copy. If you mutate a copy, the original never hears about it, and nothing warns you.

The ambush: mutations on copies vanish silently​

jaiscript
auto a = [1, 2, 3];
auto b = a;          // assignment COPIES the array
b[0] = 99;
print("a[0] = {}  (the original is untouched)", a[0]);
print("b[0] = {}", b[0]);

function double_all(arr) {
    for (auto& x : arr) { x *= 2; }   // mutates the local COPY
}
auto nums = [1, 2, 3];
double_all(nums);                     // parameter passed BY VALUE
print("after double_all(nums): nums[0] = {}  <- mutation vanished!", nums[0]);
output
a[0] = 1  (the original is untouched)
b[0] = 99
after double_all(nums): nums[0] = 1  <- mutation vanished!

*(pinned: semantics/value_semantics_tests.hpp — assignment_copies, array_assignment_copies, map_assignment_copies, function_by_value_copies; deep-copy details in semantics/test_deep_copy.cpp, test_object_deep_copy.cpp)*

This applies to class instances too — unlike Python/JS/Lua/C#, objects are values:

jaiscript
class Point {
    int x = 0;
    void set(int v) { x = v; }             // methods mutate their own instance
}
auto p = Point();
p.x = 1;
auto q = p;          // class instances COPY on assignment too
q.x = 99;
print("p.x = {}  q.x = {}", p.x, q.x);

function try_mutate(o) { o.x = 77; }       // by-value param: mutation is lost
try_mutate(p);
print("after try_mutate(p): p.x = {}", p.x);

p.set(42);                                 // method calls DO mutate the receiver
print("after p.set(42):    p.x = {}", p.x);
output
p.x = 1  q.x = 99
after try_mutate(p): p.x = 1
after p.set(42):    p.x = 42

So: methods mutate their receiver; free functions receive copies. When a mutation "doesn't stick", check whether you passed the object by value.

Escape hatch 1: & reference parameters​

Declare a parameter with & and the callee binds the caller's variable. Works with explicit types (int& x) and with auto& (any type):

jaiscript
function bump(int& x) { x += 1; }         // typed by-ref parameter
auto n = 41;
bump(n);
print("after bump(n): {}", n);

function fill(auto& arr, v) { arr.push(v); }   // auto& works for any type
auto items = [];
fill(items, "sword");
print("items.size() = {}", items.size());

class Hero { int hp = 10; }
function heal(auto& who) { who.hp += 5; }
auto h = Hero();
heal(h);                                   // & is how object mutations survive a call
print("h.hp = {}", h.hp);
output
after bump(n): 42
items.size() = 1
h.hp = 15

*(pinned: semantics/value_semantics_tests.hpp reference_parameter_preserves_modifications; vm/vm_backend_tests.cpp ref_param_* family — ~25 tests covering pass-through chains, block/loop scopes, methods, globals, recursion)*

Escape hatch 2: field and element lvalues as ref arguments​

You can pass obj.field or arr[i] straight into a & parameter. Element references re-resolve through the container, so they stay correct even if the array reallocates its storage:

jaiscript
function bump(int& x) { x += 1; }
class Hero { int hp = 10; }
auto h = Hero();
bump(h.hp);                 // field lvalue passes by reference
print("h.hp = {}", h.hp);

auto arr = [5, 6, 7];
bump(arr[1]);               // array element lvalue passes by reference
print("arr[1] = {}", arr[1]);
for (int i = 0; i < 64; ++i) { arr.push(0); }   // force reallocation
bump(arr[1]);               // element refs re-resolve through the container
print("arr[1] after realloc = {}", arr[1]);
output
h.hp = 11
arr[1] = 7
arr[1] after realloc = 8

*(pinned: vm/vm_backend_tests.cpp ref_param_instance_field_from_method_body, ref_param_element_ref_single_hop, ref_param_element_ref_pass_through_realloc, ref_param_element_ref_shrink_errors — shrinking the array out from under an element ref raises a catchable error rather than corrupting memory; the shared kernel is detail/ref_lvalue.hpp, verbatim in both backends)*

Escape hatch 3: reference declarations (auto&)​

auto& r = x; declares an alias. References chain, and element references survive reallocation just like ref params:

jaiscript
var v = 1;
auto& g = v;         // reference declaration: g aliases v
auto& h = g;         // references chain
h = h + 3;
print("v = {}", v);

var arr = [7, 8];
auto& x = arr[1];    // element reference
for (int i = 0; i < 64; ++i) { arr.push(0); }
x = 42;              // still writes through after the array reallocated
print("arr[1] = {}", arr[1]);
output
v = 4
arr[1] = 42

*(pinned: vm/vm_backend_tests.cpp ref_decl_shares_env_ref, ref_decl_element_ref_survives_realloc)*

Current caveat: an auto& bound to a typed array's element drops the element's type constraint — you can write a string through it into an array<int> (pinned deliberately for now: vm/vm_backend_tests.cpp ref_decl_element_constraint_dropped).

Known crash (reported): calling a builtin string method through a ref declaration (auto& r = s; r.length();) currently segfaults on both backends at the commit these docs were built from. String methods through ref parameters are fine, as are array/map methods through ref declarations. Until fixed, dereference first or operate on the original variable. (See INTENT_QUESTIONS.)

Escape hatch 4: range-for with auto&​

jaiscript
auto nums = [1, 2, 3];
for (auto x : nums) { x *= 2; }       // copies: original unchanged
print("after value loop: {}", nums[0]);
for (auto& x : nums) { x *= 2; }      // references: mutates in place
print("after ref loop:   {}", nums[0]);
output
after value loop: 1
after ref loop:   2

*(pinned: language/range_based_for_tests.cpp; language/review_regression_tests.cpp range_for_ref_in_function, range_for_ref_realloc_no_corruption)*

Escape hatch 5: shared_ptr<T> — opt-in reference semantics​

When you want an object shared by handle (entity registries, cross-references), declare it shared_ptr<T>. Copies of the handle alias the same object; weak_ptr<T> observes without owning:

jaiscript
class P { int x = 3; }
shared_ptr<P> sp = P();
auto alias = sp;
alias.x = 99;
print("sp.x = {} (shared!)", sp.x);
function poke(o) { o.x = 42; }
poke(sp);
print("after poke: {}", sp.x);
output
sp.x = 99 (shared!)
after poke: 42
jaiscript
class P { int x = 3; }
shared_ptr<P> sp = P();
weak_ptr<P> w = sp;
print("expired: {}", w.expired());
auto l = w.lock();
l.x;
output
expired: false
== result: 3

Note the guard rail: weak_ptr<P> w = p; from a plain (value-semantic) object is an error — "Cannot initialize weak_ptr<> from value-semantic object: use shared_ptr\<T\>". (pinned: semantics/weak_ptr_tests.cpp, semantics/script_container_tests.cpp)

What each strategy costs (measured)​

Same computation, three ways of holding/passing a meaty object (string name + 8-int stats array + 4 scalars; 200 calls per row, jaibite-precompiled, min-of-5, integer-µs harness — full methodology and tables in docs/aliasing_costs.md; rows live in the "Performance Benchmarks" suite as Aliasing ...):

strategyinterp µs/callvm µs/callvs &
read-only compute, pass Creature c (by value)8.06.61.3–1.4× — the deep copy, ~1.8 µs/call here, grows with payload
read-only compute, pass Creature& c6.24.81.0
read-only compute, pass shared_ptr<Creature> c6.44.9tie (within noise)
mutate: heal(Unit& u) vs heal(shared_ptr<Unit> u)1.7 / 1.81.4 / 1.4tie (within noise)
method call — held as value / auto& / shared_ptr5.7–5.84.7all tie: the holder doesn't matter

On the node-aliasing structure benchmark (BST, 15 nodes): in-place & params are ~1.35× faster than the shared_ptr return-and-reassign shape (that delta is the shape, not a per-access penalty), and both are ~3.5× faster than naive by-value, which deep-copies subtrees at every recursion level.

Decision guide:

  • Plain values (default) for scalars, strings (O(1) shared copies), small structs, and anywhere you want snapshot semantics. Stop when the object carries containers and sits in a hot path — the per-call deep copy is the biggest avoidable cost above.
  • T& params / auto& decls when a function needs to see or mutate the caller's object: cheapest aliasing, fastest shape for in-place algorithms. Constraint: references are aliases, not storage — plain assignment stores a value through them, and a reference can't live in a field or container. & can't be your data model.
  • shared_ptr<T> (new T(...)) when identity must outlive the call: fields holding objects, containers of entities, registries, trees/graphs where nodes hold nodes. Same cost as & at call boundaries. Copies follow the declaration: if the object was declared shared_ptr (new T(...)), var/auto copies share the handle (as in C++ — copying a shared_ptr copies the handle, not the object); if it was declared a value (MyType(5)), copies deep-copy.

Rule of thumb: values by default; & when a call needs the real thing; new/shared_ptr when the alias needs to live somewhere.

clone vs copy (host API note)​

Inside script, assignment of value-declared objects behaves as a (deep) copy, as shown above (shared_ptr-declared objects share the handle instead). On the C++ side the rule is inverted: copying a jai::script_value is a cheap O(1) shallow handle copy (heavy types sit behind strong_ptr), and value.clone() is the explicit deep copy. Don't confuse the two worlds: script = copies; C++ = aliases. (pinned: semantics/test_cpp_bound.cpp, semantics/test_deep_copy_comprehensive.cpp; documented in core/value.hpp)
