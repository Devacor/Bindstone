    Classes​

    Script classes: fields with initializers (run in declaration order), constructors with overloading and : this(...) delegation, inheritance with super, statics, and hot reload with instance migration. All methods are virtual; overriding requires the explicit override keyword. Remember from Value Semantics: instances are values: assignment copies; when you want sharing, hold a handle (shared_ptr<T>, which new T(…) spells for you).

    Fields, constructors, implicit self​

    jaiscript
    class Creature {
    string name = "anonymous";
    int health = 100;
    int max_health = health;

    Creature(string n) { name = n; }

    void take_damage(int amount) {
        health -= amount;
        if (health <= 0) { print("{} died", name); }
    }

    auto describe() { return name + " (" + to_string(health) + "/" + to_string(max_health) + ")"; }
}
auto goblin = Creature("goblin");
goblin.take_damage(30);
print(goblin.describe());
goblin.take_damage(80);
goblin.describe();
    output
    goblin (70/100)
goblin died
== result: goblin (-10/100)

    max_health = health works because field initializers run top-to-bottom in declaration order. Methods access fields directly (implicit self). Construction is a plain call: Creature("goblin") makes a value; new Creature("goblin") makes a shared_ptr handle instead (see Value Semantics for when you want which). private: / public: section labels work C++-style. See Access control below.

    Constructor overloading and : this(...) delegation​

    jaiscript
    class Point {
    int x = 0;
    int y = 0;
    Point() : this(0, 0) {}
    Point(int v) : this(v, v) {}
    Point(int px, int py) { x = px; y = py; print("main ctor ({}, {})", px, py); }
}
auto a = Point();
auto b = Point(3);
auto c = Point(1, 2);
b.x + c.y;
    output
    main ctor (0, 0)
main ctor (3, 3)
main ctor (1, 2)
== result: 5

    Converting constructors. A true one-parameter constructor makes the class a conversion target, and that conversion is one row of the one table. It runs for declarations, assignments, by-value parameters, returns and field stores alike:

    jaiscript
    class Money {
    int dollars = 0;
    int cents = 0;
    Money(int d, int c) { dollars = d; cents = c; }
    Money(int d) : this(d, 0) {}          // a true one-parameter constructor: converting
}
void pay(Money m) { print("paid {}.{}", m.dollars, m.cents); }
Money price = 5;                          // declaration, through Money(int)
pay(7);                                   // by-value parameter, the same table
pay(price);
    output
    paid 7.0
paid 5.0

    Two deliberate C++ divergences keep this predictable. A constructor that reaches one parameter only through defaults (Money(float a, int _ignored = 0)) is not converting, so a defaulted sentinel is how you opt out, and there is no explicit keyword to remember. And conversion is always a single step: the argument must fit the constructor's parameter directly, never x.to_int() first and Money(int) second.

    Inheritance: super(...), super::, explicit override​

    jaiscript
    class Cat {
    int a = 0;
    Cat(int v) { a = v; }
    auto speak() { return "meow " + to_string(a); }
}
class Tiger : Cat {
    Tiger() : super(5) {}
    auto speak() override {
        return "ROAR! (base said: " + super::speak() + ")";
    }
}
auto t = Tiger();
print(t.speak());
Cat c = t;
type_of(c);
    output
    ROAR! (base said: meow 5)
== result: Tiger

    Redefining a base method without override is an error, raised when the class declaration runs. The message is explicit:

    jaiscript
    class Cat { auto speak() { return "meow"; } }
class Tiger : Cat { auto speak() { return "ROAR"; } }   // no override
Tiger().speak();
    output
    == error: Method 'speak' shadows base class method. Use 'override' keyword if this is intentional

    Assigning a derived instance to a base-typed variable is allowed; the reverse (parent to child), siblings, and structurally-identical unrelated classes are rejected.

    A subtype member through a base-typed receiver​

    Once a variable is declared Cat, the checker holds you to Cat's members, exactly like C++. The object inside may well be a Tiger, but reaching for a member only Tiger declares is a load error:

    jaiscript
    class Cat { int a = 0; }
class Tiger : Cat { int stripes = 12; }
Cat c = Tiger();
print(c.stripes);
    output
    jaiscript: static check failed:
<script>:4:9: error: no member 'stripes' in class 'Cat' (declared at 1:7)
    print(c.stripes);
            ^

    The spelled fix is cast<Tiger&>(c): a reference to the same object, so reads and writes through it land in c. (A value-form cast<Tiger>(c) would hand you a copy. See cast in The Type Ladder.) A var receiver is the other way out: it is unchecked, so the member resolves at run time. Either way, a wrong guess about the dynamic class is a catchable error, never a silent read:

    jaiscript
    class Cat { int a = 0; }
class Tiger : Cat { int stripes = 12; }
Cat c = Tiger();
print(cast<Tiger&>(c).stripes);     // a reference to the same object: reads go through
cast<Tiger&>(c).stripes = 5;        // and so do writes
print(cast<Tiger&>(c).stripes);
var anything = c;                   // a var receiver is unchecked: members resolve at run time
print(anything.stripes);
try { cast<Tiger&>(Cat()).stripes; } catch (e) { print("caught: {}", e); }
    output
    12
5
5
caught: Cannot cast 'Cat' to 'Tiger&'

    A base-typed slot keeps the whole object, a deliberate difference from C++, which slices a Tiger copied into a Cat down to its Cat part. In JaiScript Cat c = Tiger(); holds a complete Tiger: type_of(c) is Tiger, its overrides run, and cast<Tiger&>(c) reaches its fields. The same holds for every copy into a base-typed place (another Cat variable, a Cat parameter, an element of an array<Cat>, cast<Cat>(tiger)): the copy is a copy of the whole Tiger. The slot's type decides what the checker lets you name, never what the value is.

    Deriving a C++ class, and extend​

    A class may derive a class the host bound from C++. Constructing it (Voidkin()) constructs the C++ object underneath; an object the host already owns is given the class with extend(object, Class), in place: the handle you pass, and every other handle to that object, is the new class from then on. extend re-classes pure script instances the same way, which is what lets the sample below run on its own. Swap the script Creature for one the host bound from C++ and the remaining lines do not change:

    jaiscript
    class Creature {
    string name = "grunt";
    string speak() { return "..."; }
}
class Voidkin : Creature {
    int chomp = 3;
    string speak() override { return "voidkin"; }
}
auto raw = new Creature();          // a handle the "host" already holds
auto same = raw;                    // another handle to the same object
extend(raw, Voidkin);               // re-class it in place
raw.chomp = 17;
print(raw.speak(), " ", raw.chomp);
print(same.speak(), " ", same.chomp, " ", same.name);
    output
    voidkin 17
voidkin 17 grunt

    extend is a no-op for the class the object already is and re-derives for another class that derives the object's C++ class (fields both classes declare keep their values; the new class's own fields take their initializers). Overrides of C++ methods need override like any other; bare members and inherited C++ methods resolve inside methods as usual. When the object arrives from the host rather than from script (a raw the engine injected before the file ran), tell the checker it exists with extern raw; at the top of the file, otherwise the name is an undeclared-identifier load error (see the escape hatches in Chapter 13). The host side, ownership, and serialization of these hybrids are in Script-Extensible Objects.

    nocopy classes​

    nocopy class Ledger { ... } refuses by-value copies, like a deleted C++ copy constructor: auto copy = ledger; and a by-value parameter both stop the script with an error naming the class (it goes straight to the host: a try around the copy does not see it), while auto& / var& and Ledger& parameters bind as usual:

    jaiscript
    nocopy class Ledger { int n = 1; }
auto l = Ledger();
auto copy = l;
    output
    == error: Cannot copy an instance of nocopy class 'Ledger': hold it by reference (auto&/var&) or share it (shared_ptr)

    nocopy is inherited: every class derived from a nocopy class is nocopy, and so is a script class over a C++ base that has no copy constructor. There is no opt-out further down the chain.

    Typed fields are enforced​

    Fields follow the same type ladder as variables: explicit types enforce and convert through the one conversion table; var fields stay dynamic; auto fields lock on their initializer. A store the checker cannot see through (the value came out of a var) is checked when it lands, and is catchable there:

    jaiscript
    class Stats {
    int hp = 10;
    var anything = 0;
}
auto s = Stats();
s.hp = 3.9;
print("hp = {} ({})", s.hp, type_of(s.hp));
s.anything = "free";
print("anything = {}", s.anything);
var bad = "not a number";
try {
    s.hp = bad;
} catch (e) {
    print("caught: {}", e);
}
s.hp;
    output
    hp = 3 (int)
anything = free
caught: Cannot assign string to field 'hp' of Stats (declared int)
== result: 3

    Write the literal directly (s.hp = "not a number";) and it is a load error instead: error: cannot assign 'string' to field 'hp' declared 'int' (declared at 2:9), and the try never runs. Enforcement covers direct assigns, implicit-this assigns in methods/ctors, compound assigns, inherited fields, the C++ set_field API, and JSON round-trips.

    Access control: public: / private:​

    Section labels control access, and there are two levels. Members start public: everyone reaches them. A member after a private: label is reachable from the class that declares it and from every class derived from it, by a bare name in a method, through this., and through any object of that class family. protected: is accepted as a synonym of private:, so C++ habits compile and read the same. Code outside the family (a free function, top-level code, an unrelated class) gets Cannot access private member 'x' of class 'C' for every read, write, call, compound assignment and ++/--:

    jaiscript
    class Chest {
private:
    int gold = 250;
public:
    int looted = 0;
    auto peek() { return gold; }              // the class's own code sees private members
}
class Vault : Chest {
    int double_gold() { return gold * 2; }    // so does every class derived from it
}
auto v = Vault();
print("peek() = {}, double_gold() = {}", v.peek(), v.double_gold());
var anyone = v;
try {
    anyone.gold;
} catch (e) {
    print("caught: {}", e);
}
    output
    peek() = 250, double_gold() = 500
caught: Cannot access private member 'gold' of class 'Chest'

    A var receiver is checked when the access runs, as above. When the receiver's class is known at load, the strict checker reports the same text before anything runs (warn mode prints it and lets the run reach the raise):

    jaiscript
    class Chest {
private:
    int gold = 250;
}
auto c = Chest();
print(c.gold);
    output
    <script>:6:9: error: Cannot access private member 'gold' of class 'Chest'
    print(c.gold);
            ^

    Accessors: _get_x / _set_x​

    Every field comes with synthesized accessors, which is why obj.x just works. Declare your own _get_x() / _set_x(v) and they win: obj.x reads through the getter, obj.x = v writes through the setter. Inside the class a bare x is still the backing field, so the accessors can use it without recursing:

    jaiscript
    class Thermostat {
    int target = 20;
    int _get_target() { return target * 10; }       // obj.target reads through this
    void _set_target(int v) { target = v + 1; }     // obj.target = v writes through this
    auto backing() { return target; }               // a bare name inside the class is the field
}
auto t = Thermostat();
print("t.target = {}", t.target);
t.target = 5;
print("field = {}, t.target = {}", t.backing(), t.target);
    output
    t.target = 200
field = 6, t.target = 60

    The checker types obj.x from the accessor when the declaration is unambiguous: one parameterless getter with a declared (non-var) return type gives reads that type, one single-parameter by-value setter gives writes theirs, so t.target = "warm"; is the load error cannot assign 'string' to property 'target' declared 'int', and char c = t.target; fails the same way. Anything murkier (two overloads, a var/auto getter, a getter with parameters, a reference or untyped setter parameter, an accessor on a class the engine registered from C++) leaves the member unchecked and the run-time conversion does the work. A property the host binds with dynamic_binder arrives in script as an accessor pair of this kind.

    Statics​

    Static fields and methods belong to the class and are reached with Class::name. Instance constructors/methods see them directly:

    jaiscript
    class Counter {
    static int count = 0;
    static float PI = 3.14159;
    Counter() { count = count + 1; }
    static int twice_count() { return count * 2; }
}
auto a = Counter();
auto b = Counter();
auto c = Counter();
print("Counter::count = {}", Counter::count);
print("Counter::twice_count() = {}", Counter::twice_count());
Counter::PI;
    output
    Counter::count = 3
Counter::twice_count() = 6
== result: 3.14159

    Class::name is the only spelling from outside. Counter.count is not a static access. It is a member lookup on the constructor value, and fails at run time. Static fields also enforce their declared type exactly like instance fields, through the same table: a literal mismatch is a load error, a var-sourced one raises where it lands, and the initializer converts on the way in:

    jaiscript
    class Registry {
    static int count = 0;
    static float ratio = 3;       // the initializer converts: holds 3.0
    static int last_id;           // no initializer: an int's default, 0
}
Registry::count = 2.9;            // the same table as an instance field: truncates
print("count = {} ({}), ratio = {}, last_id = {}", Registry::count, type_of(Registry::count), Registry::ratio, Registry::last_id);
var bad = "many";
try { Registry::count = bad; } catch (e) { print("caught: {}", e); }
try { Registry.count; } catch (e) { print("caught: {}", e); }
    output
    count = 2 (int), ratio = 3.0, last_id = 0
caught: Cannot assign string to static 'count' of Registry (declared int)
caught: function has no member 'count'

    (Registry::count = "many"; written as a literal is the load error cannot assign 'string' to field 'count' declared 'int'.) Statics are not inherited: a derived class neither sees them bare nor answers to Derived::count. Qualify with the declaring class:

    jaiscript
    class Base { static int count = 0; static int bump() { count += 1; return count; } }
class Derived : Base {
    auto bump_twice() { Base::bump(); return Base::bump(); }   // qualify with the declaring class
}
print(Derived().bump_twice());
try { Derived::count; } catch (e) { print("caught: {}", e); }
    output
    2
caught: class Derived has no static member 'count'

    Class::name op= v and ++Class::name are lvalues; static auto infers from its initializer and static var stays dynamic. A namespace can override class statics of the same name. See Namespaces.

    Name resolution in methods​

    A bare identifier inside a method resolves in C++ unqualified-lookup order, identical on both backends and for reads AND writes:

    1. the active catch variable (innermost catch)
    2. locals and parameters of the current function, including range-for variables, auto& reference declarations, and constructor parameters (declaration-point scoped: a use before the local's declaration resolves outward)
    3. enclosing scopes / explicit lambda captures
    4. class members: instance fields (implicit this, including inherited), then instance methods (as bound methods), then static fields and static methods (inside a static method, the statics of the class)
    5. globals (variables and free functions)

    Three consequences are worth knowing.

    First, members shadow globals: if a class has a field or method hp, a bare hp in its methods reads and writes the member even when a global hp exists, and defining a new global after the class never steals the class's bare-name member accesses. The shadow is by name, exactly like C++: a method flavor() hides a global flavor(int) entirely, so a bare flavor(42) in that class is an argument-count error rather than a silent call to the global. The escape hatch is also C++'s: ::flavor(42) resolves against the global scope only (locals, captures, and members are all skipped) and works everywhere an identifier does (::hp, ::hp = 5, ::hp += 1, ::grid[i], refill(::ammo)). The global stays reachable outside the class, and the checker's shadowing warnings (below) flag the declaration-side collisions.

    Second, lambdas created inside a method see fields too, at the same member step of the lookup as the method body. What differs is when the field is read: a bare [] lambda resolves the name when it is called, exactly like the method body; [=] captures the field's value at creation; [&] shares the live field, so writes through the capture land in the instance:

    jaiscript
    class Tank {
    int hp = 7;
    auto probe() {
        auto bare = []()  { return hp; };        // resolves hp when called, like the method body
        auto copy = [=]() { return hp; };        // captures the field's value now
        auto live = [&]() { hp += 1; return hp; }; // shares the live field
        print("bare {} copy {} live {}", bare(), copy(), live());
        hp = 100;
        print("after hp = 100: bare {} copy {} field {}", bare(), copy(), hp);
    }
}
Tank().probe();
    output
    bare 7 copy 7 live 8
after hp = 100: bare 100 copy 7 field 100

    Third, [this] captures the instance itself, as C++ captures the this pointer: the lambda reads and writes the object it was made in, never a copy ([this]() { v = 9; } sets that instance's v).

    The checker (on by default) emits warning-severity shadowing diagnostics, never errors, even in strict mode, because shadowing is legal: a local/parameter/range-for/catch variable that shadows a field of the enclosing class ("local 'hp' shadows field 'hp' of class 'Creature' (field declared at 4:2)"), a local that shadows an outer local, and a declaration that shadows a global the same function already read. Constructor parameters named after the field they initialize (C(int hp) { this.hp = hp; }) are the established idiom and stay silent.

    Hot reload with permissive migration​

    Re-executing a class declaration on the same engine reloads the class. Live instances migrate permissively: fields that still exist keep their current values (including still-default ones), brand-new fields get the new defaults, removed fields drop. The two execute() calls below run on one engine (marked //=== execute):

    jaiscript
    class Config {
    auto version = 1;
    auto name = "default";
}
auto cfg = Config();
cfg.name = "production";
print("before reload: v{} {}", cfg.version, cfg.name);
//=== execute
class Config {
    auto version = 2;
    auto name = "default";
    auto retries = 3;
}
print("after reload:  v{} {} retries={}", cfg.version, cfg.name, cfg.retries);
    output
    before reload: v1 production
== result: null
after reload:  v1 production retries=3
== result: null

    To try it from a terminal, start the REPL (jaiscript with no file) and paste the two halves as two entries. Each entry is one execute().

    Note version stayed 1: migration preserves existing per-instance state, it does not re-run initializers for fields that already exist; only the new retries field picked up its default. Methods always come from the newest class definition. Hot reload even works while a function/class on the current call stack is redefined, and suspended method coroutines survive a field-changing reload of their class.
