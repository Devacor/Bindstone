Classes​

Script classes: fields with initializers (run in declaration order), constructors with overloading and : this(...) delegation, inheritance with super, statics, and hot reload with instance migration. All methods are virtual; overriding requires the explicit override keyword. Remember from Value Semantics: instances are values — assignment copies; use shared_ptr<T> for handle semantics.

Fields, constructors, implicit self​

jaiscript
class Creature {
    string name = "anonymous";
    int health = 100;
    int max_health = health;

    Creature(string n) { name = n; }

    void take_damage(int amount) {
        health -= amount;
        if (health <= 0) { print("{} died", name); }
    }

    auto describe() { return name + " (" + to_string(health) + "/" + to_string(max_health) + ")"; }
}
auto goblin = Creature("goblin");
goblin.take_damage(30);
print(goblin.describe());
goblin.take_damage(80);
goblin.describe();
output
goblin (70/100)
goblin died
== result: goblin (-10/100)

max_health = health works because field initializers run top-to-bottom in declaration order. Methods access fields directly (implicit self). Construction is a plain call — Creature("goblin") makes a value; new Creature("goblin") makes a shared_ptr handle instead (see Value Semantics for when you want which). private: / public: section labels work C++-style — see Access control below.

Constructor overloading and : this(...) delegation​

jaiscript
class Point {
    int x = 0;
    int y = 0;
    Point() : this(0, 0) {}
    Point(int v) : this(v, v) {}
    Point(int px, int py) { x = px; y = py; print("main ctor ({}, {})", px, py); }
}
auto a = Point();
auto b = Point(3);
auto c = Point(1, 2);
b.x + c.y;
output
main ctor (0, 0)
main ctor (3, 3)
main ctor (1, 2)
== result: 5

Converting constructors: a defaulted-parameter constructor is not a converting constructor (deliberate C++ divergence — conversion requires a true one-parameter constructor; write a delegating overload to opt in). Conversion is opted into with a one-parameter overload (Money(int a) : this(a, 0) {}) and opted out of with a defaulted sentinel parameter (Money(float a, int _ignored = 0)) — the explicit keyword is unnecessary.

Inheritance: super(...), super::, explicit override​

jaiscript
class Cat {
    int a = 0;
    Cat(int v) { a = v; }
    auto speak() { return "meow " + to_string(a); }
}
class Tiger : Cat {
    Tiger() : super(5) {}
    auto speak() override {
        return "ROAR! (base said: " + super::speak() + ")";
    }
}
auto t = Tiger();
print(t.speak());
Cat c = t;
type_of(c);
output
ROAR! (base said: meow 5)
== result: object

Redefining a base method without override is an error — the message is explicit:

output
== error: Method 'speak' shadows base class method. Use 'override' keyword if this is intentional

Assigning a derived instance to a base-typed variable is allowed; the reverse (parent to child), siblings, and structurally-identical unrelated classes are rejected.

Typed fields are enforced​

Fields follow the same type ladder as variables: explicit types enforce and convert; var fields stay dynamic; auto fields lock on their initializer.

jaiscript
class Stats {
    int hp = 10;
    var anything = 0;
}
auto s = Stats();
s.hp = 3.9;
print("hp = {} ({})", s.hp, type_of(s.hp));
s.anything = "free";
print("anything = {}", s.anything);
try {
    s.hp = "not a number";
} catch (e) {
    print("caught: {}", e);
}
s.hp;
output
hp = 3 (int)
anything = free
caught: Type mismatch in assignment
== result: 3

Enforcement covers direct assigns, implicit-this assigns in methods/ctors, compound assigns, inherited fields, the C++ set_field API, and JSON round-trips.

Access control: private: / public:​

C++-style section labels control access. Fields and methods after a private: label are reachable from the class's own methods but not from outside — the violation is a catchable runtime error, not a silent read:

jaiscript
class Chest {
private:
    int gold = 250;
public:
    int looted = 0;
    auto peek() { return gold; }      // methods see private members
}
auto c = Chest();
print("peek() = {}", c.peek());
try {
    c.gold;
} catch (e) {
    print("caught: {}", e);
}
output
peek() = 250
caught: Cannot access private member 'gold' of class 'Chest'

Statics​

Static fields and methods belong to the class and are reached with ::. Instance constructors/methods see them directly:

jaiscript
class Counter {
    static int count = 0;
    static float PI = 3.14159;
    Counter() { count = count + 1; }
    static int twice_count() { return count * 2; }
}
auto a = Counter();
auto b = Counter();
auto c = Counter();
print("Counter::count = {}", Counter::count);
print("Counter::twice_count() = {}", Counter::twice_count());
Counter::PI;
output
Counter::count = 3
Counter::twice_count() = 6
== result: 3.141590

Statics work with inheritance, and a namespace can override class statics of the same name — see Kitchen Sink.

Name resolution in methods​

A bare identifier inside a method resolves in C++ unqualified-lookup order, identical on both backends and for reads AND writes:

  1. the active catch variable (innermost catch)
  2. locals and parameters of the current function — including range-for variables, auto& reference declarations, and constructor parameters (declaration-point scoped: a use before the local's declaration resolves outward)
  3. enclosing scopes / explicit lambda captures
  4. class members: instance fields (implicit this, including inherited), then instance methods (as bound methods), then static fields and static methods — inside a static method, the statics of the class
  5. globals (variables and free functions)

Three consequences worth knowing. First, members shadow globals: if a class has a field or method hp, a bare hp in its methods reads and writes the member even when a global hp exists — and defining a new global after the class never steals the class's bare-name member accesses. The shadow is by name, exactly like C++: a method flavor() hides a global flavor(int) entirely, so a bare flavor(42) in that class is an argument-count error rather than a silent call to the global. The global stays reachable outside the class, and the static checker's shadowing warnings (below) flag the declaration-side collisions. Second, [=] and [&] lambdas see fields with the same member-first order: [=] captures a field's value at creation, [&] shares the live field (writes through the capture land in the instance). Third, bare-[] lambdas are capture-free by design (minted once per site): they resolve only globals — reach fields through [=], [&], [this], or this.hp.

The static checker (engine::static_checking(check_mode::warn) or check()) emits warning-severity shadowing diagnostics — never errors, even in strict mode, because shadowing is legal: a local/parameter/range-for/catch variable that shadows a field of the enclosing class ("local 'hp' shadows field 'hp' of class 'Creature' (field declared at 4:2)"), a local that shadows an outer local, and a declaration that shadows a global the same function already read. Constructor parameters named after the field they initialize (C(int hp) { this.hp = hp; }) are the established idiom and stay silent.

Hot reload with permissive migration​

Re-executing a class declaration on the same engine reloads the class. Live instances migrate permissively: fields that still exist keep their current values (including still-default ones), brand-new fields get the new defaults, removed fields drop. The two execute() calls below run on one engine (marked //=== execute):

jaiscript
class Config {
    auto version = 1;
    auto name = "default";
}
auto cfg = Config();
cfg.name = "production";
print("before reload: v{} {}", cfg.version, cfg.name);
//=== execute
class Config {
    auto version = 2;
    auto name = "default";
    auto retries = 3;
}
print("after reload:  v{} {} retries={}", cfg.version, cfg.name, cfg.retries);
output
before reload: v1 production
== result: null
after reload:  v1 production retries=3
== result: null

Note version stayed 1 — migration preserves existing per-instance state, it does not re-run initializers for fields that already exist; only the new retries field picked up its default. Methods always come from the newest class definition. Hot reload even works while a function/class on the current call stack is redefined, and suspended method coroutines survive a field-changing reload of their class.
