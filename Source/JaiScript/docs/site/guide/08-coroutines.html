    Coroutines​

    Declare with the coroutine keyword; calling one returns a coroutine handle instead of running the body. handle.next() runs to the next yield (returning the yielded value), handle.done() reports completion, and a final return value is delivered by the last next(). Nothing in the body runs until the first next(). The interpreter implements them by continuation replay, the VM by fibers. Behavior is identical. Coroutines turn stateful multi-frame behavior (AI, cutscenes, staged animations) into straight-line code that pauses where it yields.

    yield / next / done​

    jaiscript
    coroutine int counter() {
    yield 1;
    yield 2;
    return 3;
}
auto c = counter();
print("next: {}", c.next());
print("next: {}", c.next());
print("done? {}", c.done());
print("next: {}", c.next());
print("done? {}", c.done());
    output
    next: 1
next: 2
done? false
next: 3
done? true

    done() only asks: it never starts or advances the body. next(n) advances n yields and returns the value of the last one, the same as n calls to next() in a row; the count is an int of at least 1. To run a coroutine to the end, loop on done() or drive it with a range-for:

    jaiscript
    coroutine int steps() {
    for (int i = 1; i <= 5; ++i) { yield i * 10; }
    return -1;
}
auto h = steps();
print("skip ahead: {}", h.next(3));
while (!h.done()) { print("then: {}", h.next()); }
    output
    skip ahead: 30
then: 40
then: 50
then: -1

    Coroutines take parameters like any function, and yield works inside loops and conditionals. Side effects in a yield expression run exactly once, however the suspension is implemented underneath.

    Spellings​

    coroutine is a prefix, and it goes in front of every function spelling from the Functions chapter: return-type-first, trailing arrow, the function keyword, or nothing at all. Methods take the same forms, static ones included:

    jaiscript
    coroutine int a() { yield 1; }                 // return-type-first
coroutine b() -> int { yield 2; }              // trailing arrow
coroutine function c() -> auto { yield 3; }    // function keyword + arrow
coroutine function d() { yield 4; }            // function keyword, inferred
coroutine e() { yield 5; }                     // bare: no type, no keyword
print("{} {} {} {} {}", a().next(), b().next(), c().next(), d().next(), e().next());

class Spawner {
    int base = 10;
    coroutine function waves(int n) { for (int i = 0; i < n; ++i) { yield base + i; } }
    coroutine int w2() { yield base * 2; }
    coroutine w3() -> int { yield base * 3; }
    static coroutine int ticks() { yield 1; yield 2; }
}
auto s = Spawner();
for (auto w : s.waves(3)) { print("wave {}", w); }
print("{} {}", s.w2().next(), s.w3().next());
auto t = Spawner::ticks();
print("{} {}", t.next(), t.next());
    output
    1 2 3 4 5
wave 10
wave 11
wave 12
20 30
1 2

    The type you write describes what the body yields and returns (it is never the type of the call, which is always a handle), and at run time only the final return converts to it (see the last sample in this chapter). There is no coroutine lambda, and a coroutine cannot return a reference; both are parse errors. A namespace body cannot declare a coroutine (a parse error); declare it at program scope or as a static method.

    Each call is an independent instance​

    jaiscript
    coroutine int letters() { yield 1; yield 2; yield 3; }
auto x = letters();
auto y = letters();
print("{} {} {} {}", x.next(), x.next(), y.next(), x.next());
y.done();
    output
    1 2 1 3
== result: false

    Range-for drives a coroutine​

    A range-based for over a handle (or a handle-producing call) advances it until done, iterating the yielded values; a handle already advanced with next() continues from where it stands:

    jaiscript
    coroutine int squares(int n) {
    for (int i = 1; i <= n; ++i) { yield i * i; }
}
auto total = 0;
for (auto v : squares(5)) {
    print("got {}", v);
    total += v;
}
total;
    output
    got 1
got 4
got 9
got 16
got 25
== result: 55

    Method coroutines​

    Class methods can be coroutines. The suspended body sees this. Fields read/write normally across suspensions, and every instance gets independent generators:

    jaiscript
    class Gen {
    int id = 0;
    Gen(int i) { id = i; }
    coroutine int gen() { yield id; yield id * 2; }
}
auto a = Gen(1);
auto b = Gen(2);
auto ga = a.gen();
auto gb = b.gen();
print("{} {} {} {}", ga.next(), gb.next(), ga.next(), gb.next());
    output
    1 2 2 4

    Range-for drives method coroutines too, and inherited method coroutines work on derived classes.

    Receiver pinning​

    The handle pins the receiver alive. Even if the only strong reference to the instance dies with the frame that created it, resuming still sees the fields:

    jaiscript
    class D {
    int v = 7;
    coroutine int g() { yield v; v = 99; yield v; }
}
function make() {
    auto d = D();
    return d.g();
}
auto h = make();
print("{}", h.next());
print("{}", h.next());
h.done();
    output
    7
99
== result: false

    The handle keeps the instance alive for as long as the coroutine is suspended.

    Rules and edges​

    • Handles are reference-semantic: copying a handle (into a field, an array/map element, a by-value parameter, another variable) shares the ONE live coroutine; every alias sees the same next()/done() state. Even deep-copying an instance shares its handle field (a handle references a running computation; there is no meaningful deep copy). This is what lets an AI park its behavior coroutine in a field of its own game object and advance it every tick. Note the deliberate strong cycle when an instance's field holds a handle of its own method (the handle pins the receiver): break it by re-assigning/nulling the field, exactly like any shared structure. static coroutine methods work the same way; the handle just carries no receiver.
    • Handles advance correctly across separate execute() calls, through by-ref helper params, and from inside running functions without disturbing the caller's frame.
    • next() takes only its optional count and done() takes no arguments: a value cannot be sent into a running coroutine (h.next("go") raises next() count must be an integer, h.next(0) raises next() count must be at least 1). Give it its inputs as parameters when it is created, or let it read state it shares with the caller: a field of its instance for a method coroutine, or a program-scope variable.
    • A failed next() marks only that handle done. Calling next() on a finished coroutine raises the catchable Cannot resume a completed coroutine; a next(n) that reaches the end before its last step runs the steps before the end, then raises the same text.
    • Hot reload: a free coroutine can be redefined while one of its handles is suspended (the old handle keeps the old body), and method coroutines survive field-changing reloads of their class.
    • The execution budget still applies during next(), and budget errors skip catches inside coroutines too.
    • The checker stays out of the body's way: yield and return values are not checked statically, and what next() returns is unknown, so everything downstream of it is lenient. The handle itself is typed: a member other than next or done is a load error (h.resume() reports no member 'resume' on 'coroutine_handle' (did you mean 'next'?)).

    The declared type still does its work at run time: a yield e converts like a return of the same type, and a value the type cannot take raises at the yield, catchable around the next(). A failed next() finishes the coroutine. A bare yield; hands out nothing and is not converted:

    jaiscript
    coroutine int g() { yield 2.9; yield "three"; return 4; }
auto h = g();
print(h.next());
try { h.next(); } catch (e) { print("caught: ", e); }
print(h.done());
    output
    2
caught: Cannot yield string from 'g' (declared -> int)
true
