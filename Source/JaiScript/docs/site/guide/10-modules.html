Modules: include vs import​

Design intent (verbatim from Dev)​

include = PHP-template semantics, runs every time, may return a value, dynamic path exprs OK; import = module declaration, NOT an expression, never yields a value, cached (default file_timestamp mtime behavior; once/always modes; engine reset_import(s) for invalidation; add_include_path roots).

Everything below is the verified current behavior. (pinned: language/include_import_tests.cpp — all 13 tests)

include: runs every single time​

include "file.jai" (or include <file.jai>) executes the file's contents in the current scope, every time it is evaluated. Definitions land in your scope; side effects repeat on every include:

jaiscript
include "mod_math.jai"
print("mod_add(2, 3) = {}", mod_add(2, 3));
print("MOD_PI = {}", MOD_PI);
auto load_count = 0;
include "mod_count.jai"
include "mod_count.jai"
include "mod_count.jai"
print("include runs EVERY time: load_count = {}", load_count);

with mod_math.jai:

jaiscript
function mod_add(int a, int b) -> int { return a + b; }
auto MOD_PI = 3.14159;

and mod_count.jai:

jaiscript
load_count = load_count + 1;
output
mod_add(2, 3) = 5
MOD_PI = 3.141590
include runs EVERY time: load_count = 3

Includes nest (an included file can include another — pinned: nested_includes), and the # prefix is accepted and ignored for C++ muscle memory: #include "x.jai" (pinned: hash_prefix_ignored).

Note on "may return a value": that is the design intent; at the pinned commit include is statement-only — auto x = include "f.jai"; is a parse error and the included file's trailing value is discarded (see INTENT_QUESTIONS).

Dynamic paths​

The call form takes any string expression — both for include and import:

jaiscript
auto libname = "mod_" + "math" + ".jai";
include(libname);
mod_add(20, 22);
output
== result: 42

*(pinned: dynamic_include_with_variable, dynamic_import_with_expression)*

import: cached module declaration​

import "file.jai" executes the file at most once per engine (subject to the mode below). Repeating the import is free:

jaiscript
auto load_count = 0;
import "mod_count.jai"
import "mod_count.jai"
import "mod_count.jai"
print("import caches (default: re-run only if the file changed): load_count = {}", load_count);
output
import caches (default: re-run only if the file changed): load_count = 1

And import is not an expression — it never yields a value:

jaiscript
auto x = import "mod_math.jai";
output
== error: Parse error: <script>:1:10: Expected expression

Import modes (engine::import_behavior)​

ModeBehavior
file_timestamp (default)Re-imports only when the file's mtime changed since it was last imported — the hot-reload-friendly default.
onceImport exactly once; ignore later file changes.
alwaysTreat import as include (runs every time).

Set with engine->set_import_behavior(engine::import_behavior::once);. *(pinned: basic_import_once_behavior, import_file_timestamp_behavior, import_always_behavior)*

Invalidation and tracking (host API)​

C++
eng->add_include_path("scripts/");        // search roots; FIRST added path wins on collisions
eng->reset_import(canonical_path);        // forget one module -> next import re-runs it
eng->reset_imports();                     // forget all
eng->is_imported(canonical_path);         // query (canonical/absolute path)
eng->get_imported_files();                // list

Path resolution checks the include paths in the order they were added (pinned: include_path_resolution); a missing file throws (pinned: file_not_found_error).

Which one do I want? (the real-world idiom)​

The example games use both, exactly along the intended split (examples/roguelike/scripts/main.jai — verbatim):

jaiscript
// jai_rogue entry point. The host executes: import "main.jai"; rogue_main();
// state.jai holds the persistent globals and is excluded from hot reload.

import "state.jai";
import "util.jai";
import "data.jai";
// ... one import per module ...

// Re-execute every rule file mid-run ('R' with --dev). Classes hot-reload with
// instance migration; live coroutines (monster brains) keep their old bodies
// until rebuilt. G and RNG live in state.jai, which is deliberately skipped.
function reload_scripts() -> void {
    include "util.jai";
    include "data.jai";
    // ... include forces a re-run, giving in-game hot reload ...
}

Rules of thumb:

  • Declaring your module graph: import at the top of each file — cached, cheap to repeat, mtime-aware by default.
  • Forcing a re-run (hot reload of rules/content mid-game): include — it always executes.
  • Persistent state goes in a module you only import and never include, so a reload can't wipe it (the roguelike's state.jai).
