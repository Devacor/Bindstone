    Parallel Loops​

    parallel_for, parallel_transform and parallel_reduce run a loop over an array on every core with deterministic results: the same output at every thread count, byte-identical to the serial loop. The engine checks the body when the statement is reached, before any element runs, and a body it cannot prove safe is refused with a catchable error that names the construct; it is never run serially in silence. The table below is that contract, and the rest of the chapter walks through each form.

    What a parallel body may do​

    A text that starts with parallel_for: is raised when the statement is reached, before any element runs; most of them end with the position of the construct, at LINE:COL, left off here. parallel_transform and parallel_reduce raise the same texts under their own names. A text without the prefix is raised when the body runs the construct, because only then is the receiver known. The rules cover everything a body reaches: the functions it calls, the methods it runs and the constructors and destructors of the objects it makes.

    parallel_for and parallel_transform​

    parallel_for runs a loop body over the elements of an array on every core. The loop variable is the element, so auto& mutates it in place. parallel_transform(arr, fn) returns a new array with out[i] = fn(arr[i]); it is the same loop in a different spelling, as below shows. thread_count() reports the worker count.

    jaiscript
    var nums = [1, 2, 3, 4, 5, 6, 7, 8];
parallel_for (auto& x : nums) {
    x = x * x;                    // each element mutated in place, across workers
}
print("squares: {}", to_json(nums));

int inc(int v) { return v + 1; }
print("mapped:  {}", to_json(parallel_transform(nums, inc)));
    output
    squares: [1,4,9,16,25,36,49,64]
mapped:  [2,5,10,17,26,37,50,65]

    The zip form​

    The zip form walks several arrays of the same length in lockstep, one loop variable per array. Worker n owns segment n of every array, so a pre-allocated array of output structs is written in place: no construction per element, no result marshalling. This is the emitter shape, one input array and one output array of the same length, and the preferred way to produce several values per element.

    jaiscript
    class Body { float x = 0.0; float vx = 0.0; Body() {} Body(float px, float v) { x = px; vx = v; } }
class Sample { float pos = 0.0; bool moving = false; }
array<Body> bodies = [];
array<Sample> samples = [];
for (int i = 0; i < 6; i++) { bodies.push(Body(i * 10.0, i % 3 - 1.0)); samples.push(Sample()); }

parallel_for (auto& b, auto& s : bodies, samples) {   // one loop variable per array, walked in lockstep
    b.x += b.vx * 0.5;                                 // the input mutated in place
    s.pos = b.x;                                       // the pre-allocated output written in place
    s.moving = b.vx != 0.0;
}
for (auto& s : samples) { print(`${s.pos:.1f} ${s.moving}`); }
    output
    -0.5 true
10.0 false
20.5 true
29.5 true
40.0 false
50.5 true

    Arrays of different length, the range itself as a zipped array, or a non-array raise a catchable error when the statement is reached, before any element runs: parallel_for: zipped array 2 has 1 elements, the range has 3 (zipped arrays must have the same length), parallel_for: zipped array 2 is the range itself, parallel_for: zipped array 2 is not an array.

    parallel_transform is that zip​

    parallel_transform(xs, fn) is parallel_for (auto& x, auto& o : xs, out) { o = fn(x); } over a fresh output of xs.size() slots, and it costs exactly that loop plus the output. When fn only reads its parameter, its body runs inlined in the loop with the parameter bound to the element in place, so there is no call and no copy per element. A fn that mutates its parameter works on a private copy, so the source array is never touched either way. Any result type works, objects included: the returned array holds copies that alias nothing.

    jaiscript
    class Body { float x = 0.0; float vx = 0.0; Body() {} Body(float px, float v) { x = px; vx = v; } }
array<Body> bodies = [];
for (int i = 0; i < 4; i++) { bodies.push(Body(i * 10.0, 1.0)); }

float next_x(Body b) { return b.x + b.vx; }              // reads its parameter: the body runs inlined in the loop
Body stepped(Body b) { b.x += b.vx; return b; }         // mutates its copy: the source is untouched

var xs = parallel_transform(bodies, next_x);
var moved = parallel_transform(bodies, stepped);
print(`${to_json(xs)} moved ${moved[3].x:.1f} source ${bodies[3].x:.1f}`);
    output
    [1.0,11.0,21.0,31.0] moved 31.0 source 30.0

    An optional third argument, parallel_transform(arr, fn, weight_fn), balances chunks by per-element effort (e.g. weigh strings by length):

    jaiscript
    var texts = ["7", "42", "1999", "3", "250"];
int parse_one(string s) {                            // digits -> int, no host calls
    var n = 0;
    for (var i = 0; i < s.size(); i++) { n = n * 10 + (s[i] - '0'); }
    return n;
}
float w(string s) { return s.size(); }               // heavier strings, fatter chunks
var parsed = parallel_transform(texts, parse_one, w);
print("parsed: {}", to_json(parsed));
    output
    parsed: [7,42,1999,3,250]

    Control flow in the body​

    The body is the loop's body: continue moves to the next element, and so does a return written at the body's top level (iterations are independent, there is nothing to return to). A loop-level break is rejected when the statement is reached, before any element runs, with parallel_for: 'break' is not allowed in a parallel body (iterations are independent; use 'continue' for the next element). Inside a nested loop or switch, break and continue keep their usual meaning.

    jaiscript
    var words = ["keep", "", "skip", "keep", "", "keep"];
array<int> kept = [0, 0, 0, 0, 0, 0];
parallel_for (auto& w, auto& k : words, kept) {
    if (w == "") { continue; }        // next element
    if (w == "skip") { return; }      // also the next element: the body is the loop's body
    k = w.size();
}
print("{}", to_json(kept));
    output
    [4,0,0,4,0,4]

    A throwing element fails the whole call with the first error in iteration order, so failures are as deterministic as results.

    Captured reads​

    The body may read enclosing globals: scalars, strings, and value-semantic containers. Every worker sees the content as of the call (the "barrier"), identical at every worker count. Provisioning is automatic and tiered: a container of primitives or strings touched only by subscript reads is a zero-copy borrow (workers read the shared storage in place; a string read copies its bytes into a worker-owned string); anything else (nested containers, iterated or whole-value reads) is copied once per worker at the barrier and charged to memory_cap. This is what makes the "shared read-only grid" and "shared palette" renderer shapes cheap:

    jaiscript
    var gw = 4;
var grid = [];                       // the shared input: three rows of gw cells
for (var i = 0; i < gw * 3; i++) { grid.push(i); }
int row_sum(int row) {
    var total = 0;
    for (var x = 0; x < gw; x++) { total += grid[row * gw + x]; }   // captured reads
    return total;
}
var row_indices = [0, 1, 2];
var sums = parallel_transform(row_indices, row_sum);   // grid rides along for free
print("row sums: {}", to_json(sums));
    output
    row sums: [6,22,38]

    Writes to enclosing state​

    Writes to enclosing state are errors, with one proven exception, the index write below. The elements behind the loop variables are what a body mutates. Assigning to captured state in any other shape (g = ..., g[j] = ... with an index that is not a loop variable, compound stores, g.push(...) (any mutating or unrecognized method on a captured value), var& r = g aliases, passing captured state to a by-reference parameter, or for (auto& v : g)) raises an error like parallel_for: body writes enclosing state 'total' at 3:33. Objects cannot be captured at all (parallel_for: member access reaches captured state 'cfg' (captured reads are read-only, and objects cannot be captured) at 4:45); pass per-element object state through the arrays instead. Calls to other script functions (including recursion) and builtin container/string methods are fine.

    Index writes​

    out[i] = v (and op=, ++, --) is legal when out is an enclosing array and i a loop variable the body never writes. The loop variable's values must name distinct slots, which the statement checks when it is reached: two elements carrying one index raise parallel_for: elements 2 and 5 write 'out' at the same index 4. The body may touch out only as out[i], since reading another slot would race the writes (parallel_for: body touches 'out' beyond the slot it writes, out[i] at 4:20). Each worker writes a private copy of out, and the statement copies every element's slot back in element order, up to the first failing element: exactly the stores the serial loop makes.

    jaiscript
    array<int> order = [3, 0, 2, 1];
array<int> placed = [0, 0, 0, 0];
parallel_for (int slot : order) {
    placed[slot] = slot * 10;          // each element writes the slot its value names
}
print("{}", to_json(placed));
    output
    [0,10,20,30]

    Constructing objects​

    A body constructs objects in every spelling: Hit(r, d), Hit h(r, d);, Hit h; and new Hit(r, d). The new object belongs to the worker that made it, so its constructor writes its fields freely; everything else that construction runs follows the body's rules. When the statement is reached, before any element runs, it checks the constructor each call can reach (every one its argument count admits), the base constructors its initializer list names (a base it does not name is default-constructed), each level's field initializers, and the destructor of every class whose instance can die in the body: an object the body makes, an element it replaces, and whatever their fields hold. Class code may call script functions, methods on the object, and the same pure host functions a body may.

    jaiscript
    string PREFIX = "hit-";
class Vec { float x = 0.0; float y = 0.0; Vec() {} Vec(float a, float b) { x = a; y = b; } }
class Hit {
    int ray = -1;
    Vec at;
    string tag = PREFIX;
    Hit() {}
    Hit(int r, float d) { ray = r; at = Vec(d, d * 2.0); tag = tag + to_string(r); }
}
array<int> rays = [0, 1, 2, 3];
array<Hit> hits = [Hit(), Hit(), Hit(), Hit()];
parallel_for (int r : rays) {
    hits[r] = Hit(r, r * 0.5);         // each worker constructs the hit its ray owns
}
print("{} {} {}", hits[3].tag, hits[3].at.y, hits[0].ray);
    output
    hit-3 3.0 0

    Construction code that writes state the body does not own refuses the statement, and the error names where that code sits: a constructor, a field initializer or a destructor.

    jaiscript
    int next_id = 0;
int deaths = 0;
class Tick { int id = 0; Tick() { id = next_id; next_id++; } }
class Tag { int id = next_id++; }
class Res { int v = 0; ~Res() { deaths++; } }
array<int> xs = [1, 2, 3];
try { parallel_for (auto& x : xs) { Tick t; x = t.id; } } catch (e) { print(e); }
try { parallel_for (auto& x : xs) { Tag t; x = t.id; } } catch (e) { print(e); }
try { parallel_for (auto& x : xs) { Res r; x = r.v; } } catch (e) { print(e); }
    output
    parallel_for: body writes enclosing state 'next_id' in the constructor of 'Tick' at 3:49
parallel_for: body writes enclosing state 'next_id' in a field initializer of 'Tag' at 4:22
parallel_for: body writes enclosing state 'deaths' in the destructor of 'Res' at 5:33

    C++ classes and hybrids​

    A class the host binds, and a script class over one, construct in a body too: the host's constructor and destructor are taken to be safe on any thread, while the script levels follow the rules above. A host class whose constructor or destructor touches state other objects share (a registry, a cache, a service) is bound with .serial_only_constructor() (see the binder); a body that constructs it, or a script class over it, is refused before any element runs, with parallel_for: C++ class 'Sprite' is marked serial_only_constructor() and cannot be constructed in a parallel body at 3:48 or parallel_for: class 'Glowing' has a C++ base 'Sprite' marked serial_only_constructor() and cannot be constructed in a parallel body at 4:49. An object of such a class that dies on a worker anyway is released when the statement's workers are done, on the calling thread, in element order.

    C++ calls​

    Bound C++ functions, static methods and methods are parallel unless the host registered them serial (the binder). The library's own builtins are serial apart from pure math and to_string, so print in a body is refused before any element runs: parallel_for: host function 'print' is marked serial_function() and cannot be called in a parallel body at 3:5, and a serial static method reads parallel_for: C++ static method 'Sound::play' is marked serial_static_method() and cannot be called in a parallel body at 3:5. A method's mark covers its non-const overloads, so a const getter of the same name stays parallel. A method's receiver class is known only when it is called, so a serial method is refused then: C++ method 'publish' of 'Meter' is marked serial_method() and cannot be called in a parallel body. A non-const C++ method, or a store to a C++ property, runs only on an object the body owns: its element (a range or zipped element, which the statement proves the only element of its object, or a parallel_reduce accumulator) or one it made. On any other object, such as one a C++ function returns, only const methods run, and anything else is refused with C++ method 'add' of 'Meter' changes an object this parallel body did not make (only its const methods may run on it) or C++ property 'level' of 'Meter' is stored on an object this parallel body did not make (only an object it made takes stores).

    Random numbers​

    math::random, math::random_int and math::random_range work in a body, and in the functions, methods and constructors it calls. The statement takes one draw from the engine's stream to seed a stream of its own, and each draw depends only on that seed, the element running (the chunk, for parallel_reduce) and how many draws that element made before it. So the loop gives the same numbers on any number of cores, and the engine's stream after it is the same too: it has moved one draw for each statement whose code can draw. The numbers are not the ones the serial loop would draw, since a serial loop takes its draws in the order its elements run and a parallel one has no such order. math::random_seed in a body is refused before any element runs; seed before the loop.

    jaiscript
    math::random_seed(7);
array<int> rolls = [0, 0, 0, 0, 0, 0, 0, 0];
parallel_for (auto& r : rolls) { r = math::random_int(1, 6); }   // the same rolls on any number of cores
print(rolls.join(" "));
try { parallel_for (auto& r : rolls) { math::random_seed(r); } } catch (e) { print(e); }
    output
    3 1 2 5 2 1 2 4
parallel_for: math::random_seed cannot be called in a parallel body (seed before the loop: the loop's draws come from a stream it seeds from the engine's) at 5:46

    Handles as elements​

    An array of shared_ptr<T> or weak_ptr<T> elements runs when they name distinct objects. The statement checks, once when it is reached, that no object appears at two elements of the range and its zipped arrays, and raises parallel_for: elements 0 and 3 hold the same object (an object a body reaches through a handle element belongs to one element) otherwise. The check proves that one worker reaches each object. It proves nothing about what the object holds: its class must still be a flat value class (fields that are values, no handles), as for an element held by value. Another holder of the same object elsewhere in the program is fine, since nothing else runs during the loop.

    Reductions: parallel_reduce​

    parallel_reduce(xs, init, step, combine) folds an array on every core: xs splits into chunks whose size depends on xs.size() alone, each chunk folds its elements in order with step(acc, x) starting from its own copy of init, and the chunk results combine left to right with combine(a, b). The chunking never depends on the worker count, so a float sum is bit-identical on every machine. init should be combine's identity (0 for a sum), since every chunk starts from it; an empty array returns it. The accumulator may be a container or an object, and step is admitted like a parallel_for body: it may not write enclosing state, and a throw from it fails the call as from parallel_for. step and combine may be lambdas, their captures provisioned as a parallel_for body's are. step's body runs grafted into the chunk loop, so no call is paid per element; a step that takes its accumulator by reference (void step(T& acc, x), or -> T& returning acc) folds the chunk's accumulator in place with no copy in or out, the form for a container or object accumulator, while the by-value form T step(T acc, x) suits a scalar. The element x is taken by value. The input may hold class instances: step reads their fields and runs their methods and operators under the body rules, and every element must be its own object, as a zipped array's are, so an input holding one shared_ptr twice is refused with parallel_reduce: input elements 0 and 1 hold the same object (an object the step reaches through a handle element belongs to one element).

    jaiscript
    array<float> prices = [4.5, 12.0, 7.25, 3.0, 9.5];
float add(float a, float b) { return a + b; }
class Span { float lo = 1000000.0; float hi = -1000000.0; }
void widen(Span& r, float x) { if (x < r.lo) { r.lo = x; } if (x > r.hi) { r.hi = x; } }   // folds in place
Span join(Span a, Span b) { if (b.lo < a.lo) { a.lo = b.lo; } if (b.hi > a.hi) { a.hi = b.hi; } return a; }
print(`total ${parallel_reduce(prices, 0.0, add, add):.2f}`);
Span r = parallel_reduce(prices, Span(), widen, join);   // an object accumulator
float big = parallel_reduce(prices, 0.0, [](float a, float x) { return x > 5.0 ? a + x : a; }, add);
print(`span ${r.lo:.2f}..${r.hi:.2f} big ${big:.2f}`);
    output
    total 36.25
span 3.00..12.00 big 28.75

    The long form is the same loop written out: a zipped array of per-chunk accumulators and their chunk numbers, each chunk folding its slice in place, then a serial fold of the partial results. A body that adds into a captured total instead raises the enclosing-state error.

    jaiscript
    array<float> prices = [4.5, 12.0, 7.25, 3.0, 9.5];
int size = 2;
array<float> partial = [0.0, 0.0, 0.0];   // one accumulator per chunk of `size` elements
array<int> chunk_ids = [0, 1, 2];
parallel_for (auto& p, int c : partial, chunk_ids) {
    for (int i = c * size; i < c * size + size && i < prices.size(); i++) { p += prices[i]; }
}
print(`total ${partial.reduce((s, p) => s + p, 0.0):.2f}`);
    output
    total 36.25

    Choosing a shape​

    Use captured reads for shared inputs, a zipped output array for per-element results, and parallel_reduce for a total. Where the output shape is not known up front, the pair idiom serves: elements shaped [input..., tag] come back from parallel_transform as [tag, outputs...], collected from the result in iteration order.
