Open Questions​

Behaviors documented as observed — seven now carry design rulings, six remain open.

These docs were generated from the test suite: every example was executed on both backends before it was written down. A side effect of writing documentation that way is that you meet the language as it is, not as it was intended — and thirteen behaviors surfaced that look accidental, inconsistent, or underdocumented. Each has a verified repro (both backends, at the commit the docs were built from) and a pointer to the test that pins it (or the gap where one should be). Nothing on this list was guessed at in the docs: where a chapter touches one of these, it documents the surprising behavior as-is and points here.

This page is a feature, not a confession. A doc set with no open questions is a doc set nobody executed.

Items 1–9 came out of the core language guide; items 10–13 out of the embedding chapters. Numbering is stable: items are grouped below by ruling status, never renumbered.

Ruled​

Dev has ruled on these seven. Each keeps its verified repro and test pointer exactly as written; the ruling and current status are appended.

1. CRASH: builtin string method through a ref declaration segfaults​

jaiscript
auto s = "a";
auto& r = s;
r.length();        // segfault (0xC0000005), interpreter AND vm, Debug build

Also reachable via range-for: for (auto& s : strs) { s.to_upper(); }. Scope: string methods through a ref declaration only — array/map methods through ref decls work (auto& r = arr; r.size() fine), and string methods through ref parameters work (function f(auto& r) { return r.to_upper(); } fine). No test covers this combination (vm ref_decl tests use assignment, not method calls; string_tests never call through a ref). The docs steer around it (Value Semantics, Containers & Strings).

Ruling: a bug. The fix is in flight — the cells refactor carries it. Status: FIX IN FLIGHT.

2. Compound bitwise assignments don't parse​

f |= 4;, f &= 3;, f ^= 1;, f <<= 3;, f >>= 1; → Parse error: Expected expression. Both docs/grammar.md (assignmentOperator list) and the project instructions ("and compound assigns") advertise them, and zero tests exercise them. Intentionally unimplemented, or a gap? The docs currently say "not currently parsed — spell it out" (Operators).

Ruling: intentionally not implemented — low value. Spell it out: x = x | y. docs/grammar.md now states the omission is deliberate. Status: BY DESIGN.

3. new keyword is advertised but not parseable​

var p = new P(); → Parse error: Expected ';' after variable declaration. grammar.md documents newExpression = "new" type "(" args ")" and Design Note 9 says "Smart Pointers: new returns shared_ptr<T> automatically". The actual working spelling is shared_ptr<P> sp = P();. The AST even has new_expr — but the parser only emits it for constructor-call syntax P(...), never for the new keyword. grammar.md needs updating (or new needs implementing as sugar for the shared_ptr declaration?).

Ruling: implement it — new P(args) becomes sugar for shared_ptr<P> construction, i.e. the reference-semantics opt-in. grammar.md documents it only when it lands (the current rewrite honestly says there is no new keyword). Status: SHIPPED — new T(args) / new T{args} parse as the exact shared_ptr<T>(args) expression on both backends; a var/auto declaration keeps the shared marker (var p = new P(); IS shared_ptr<P> p = P();). grammar.md documents the sugar; pinned in language/script_class_tests.cpp (new_keyword_*).

4. private: / public: parse but are not enforced​

jaiscript
class S { private: int secret = 7; public: int peek() { return secret; } }
auto s = S();
s.secret;          // returns 7 — no access error

Per-member prefix form (private int secret = 7;) is a parse error; section labels parse and are then ignored for field access from outside. No test asserts an access violation. Is visibility future work, and should the docs promise anything? (Classes currently says "parse, but access is not currently enforced".)

Ruling: enforcement to be implemented, plus protected: — with an engine toggle if enforcement costs hot-path perf. Status: SHIPPED — private:/protected:/public: enforce at member access on both backends (private = declaring class only, protected = + subclasses, lambdas inherit their method's class, host C++ API unrestricted, hot reload permissive). Measured cost: within benchmark noise (one flag test on all-public classes), so no toggle was needed. Pinned in language/script_class_tests.cpp (member_access_*).

5. include can't return a value (design intent says it may)​

Design intent: include "may return a value". Actual: auto x = include "f.jai"; and auto x = include("f.jai"); are parse errors, and when an include is the last statement, the included file's trailing expression value is discarded (result is null). Pinned only as statement-usage in language/include_import_tests.cpp. Planned expression-include, or intent drift?

Ruling: include should return its value if the implementation isn't contorted (the data-file idiom: var cfg = include "f.jai";); if it turns out contorted, the fallback is to fix the docs to say no-return. Status: SHIPPED — the implementation was not contorted: both backends already produced the value internally, so include in expression position (var cfg = include "f.jai";, include(pathExpr), in-call use) now evaluates to the included file's result on both backends. Statement position still discards; include never caches, so the value is always fresh; import stays declaration-only. Pinned in language/include_import_tests.cpp (include_expression_*).

6. auto& over a typed array element drops the element-type constraint​

jaiscript
array<int> arr = [1, 2, 3];
auto& x = arr[1];
x = "s";           // succeeds; arr[1] is now a string inside array<int>

Pinned deliberately by vm/vm_backend_tests.cpp ref_decl_element_constraint_dropped ("D4v pin: ... (today's decl semantics)"), so this is a conscious ruling — but it punches a hole in array<T> invariants that push carefully guards (push rejects mismatches with a nice error). Long-term: keep constraint-dropping, or re-type refs?

Ruling (delegated to Claude): enforce the element type through the ref, consistent with typed-field and push enforcement. The ref_decl_element_constraint_dropped pin flips when it lands. Status: SHIPPED — element refs from typed containers carry the container's element type: auto& decls, range-for auto&, ref params bound to elements, and compound stores through them all error with the same text as direct element assignment (Cannot assign 'string' to element of type 'int'), on both backends. var (any-tagged) containers stay unconstrained. The pin is flipped to ref_decl_element_constraint_enforced, plus new shape coverage in vm/vm_backend_tests.cpp.

7. grammar.md map-literal syntax disagrees with the implementation​

grammar.md: mapEntry = "{" expression "," expression "}" (i.e. {{k, v}, ...}). Actual language (all tests, all examples): {"key": value, ...} colon syntax. grammar.md also shows override-less method overriding (now an error: "use 'override' keyword") and the new keyword (see #3). grammar.md looks stale against the current parser in several places — worth a refresh pass since it's the document a site would naturally link as "the grammar".

Ruling: the language is correct; the docs were wrong — and have been fixed (the c7644e15 grammar rewrite regenerated docs/grammar.md from the shipped lexer/parser: real keyword table, both map styles, no new, no bitwise compound assigns, override semantics). Status: RESOLVED.

Still open​

No rulings yet — more decisions soon, per Dev. Documented as observed in the meantime.

8. Single-argument print skips brace-escape processing​

print("{{x}}") prints {{x}} (raw), while print("{{x}} {}", 1) prints {x} 1. stdlib/io.hpp defines process_single_arg_escapes which would handle the single-arg case, but the single-arg fast path returns before calling it (dead code?). Minor, but it makes {{/}} behavior inconsistent between one-arg and format-path calls.

9. shared_ptr.use_count() reports 1 after a script-side alias copy​

jaiscript
class P { int x = 3; }
shared_ptr<P> sp = P();
auto alias = sp;      // alias.x = 99 IS visible through sp (they share)
sp.use_count();       // 1, not 2

Sharing works (mutations visible through both), so presumably the alias holds the same handle rather than a new strong ref — but use_count() == 1 will confuse anyone using it to debug lifetimes. Intended accounting, or should the copy bump the count?

10. Zero-arg and variadic host functions are invisible to registration_fingerprint()​

C++
auto a = jai::engine::make();
auto b = jai::engine::make();
a->registration_fingerprint() == b->registration_fingerprint();   // true (both empty)
a->add_function("zero_arg", []() -> jai::script_int { return 1; });
a->registration_fingerprint() == b->registration_fingerprint();   // STILL true (!)
a->add_function("one_arg", [](jai::script_int n) { return n; });
a->registration_fingerprint() == b->registration_fingerprint();   // false

Consequence: a .jaib saved from an engine whose only registration difference is a zero-arg or variadic function loads with registration_mismatch() == false, then fails at execute with Undefined variable 'host_bonus'. Why: the fingerprint hashes overloaded functions + registered classes + template types, but a first-time zero-arg add_function (empty param list) and add_variadic_function register as plain globals instead. Either the fingerprint should include ALL registered function names, or the docs/comments should say "overloaded/typed functions only". Zero-arg callbacks (host_reload(), frame_mark(), ...) are among the most common registrations in the shipped examples. No pinning test found for the negative case.

11. Script-class operator methods reject named-class return types (parse level)​

jaiscript
class Money {
    int cents = 0;
    bool operator<(Money o)  { return cents < o.cents; }        // parses fine
    Money operator+(Money o) { return Money(cents + o.cents); } // Parse error:
    // "<script>:N:20: Expected ';' after field declaration"
}

Workaround that parses and runs correctly on both backends: function operator+(Money o) { ... }. Primitive return types (bool, int) are accepted in operator-method declarations, but a class-typed return (Money) is not — the parser apparently treats Money operator as a field declaration. Ordinary methods accept class-typed returns (Money clone() { ... } parses). Inconsistent by shape; the fuzz generator itself only ever emits bool operator<, so the gap is invisible to the differential fuzzer. No pinning test for the rejected form.

12. Bound-value stores: object members detach at store, array/map slots keep the alias​

jaiscript
// c8 is a C++ int bound via add_global_ref
var arr = [c8];    // element KEEPS the live alias (reads track C++ until a compound)
obj.f = c8;        // member SNAPSHOTS at store time (alias dropped immediately)

Two store destinations, two aliasing lifetimes — pinned as-is in semantics/test_cpp_bound.cpp (pin_element_compound_detach_and_replace vs pin_member_compound_detach_and_replace; the test comments label the member behavior "Pinned as-is", i.e. captured, not ruled). Embedders sharing a bound global into script data structures get different staleness semantics depending on container kind. Is the long-term intent to unify (probably on "detach at store", matching plain-assign-through-ref detach), or is element aliasing load-bearing for some pattern?

13. Opaque cpp_bound objects (make_value(T*) on an unregistered type) read as null​

C++
t1_opaque_probe probe;                       // unregistered struct
auto val = eng->make_value(&probe);
val.is_cpp_bound();                          // true
val.is_null();                               // ALSO true (reads as null)
eng->execute("bop == null");                 // true; falsy in if/while
val.as<t1_opaque_probe&>().v = 42;           // yet as<T&> aliases the live object fine

The value is simultaneously "a live pointer you can alias through as<T&>" and "null as far as the script can tell" — script code cannot even null-check it meaningfully to distinguish "no object" from "opaque host object". If the intent is "opaque pins are host-only pass-through tokens", the docs could say so explicitly; if scripts are ever meant to hold them, == null being true looks like a trap. (Pinned as-is in semantics/test_cpp_bound.cpp::pin_unregistered_class_bound; deliberately left out of the chapters pending a ruling.)
