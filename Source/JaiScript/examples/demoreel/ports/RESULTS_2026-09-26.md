# demoreel: JaiScript vs Lua 5.4, 2026-09-26

The demoreel (17 scenes, `scenes/*.jai`) against its Lua 5.4 / sol2 port
(`ports/lua/*.lua`), both driven by the shared host (`demoreel_host.cpp`, see
`../PORTING.md`). Same algorithms, same 100x40 cells (100x80 pixels), same frame
bytes.

- Machine: the MSI box (Core Ultra 9 285HX), Windows 11, other agents idle while
  the timing lock was held.
- Build: `x64-Release BENCHMARKS` (MSVC 14.51 Release, JaiScript LTCG), branch
  `demoreel-lua-port` at the Lua port commit (master c377b71f + OSSUARY ff623053).
- Lua: the repo's vendored Lua 5.4 built from source as `demoreel_lua_runtime`
  (MSVC `/O2`, same CRT), sol2 bindings; `demoreel_lua` (`-DDEMOREEL_PORT_LUA=ON`).
- JaiScript parallel = the engine default width (min(hardware - 1, 6) = 6 workers)
  for `parallel_transform`; serial = `--workers 1`. Lua runs the same row functions
  as serial loops.

## Parity

**Every frame is bit-identical.** The Lua `--smoke` stream hash is
`1a0337f81a618c10`, the same as `jai_demoreel --smoke` on both JaiScript backends
(1700 frames: all 17 scenes on 3 s smoke durations plus every transition). Each
`--perf` scene hash below is also identical across all five runtimes. No scene
needed an exception.

## Reading the numbers

- **Serial VM vs Lua**: Lua 5.4 is 1.15x-7x faster per scene, 4.0x on the sum
  without OSSUARY, 6.7x with it. Closest: the table-driven integer scenes
  (PLASMA 1.15x, TUNNEL 1.25x, CANYONRUN 1.56x, KINSTEIN 1.77x), where the VM's
  typed-lane cells work. Furthest: call-heavy float code (OSSUARY 7x, DONUT 6.5x,
  SPONGEWORKS 5.3x) and object/field traffic (BOIDS 6.3x, POWDER 4.7x).
- **Parallel VM vs Lua**: with six workers on its row sections the VM beats serial
  Lua on LAVALAMP (0.79x) and ties on CHROME (0.99x); it stays behind on the
  heaviest parallel scene, OSSUARY (1.33x), and on SPONGEWORKS (2.3x). The whole
  reel is 1.49x Lua's time.
- **Parallel scaling in JaiScript**: 6 workers give 4.1-5.2x on the vm (DONUT
  4.4x, CHROME 4.8x, OSSUARY 5.2x, LAVALAMP 4.2x) but only 2.0x on JULIA and 2.3x
  on SPONGEWORKS (uneven row costs: JULIA's interior rows run the full 48
  iterations, SPONGEWORKS updates one Bayer phase per frame).

## Fairness notes

- Same frame content by construction: the hash gate covers every byte.
- Lua's row functions write the grid in place; JaiScript's return a row array that
  the scene copies into the grid (the `parallel_transform` contract). This is a few
  hundred microseconds a frame of array traffic the JaiScript serial runs pay and
  Lua does not.
- `--workers 1` still routes rows through `parallel_transform` on one worker, not
  through a plain script loop.
- Lua keeps hot state in upvalue locals and caches fields into locals at the top
  of hot functions, as idiomatic Lua does; the JaiScript scenes do the same with
  `var&` and local copies.
- The JaiScript interpreter numbers are included for scale; the comparison is VM
  vs Lua.

## Port notes

- 5.9k lines of Lua for 5.8k lines of JaiScript (the scene files one to one, plus
  main.lua); a 119-line adapter.
- The first full smoke matched on every scene but one:
  POWDER. Its element classes take the scene Rng as `var r` BY VALUE, and
  JaiScript copies a bound object into a by-value parameter, so ember burn-out and
  plant growth draw from a fresh copy of a scene rng that `do_fall`/`do_smoke`
  never advance (every such draw within a frame sees the same state). The port reproduces it with a
  `copy()` binding (`r:copy():next(n)`). Whether the scene meant that is a separate
  question; the reference is the spec here.
- Integer semantics were translated site by site: truncating `/` via
  the `idiv` helper only where an operand can be negative (starfield
  interpolation, voxelspace heights, the kinstein tracer, the voxel roll), `//`
  otherwise; arithmetic `>>` of a possibly negative value as `// 2^k` (plasma);
  C truncation for every float-to-int slot (`itrunc`), never `math.floor`, except
  where the reference itself floors.
- Lua's `math.log(x, 2)` calls C `log2` in 5.4, matching JaiScript's `log2`;
  `math.atan(y, x)` is `atan2`. Both runtimes call the same CRT, so every float
  result matches bit for bit.
