# Gator Quest smoke: JaiScript against Lua, 2026-10-02

The Lua port in this folder runs the simulation of `gatorquest.jai -- smoke` (world generation, content tables, mobiles,
spawners, combat, items, quests, actions, bots, the tick, the state hash). JaiScript: master 1661f023c, the Release
runner (`jaiscript_runner`, MSVC 19.51, /O2 /Ob2 /GL, /LTCG, static CRT, debugger compiled in and off with `--no-debug`).
Lua 5.4.8 and 5.5.1: stock `lua.c` and library from the pinned sources, /O2 /Ob2 /Oi /Ot /GL /MT /DNDEBUG
/DLUA_COMPAT_5_3, /LTCG. LuaJIT 2.1 (24c20c94): the cached build of the kernel suite, run with the JIT on and with `-joff`.

line, the run line's mobile/kill/spawn counts, each bot's title, hit points, gold, fame, kills, deaths, position,
skills, pack, worn items, journal and plan, and STATE_HASH. All 27 configurations below match under Lua 5.4.8, Lua 5.5.1,

## Where the time goes (6000 ticks, 4 bots, seed 1)

JaiScript: the VM-profile build (`/DJAISCRIPT_VM_PROFILE`, Release, same source; rdtsc pairs per instruction, so cheap
instructions weigh more than in the plain build; the whole run, world generation under 1% of it). Inlined callees
(`tile_now`, `bot_walkable`, `mob_at`, `in_world`, `walk_at`, `cheb`) count in their caller. Lua 5.4.8: `profile.lua`,
the tick loop sampled every 1000 VM instructions (shares of executed Lua instructions; C functions and the collector are
not sampled). LuaJIT `-joff`: its time sampler (`-jp=F`). Inclusive shares; ms/tick = share x the CPU medians above
(VM 5.42, Lua 5.4.8 1.20), so the absolute columns inherit both profiles' approximations.

| subsystem | VM share | VM ms/tick | Lua 5.4 share | Lua 5.4 ms/tick | VM / Lua |
|---|---:|---:|---:|---:|---:|
| bots: BFS route planning (`bfs_path` + walkability) | 46.3% | 2.51 | 57.5% | 0.69 | 3.6 |
| bots: the rest (target scans, gathering, gear, intents) | 17.9% | 0.97 | 14.4% | 0.17 | 5.6 |
| `status_tick` (poison, burn, lava, regen over all mobiles) | 15.5% | 0.84 | 14.8% | 0.18 | 4.7 |
| `ai_tick` (monster brains) | 13.0% | 0.70 | 11.1% | 0.13 | 5.3 |
| `players_tick` (intents, actions, auto-attack) | 4.5% | 0.25 | 2.1% | 0.03 | 10 |

Both sides spend their time in the same places: the bots' pathfinding is about half the run, the monster and status
passes a quarter. LuaJIT `-joff` (time) agrees: `bfs_path` 22% self, `tile_now` 21%, `bot_walkable` 10%, `mob_at` 7%,
`status_tick` 7%. The VM's deficit is broad (3.6x to 10x per subsystem), not one pathological function.

VM leads (from the profile's lines and slot census, confirmed by micro-benchmarks in a function body, under the same
load):

- A field read through an element of a program-scope `array<Class>` (`MONS[k].regen`, `ITEMS[b].kind`, `GI_ITEM[i].base`,
  `CHARS[s].active`, `TILES_DEF[t].station`) costs ~210 ns; the same read through a local `array<Small>& loc = SMALLS`
  ~58 ns, a program-scope flat `array<int>` element ~25 ns, the Lua table equivalent ~20 ns. It is not a copy (a
  2-field class costs the same as an 8-field one). `int rg = MONS[MOB_KIND[m]].regen;` alone is ~19% of `status_tick`
  (~1400 profile cycles per execution, 3 million executions). Gator Quest reads its content tables and pools this way
  everywhere.
- Declared record copies: `ItemDef d = ITEMS[it.base];` in `item_stat` (inlined into `player_bonus`, run for every worn
  item on every stat query) deep-copies an `ItemDef` (4 strings, 2 arrays). `player_bonus` is 4.7% of the VM run (~108k
  profile cycles per call) against 1.0% of Lua's instructions (the port aliases the record). A record copy measured
  ~1440 ns against ~340 ns for `Rec& d`. The script could say `ItemDef& d`; the VM could elide a copy that is only read.
- The BFS loop executes ~70 boundary materializations per dequeued tile (proven scalar slots boxed for a general op:
  `nx`, `ny`, `ww`, the inlined `x`/`y`) beside ~176 typed operations and ~108 other operations; the slot census
  names them.
- The 2D neighbourhood scans (`bot_nearest_hostile` r=9, `find_target` r=7..10, `spell_target`) run as cell blocks
  (~90k profile cycles per block entry); with their callers they are ~14% of the VM run (`bot_fight_and_loot` 8.8% self,
  `find_target` 4.9%) against ~9% of Lua's instructions.

## Port decisions

- Arrays are 0-based Lua tables (`t[0]` lives in the hash part, the rest in the array part), so every id, index and
  hashed value is the script's own. The hot pools carry explicit sizes (`MOB_N`, `GI_N`, `SP_N`, `EV_N`, `CHAR_N`).
- JaiScript `/` and `%` on integers truncate; Lua's `//` and `%` floor. Every division or remainder that can see a
  negative operand goes through `idiv` / `imod` (C semantics); `//` and `%` remain where both operands are non-negative.
  Checked overflow never fires in the script (it would abort the run), so Lua's wrapping 64-bit integers agree.
- Class instances are values in JaiScript and tables are references in Lua. An `Item` is copied (`copy_item`) where the
  script's copy is stored into a container or mutated afterwards; read-only record reads (`ItemDef d = ITEMS[b]`,
  `MonDef d = MONS[k]`, `TileDef td = ...`) alias the table, which is what a Lua program does and observably the same.
  The script pays for those copies; the hot-spot section shows where.
- Lua idioms where the script allocates: two-element `[x, y]` results are two return values; the per-tick event arrays
  and the BFS queue are reused with a count instead of being replaced by `[]` each tick.
- Loop bounds that the script re-evaluates every iteration are re-evaluated in the port (`status_tick` visits mobiles a
  slime split adds mid-loop; `open_chest` rolls `1 + rnd(3)` on every test).
- Loop-invariant loads are hoisted into locals where a Lua programmer would (`W_H[w]` in `bfs_path`, `MOB_X[m]` and
  `MOB_Y[m]` in the neighbourhood scans, `TICK` in `ai_tick` and `spawners_tick`); the script re-reads them.
- Functions are globals across modules; each module keeps the arrays and the earlier modules' functions it uses in
  locals (the arrays are created once and cleared in place, so the locals stay valid).
- LuaJIT: `luajit/` is generated by `to_luajit.py` from the same source (operators become `bit` calls and
  `math.floor`), with a hand-written `luajit/gq_util.lua` whose 32-bit hash and RNG multiply exactly on doubles.
  LuaJIT allows 60 upvalues per function: `attack` reads its enum constants through `SK`, `FX`, `EV`, `SLOT` tables.
- The `/invite` chat command lowers names in place, like the script's `to_lower()`; no bot uses chat.
